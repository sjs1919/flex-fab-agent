### 第 4 层 · 工具注册中心（`tools/registry.py`）★ 重点

**读什么：** `registry.py` 全部（约 180 行）

**这是连接 Agent 和工具的桥梁。** 为什么要有注册中心？因为 week1 是硬编码 if/elif 链（O(n) 线性查找），注册中心改为 O(1) 字典查找。

```python
class ToolRegistry:
    def register(self, name, description, parameters, handler, ...):
        """注册工具：Schema + Handler 一起注册"""
        self._tools[name] = ToolSchema(...)     # 存元数据（给 LLM 看的）
        self._handlers[name] = handler          # 存函数（执行用的）

    def get_tool_defs(self) -> list[dict]:
        """返回 OpenAI Function Calling 格式的工具列表，直接传给 LLM"""

    def execute(self, name, arguments, token=None, audit=None):
        """执行工具，三步：① 参数白名单过滤 ② RBAC 校验 ③ 调 handler"""
        # 参数白名单：只传 Schema 定义的参数，防 LLM 传多余字段
        valid_keys = set(schema.parameters.get("properties", {}).keys())
        filtered = {k: v for k, v in arguments.items() if k in valid_keys}
        # RBAC 校验（token 非空时）
        if token is not None:
            allowed, reason = check_tool_permission(token, name, audit)
            if not allowed: return f"❌ 鉴权拒绝：{reason}"
        # 执行 + tracer 记录
        with tracer.span(f"tool:{name}", server=schema.server):
            return self._handlers[name](**filtered)
```

**build_default_registry() 注册了 7 个工具：**
- 3 个订单工具（order_server）
- 3 个资源工具（resource_server）
- 1 个 RAG 工具 search_knowledge_base（rag_server，懒加载）

**关注点：**
- `register()` 一次调用完成 Schema + Handler 绑定，不会出现"定义了但没实现"或反之
- `execute()` 的**参数白名单**是关键安全机制——LLM 可能传多余参数，白名单过滤保安全
- `execute()` 的 **RBAC 校验**是洋葱型防御的第 3 层（见第 8 层）
- RAG 工具用**懒导入包装**——注册时不加载重依赖，首次调用才拉 jieba/chromadb/sentence_transformers

### 第 5 层 · LLM 调用基座（`core/llm_client.py`）

**读什么：** `llm_client.py` 全部（约 80 行）

**这是 Agent 的"大脑"——所有 LLM 调用都走这里的统一入口。**

```python
def call_llm(messages, tools=None, max_tokens=500, temperature=0.3):
    """统一 LLM 调用，内置主备自动降级。遍历 PROVIDERS，第一个成功即返回"""
    for p in PROVIDERS:
        if not p.get("enabled") or not _is_real_key(p["api_key"]):
            continue
        try:
            client = OpenAI(
                api_key=p["api_key"],
                base_url=p["base_url"],
                http_client=httpx.Client(trust_env=False),  # ★ 绕过 Windows 死代理
            )
            kwargs = {"model": p["model"], "messages": messages, ...}
            if tools: kwargs["tools"] = tools  # 有工具就传工具
            with tracer.span("llm:call", provider=p["name"], model=p["model"]) as s:
                resp = client.chat.completions.create(**kwargs)
            # 记录 token 用量到 span
            if resp.usage:
                s.attributes["tokens_in"] = resp.usage.prompt_tokens
                s.attributes["tokens_out"] = resp.usage.completion_tokens
            return resp
        except Exception as e:
            print(f"  ⚠️  [{p['name']}] 失败: {e}，切下一个...")
    raise RuntimeError(f"所有 provider 均失败")
```

**关注点：**
- `trust_env=False`：绕过 Windows 系统代理（cc-switch 退出后注册表可能残留死代理）
- 主备降级对调用方透明——调用方不关心当前用的是豆包还是 DeepSeek
- token 用量记录在 span 的 attributes 里，随观测层导出
- `call_llm_simple(system, user)` 是便捷形式，供 RAG / 子 Agent 等无需工具的简单调用

### 第 6 层 · 单 Agent 编排（`graph/`）

**读什么：** 按顺序 `graph/state.py` → `graph/single_agent_graph.py` → `graph/checkpointer.py`

#### 6.1 状态定义（`state.py`）

```python
class AgentState(TypedDict):
    messages: list[dict]       # 对话历史（system + user + assistant + tool）
    tool_results: list[dict]   # 工具调用结果汇总
    iteration: int             # 当前迭代次数（防死循环，上限 5 轮）
    final_answer: str          # 最终输出
```

**关注点：** 4 个字段贯穿所有节点，显式 TypedDict 比裸 dict 安全

#### 6.2 状态图（`single_agent_graph.py`）★ 重点

**这是单 Agent 的核心编排逻辑——4 个节点 + 1 条条件边组成循环：**

```
START → analyze_intent → select_and_execute → evaluate_results
          ↑                    ↑                    │
          │                    └──────────┬─────────┘
          │                needs more data?  (should_continue)
          │                               │
          │                    data enough │
          │                               ▼
          │                        generate_answer → END
          │
          (这个循环最多 5 轮，防死循环)
```

**4 个节点：**

| 节点 | 做什么 | 关键逻辑 |
|------|--------|----------|
| `analyze_intent` | 打印用户问题 | 当前仅日志；生产可扩展为意图分类器 |
| `select_and_execute` ★ | LLM 决策调哪些工具 → 执行 → 注入结果 | 核心：LLM 返回 tool_calls → 逐个调 registry.execute() → 结果注入 messages |
| `evaluate_results` | 评估数据是否足够 | 当前是 noop，由 should_continue 条件边决定 |
| `generate_answer` | 汇总所有数据生成最终建议 | 追加 system prompt 要求 LLM 综合输出 |

**条件边 `should_continue`：**
```python
def should_continue(state):
    if state["iteration"] >= 5: return "generate_answer"  # 安全阀
    if last_msg["role"] == "tool": return "select_and_execute"  # 还有结果要处理
    if last_msg["role"] == "assistant" and last_msg.get("tool_calls"):
        return "select_and_execute"  # LLM 还想调更多工具
    return "generate_answer"  # 数据够了，生成答案
```

**关注点：**
- 图通过 `build_single_agent_graph(registry, checkpointer)` 工厂构造——registry 决定 Agent 可用哪些工具，依赖注入而非硬编码
- `select_and_execute` 里 LLM 返回的 tool_calls 逐个执行，结果按 OpenAI 格式注入 messages（assistant 消息含 tool_calls 元数据 + tool 消息含执行结果）
- 5 轮安全阀：防止 LLM 在"调工具→看结果→调工具"里无限循环

#### 6.3 状态持久化（`checkpointer.py`）

```python
def build_checkpointer():
    mode = os.getenv("CHECKPOINTER", "sqlite").lower()
    if mode == "none": return None
    if mode == "memory": return MemorySaver()
    # sqlite 默认：落盘 demo/data/checkpoints.db，重启可恢复
    conn = sqlite3.connect(str(RUNTIME_DIR / "checkpoints.db"), ...)
    return SqliteSaver(conn)
```

**关注点：**
- 为什么不用 `add_messages` reducer？它会把消息转成 LangChain 对象，而本 demo 全链路按 dict 处理，直接喂 OpenAI SDK。改对象类型风险大，保持 dict + 覆盖语义
- 多轮对话时，从 checkpoint 取历史 messages 追加新问题，每轮重置 tool_results/iteration

```python
        hit = semantic_cache.get(query)
        if hit: return {"final_answer": answer, "tool_results": []}  # 命中→直接返回

    # 2. 构建图（模块级缓存，首次构建接 checkpointer）
    app = _get_app(registry)

    # 3. 多轮：从 checkpoint 取历史追加新问题；单次：新起 system + user 消息
    if thread_id: hist = app.get_state(config).values.get("messages", [])
    initial_state = {"messages": [system_prompt] + hist + [user_msg], ...}

    # 4. 执行图
    result = app.invoke(initial_state, config)

    # 5. 缓存写入（仅无多轮上下文）
    if thread_id is None: semantic_cache.put(query, result["final_answer"])
    return result
```

**关注点：**
- 语义缓存只对 `thread_id=None` 的独立问题生效——多轮对话答案依赖前文，不能复用首轮缓存
- 图编译用模块级缓存 `_app`，避免每次请求重建图（checkpointer 是单例，跨请求复用连接）
- 多轮时显式从 checkpoint 取历史 messages，而非依赖 LangChain 的自动 reducer

#### 10.2 混合检索（`retriever.py`）★ 核心

**四步检索管线：向量召回 → BM25 召回 → RRF 融合 → Cross-Encoder 重排**

```
query: "广州航天合同有什么特殊条款"
  │
  ├─→ 向量检索（Chroma MiniLM）：top-10 候选
  ├─→ BM25 检索（jieba 分词 + Okapi BM25）：top-10 候选
  │
  ├─→ RRF 融合（两路按排名打分 1/(k+rank)，相同 chunk 分数累加）
  │
  └─→ Cross-Encoder 重排（BAAI/bge-reranker-base，对每个 (query, chunk) 算相关分）
       └─→ 取 top-3 返回
```

**为什么混合？** 纯向量（MiniLM）中文召回弱（top1 常召回"历史延期记录"而非目标合同），BM25 补关键词精确匹配，RRF 融合两路，Cross-Encoder 精排把目标合同顶到 top1。

**重排器加载防坑（`load_reranker`）：**
```python
def load_reranker(model_name="BAAI/bge-reranker-base"):
    # 先尝试离线加载（已缓存则秒级）
    os.environ["HF_HUB_OFFLINE"] = "1"
    huggingface_hub.constants.HF_HUB_OFFLINE = True  # ★ 必须 patch constants
    try:
        return CrossEncoder(model_name)
    except:
        # 离线失败 → 走代理下载 → 缓存到本地
        os.environ["HTTPS_PROXY"] = "http://127.0.0.1:3450"
        return CrossEncoder(model_name)
```

**关注点：**
- `huggingface_hub` 在 import 时把 `HF_HUB_OFFLINE` 固化到 constants，运行时设 env 无效，必须直接 patch constants
- 四步管线中每一步都可以独立替换（换 embedding 模型、换 BM25 参数、换 reranker）
- 懒加载：`_ensure_rag()` 首次调用才初始化向量库 + BM25 + reranker，非 RAG 问题零开销

### 第 11 层 · 语义缓存（`cache/semantic_cache.py`）

**读什么：** `cache/semantic_cache.py` 全部（约 70 行）

**相似问题直接返回缓存答案，跳过 LLM 调用。** 教学版用 Chroma（cosine 空间），生产换 Redis。

```python
def get(query, threshold=0.20):
    """查相似问题：向量检索 → 距离 ≤ 阈值则命中"""
    col = _get_collection()  # 独立 Chroma collection（cosine 空间）
    res = col.query(query_texts=[query], n_results=1)
    if res["distances"][0][0] <= threshold:
        return (answer, distance)  # 命中
    return None  # 未命中

def put(query, answer):
    """存入缓存：query 作为 document，answer 存在 metadata"""
    qid = hashlib.md5(query.encode()).hexdigest()[:16]
    col.upsert(ids=[qid], documents=[query], metadatas=[{"answer": answer}])
```

**阈值校准（MiniLM cosine distance，越小越相似）：**
- 完全相同 0.00 · 多标点 0.04 · 近义改写 0.17 · 较远改写 0.37 · 不相关 0.46+
- 默认 0.20：catches 同义/标点/近义改写，排除较远与不相关

**关注点：**
- 仅对 `thread_id=None` 的独立问题启用（多轮上下文不可复用，详见第 7 层）
- 命中/未命中记为 `cache:lookup` span（result=hit/miss + distance），随观测层导出

### 第 15 层 · 工具沙箱（`tools/sandbox.py` 🆕 R1）— 工具挂了怎么兜底

**读什么：** `tools/sandbox.py` 全部（约 90 行）

**关注点：**
- `run_with_retry(handler, args, tool_name)` — 每个工具调用包裹在这个函数里，对上层透明
- 超时控制：用 `threading.Timer` 做跨平台超时（生产换 subprocess），默认 10s
- 指数退避重试：1s → 2s → 4s，最多 3 次（TOOL_MAX_RETRIES）
- 返回三元组 `(result_str, success, retries)` — registry 不感知重试细节
- 全部重试失败时返回结构化错误（而非崩溃），LLM 收到错误后可换策略

**为什么不是裸 try/except：** 异常捕获只兜底一次，Agent 没法知道"这次失败是不是偶发的"。重试 + 退避让瞬时故障自愈。

**集成点：** `tools/registry.py:execute()` 中调用，trace 记录 `tool_success` 和 `tool_retries`。

### 第 18 层 · Agent 评估（`eval/` 🆕 R6 + 三层升级）— 怎么量化 Agent 好不好

**读什么：** `eval/ground_truth.json`（数据集）→ `eval/metrics.py`（工具层）→ `eval/trajectory.py` + `eval/trajectory_capture.py`（轨迹层）→ `eval/judge.py` + `eval/judge_prompt.py`（语义层）→ `eval/runner.py`（运行器）

**关注点：**
- 10 组排产场景 ground truth，每组含 expected_tools + expected_order_ids + checks（must_contain / must_not_contain / min_tools_called）
- **工具层**（`metrics.py`）：工具 F1 + 完整性 + 订单召回 + **min_tools_called**（该调 N 个工具、实际少于 N → 工具分直接 0）
- **轨迹层**（`trajectory.py` + `trajectory_capture.py`）：`path_efficiency`（同一工具冗余调用扣 0.2）+ `retry_quality`（每次重试扣 0.2、失败扣 0.3，全失败清零）+ `loop_detection_penalty`（循环给 0），加权 0.4/0.4/0.2
- **语义层**（`judge.py` + `judge_prompt.py`）：复用 `core.llm_client.call_llm` 的自研 LLM-as-Judge，输出 JSON `{faithfulness, answer_relevancy}`；无检索上下文时 faithfulness 降级 0、relevancy 用关键词启发式兜底
- **聚合**：`overall = 工具×0.5 + 轨迹×0.3 + 语义×0.2`，case ≥0.6 算 pass，回归基线 ≥7/10
- **可视化**：`eval/report.py` 单页 HTML，三层指标 + 通过/失败 + 循环标记
- **回测**（`backtest/`）：让 Agent 复盘 `data/历史延期记录.txt` 提取的 5 个真实案例，按人工复盘结论的 `expected_keypoints` 覆盖度评分
- 用法：`python -m demo.eval.runner` / `--mode multi` / `--case eval_001` / `--no-judge` / `--report`
- 一键自动化：`python run_all_tests.py [--eval] [--report]`（pytest 全量 → 三层评估 → HTML 报告，等价 `./test_demo.sh`）

## 第三部分：数据流全景（一个请求的完整生命周期）

以 `python -m demo.main "查询紧急订单"` 为例：

```
1. main.py: main()
   ├─ 解析参数：query="查询紧急订单", mode="single"
   └─ _run_with_trace(run_single_agent, query)
        │
2. tracer.reset()  ← 清空上一轮 span
   cost_tracker.reset()  ← 清空上一轮费用
        │
3. agents/single_agent.py: run_single_agent("查询紧急订单")
   ├─ semantic_cache.get("查询紧急订单")  ← 查缓存（miss）
   ├─ _get_app(registry)  ← 构建/复用 LangGraph 图
   │    └─ graph/single_agent_graph.py: build_single_agent_graph(registry)
   │         ├─ registry.get_tool_defs()  ← 7 个工具的 OpenAI Function Calling schema
   │         └─ compile(checkpointer=SqliteSaver)  ← 接 sqlite 持久化
   ├─ initial_state = {messages: [system_prompt, user_msg], tool_results: [], iteration: 0}
   └─ app.invoke(initial_state)
        │
4. LangGraph 执行循环
   ├─ analyze_intent: 打印 "用户提问：查询紧急订单"
   ├─ select_and_execute:
   │    ├─ core/llm_client.py: call_llm(messages, tools_schema)
   │    │    ├─ L1 精确缓存查 llm_cache.get()  ← miss
   │    │    ├─ tracer.span("llm:call")  ← 记录 LLM 调用
   │    │    ├─ 遍历 PROVIDERS: 火山豆包 → client.chat.completions.create()
   │    │    └─ cost_tracker.record() + llm_cache.put()  ← 计费 + 写入缓存
   │    ├─ LLM 返回 tool_calls: [{function: {name: "query_orders", arguments: {status: "紧急"}}}]
   │    └─ registry.execute("query_orders", {status: "紧急"})
   │         ├─ tracer.span("tool:query_orders")  ← 记录工具调用
   │         ├─ 参数白名单过滤
   │         ├─ RBAC 校验（单 Agent 无 token，放行）
   │         ├─ sandbox.run_with_retry(handler, args) 🆕 R1 ← 超时控制 + 指数退避重试
   │         └─ tools/order_tools.py: query_orders(status="紧急")
   │              └─ tools/data.py: load_orders() → 过滤 → format_table()
   ├─ evaluate_results: 🆕 R3 检查工具结果质量（非空/非错误）+ 数据完整性（有订单+资源数据）
   ├─ should_continue: needs_retry/needs_more → "select_and_execute"；末条 tool → "select_and_execute"
   ├─ select_and_execute（第 2 轮）:
   │    ├─ should_compress 检查 🆕 R4 ← 超出阈值则压缩早期消息
   │    └─ call_llm(messages) → LLM 看到工具结果，决定不再调工具，直接回答
   ├─ should_continue: 末条是 assistant 文本 → "generate_answer"
   └─ generate_answer:
        ├─ call_llm → LLM 生成排产建议
        └─ run_guardrails(answer) 🆕 R2 ← 越权/敏感/缺失段落检查，拦截则重试
        │
5. 回到 single_agent.py
   ├─ 打印 "最终调度建议" + 工具调用统计
   └─ semantic_cache.put("查询紧急订单", answer)  ← 写入缓存
        │
6. 回到 main.py: _run_with_trace()
   ├─ tracer.format_text()  ← 打印 trace 摘要
   ├─ cost_tracker.format_text()  ← 打印费用摘要
   └─ tracer.flush()  ← 批量导出 span（console/otel/none）
```

## 第五部分：持久化全景（6 种存储，全链路落盘）

> demo 涉及 6 种持久化，分布在 4 个目录。每种存储的数据形态、生命周期、清理策略各不相同。
> 理解它们才能看懂「重启不丢」「跨容器恢复」「成本分析」的实现。

### 5.1 全景一览

| # | 存储 | 类型 | 位置 | 管理模块 | 用途 | 生产演进 |
|---|------|------|------|---------|------|---------|
| ① | `checkpoints.db` | SQLite | `RUNTIME_DIR/` | `graph/checkpointer.py` | 多轮对话上下文、跨进程恢复 | **PostgreSQL**（多副本读写，连接池，LangGraph 原生支持 `AsyncPostgresSaver`） |
| ② | `tokens.db` | SQLite | `RUNTIME_DIR/` | `auth/token_exchange.py` | STS Token 持久化，重启不丢 | **PostgreSQL** 或 **Redis**（TTL 自动过期，无需应用层删过期行） |
| ③ | `audit.jsonl` | JSONL 文件 | `RUNTIME_DIR/` | `auth/audit_logger.py` | 审计日志落盘，事后追溯 | **stdout → Loki / ELK**（集中收集 + 全文检索，不改代码，改日志采集器） |
| ④ | `llm_cache.db` | SQLite | `RUNTIME_DIR/` | `cache/llm_cache.py` | L1 精确缓存，相同 prompt 命中 <1ms | **Redis**（内存级延迟 <0.1ms，TTL 自动过期，高 QPS） |
| ⑤ | `cache_db/` | Chroma 向量库 | `RUNTIME_DIR/` | `cache/semantic_cache.py` | L2 语义缓存，近义改写命中省 token | **Redis + bge-large-zh**（毫秒级向量检索，更强的中文 embedding） |
| ⑥ | `chroma_db/` | Chroma 向量库 | `RUNTIME_DIR/` | `rag/knowledge_base.py` | RAG 知识库，合同条款混合检索 | **Milvus / PGVector**（独立向量服务，支持增量索引、多租户、混合标量过滤） |

> `RUNTIME_DIR` 默认 = `demo/data/`（宿主直接跑），容器内 = `/data/runtime/`（Docker volume 挂载）。
>
> **为什么现在是 SQLite 而不是 PostgreSQL？** demo 阶段零外部依赖，一键启动。SQLite 在单机低并发下足够——3 个 SQLite 文件的写频率都不高（checkpoint 每图节点 1 次，token 签发低频，缓存写 LLM 响应后 1 次）。生产多副本部署时，SQLite 的文件锁会成为瓶颈，那时切换到 PostgreSQL + Redis。**LangGraph 的 `AsyncPostgresSaver` 换一行 import 即可切换**，checkpoint schema 完全兼容。

### 5.2 每种存储详解

#### ① checkpoints.db — LangGraph 状态检查点

```
写入者：LangGraph SqliteSaver（checkpointer）
数据：每个 thread_id 的完整 AgentState
  ┌─ messages:       对话历史（system/user/assistant/tool 消息列表）
  ├─ tool_results:   每轮工具调用结果
  ├─ iteration:      当前迭代次数
  └─ final_answer:   最终回答

生命周期：
  写入  — 每个图节点执行后 LangGraph 自动 write_checkpoint
  读取  — 新请求带 thread_id → 恢复历史 messages
  清理  — 无自动清理；多轮对话用 /new 建新 session，旧 session 残留
         生产建议：按最后访问时间 TTL 清理（缺口 #6）
```

代码路径：
- `graph/checkpointer.py` — `get_checkpointer()` 按 `CHECKPOINTER` 环境变量创建
- `agents/single_agent.py` — `app.invoke()` 时传 `{"configurable": {"thread_id": thread_id}}`
- `api.py:81-95` — `GET /threads/{id}/history` 读回历史

#### ② tokens.db — STS Token 持久化

```
写入者：auth/token_exchange.py 中的 SqliteTokenStore
数据：
  ┌─ token_id:     主键（uuid hex，12 位）
  ├─ subject:      用户/Agent 身份
  ├─ role:         角色（admin/scheduler/reviewer/operator/viewer）
  ├─ permissions:  工具权限列表（JSON）
  ├─ source:       "user" | "token_exchange"
  ├─ parent_trace: 父 Token 链路（审计追溯用）
  ├─ issued_at:    签发时间（unix timestamp）
  └─ expires_at:   过期时间（unix timestamp）

生命周期：
  写入  — issue_user_token() / exchange() 时 save()
  读取  — get_token() / exchange() 时 get()；读时自动清理过期 Token
  清理  — revoke() 单个删除；revoke_all() 全清；过期 Token 读时自动 delete
```

代码路径：
- `auth/token_exchange.py:96-143` — `SqliteTokenStore` 实现
- `auth/token_exchange.py:146-152` — `_build_token_store()` 按 `TOKEN_STORE` 选后端

#### ③ audit.jsonl — 审计日志落盘

```
写入者：auth/audit_logger.py 中的 AuditLogger._persist()
格式：每行一个 JSON 对象（JSONL，追加写，不覆盖）

{"id": "a1b2c3d4", "trace_id": "e5f6...", "timestamp": "2026-08-05T10:30:00",
 "level": "INFO", "action": "tool.execute", "subject": "scheduler:reviewer",
 "target": "query_orders", "params": {"status": "紧急"},
 "result_summary": "找到 3 个紧急订单..."}

生命周期：
  写入  — 每次 audit.log() 即时追加一行（_persist 内 open+append+close）
  读取  — 无内置查询（用 grep/jq 读）；生产建议 ELK/Loki 集中收集
  清理  — 无自动清理；文件持续增长（生产加 log rotate）
```

代码路径：
- `auth/audit_logger.py:47-56` — `_persist()` 方法

- 环境变量：`AUDIT_LOG=none` 禁用 / `AUDIT_LOG_PATH` 自定义路径

#### ④ llm_cache.db — L1 精确缓存

```
写入者：cache/llm_cache.py，在 call_llm 成功后自动 put()
缓存 key：MD5(messages + tools + model + max_tokens + temperature)

数据：
  ┌─ cache_key:        主键（32 位 MD5 hex）
  ├─ content:          LLM 文本回答
  ├─ tool_calls:       Function Calling 结果（JSON，无则为 null）
  ├─ prompt_tokens:    输入 token 数
  ├─ completion_tokens:输出 token 数
  ├─ model:            使用的模型名
  └─ created_at:       写入时间（unix timestamp，TTL 判断用）

生命周期：
  写入  — call_llm 成功后 put()
  读取  — call_llm 前 get()；命中 → 返回 _CachedResponse，跳过 API 调用
  清理  — 读时 TTL 过期自动 delete；clear() 全清；stats() 看 expired 数量
  注意  — 缓存命中不触发 cost_tracker（无实际 API 消耗），span 记 cost_saved 预估
```

代码路径：
- `cache/llm_cache.py` — 全部逻辑
- `core/llm_client.py:87-102` — 缓存查询 + `_CachedResponse` 返回
- `core/llm_client.py:115-122` — 缓存写入
- 环境变量：`LLM_CACHE=on/off`、`LLM_CACHE_TTL=3600`

#### ⑤ cache_db/ — L2 语义缓存（Chroma）

```
写入者：cache/semantic_cache.py
数据：Chroma collection "semantic_cache"，cosine 空间

每条记录：
  ┌─ id:       MD5(query) 前 16 位（upsert 同 id 覆盖）
  ├─ document: 原始用户问题
  └─ metadata: {"answer": LLM 回答}

生命周期：
  写入  — 单 Agent 回答后 put()（仅 thread_id=None 时，多轮不缓存）
  读取  — 单 Agent 问题前 get()；cosine distance ≤ 0.20 → 命中
  清理  — 无自动清理；同 id 覆盖式 upsert
```

代码路径：
- `cache/semantic_cache.py:40-58` — `get()` 查询
- `cache/semantic_cache.py:62-68` — `put()` 写入
- `agents/single_agent.py:22-26,40-42` — 调用时机

#### ⑥ chroma_db/ — RAG 知识库（Chroma）

```
生命周期：
```

### 5.3 持久化架构图

```
请求 -> run_single_agent() ──┬── L2 语义缓存 ⑤ (cache_db/)
                           │     命中 -> 跳过整个图执行 -> 返回
                           │     miss ↓
                           └── 进入 LangGraph 图执行
                                   └─> call_llm() ──┬── L1 精确缓存 ④ (llm_cache.db)
                                                    │     命中 -> _CachedResponse -> 返回
                                                    │     miss ↓
                                                    ├── LLM API 调用
                                                    │     │
                                                    ├──── 成本追踪 -> span attributes (cost/tokens)
                                                    │     │
                                                    └── 写入 L1 缓存 ④

Agent 执行过程中：
  ├── 状态检查点 ① (checkpoints.db) ← LangGraph 自动写
  ├── Token 签发/交换 ② (tokens.db) ← STS.save()
  ├── 审计记录 ③ (audit.jsonl) ← audit._persist() 即时追加
  └── RAG 检索 ⑥ (chroma_db/) ← retriever 查询

每轮 query 结束：
  └── tracer.flush() → exporter.export(trace_id, spans)
       ├─ console → stdout JSON（默认）
       └─ otel → OTel Collector → Jaeger / TimescaleDB / ...
```

### 5.4 能否统一？

> 6 种存储能不能合并成 1 个？逐一分析每种存储的**访问模式**和**唯一性**，结论：可合并 2 项（⑤⑥ Chroma 合并为一个 client），但大多数不能合并，不是设计问题，是访问模式根本不同。

| 存储 | 访问模式 | 写入频率 | 能合并到 SQLite？ | 为什么不能/不必 |
|------|---------|---------|-------------------|----------------|
| ① checkpoints.db | 整块读写（state 序列化/反序列化） | 每图节点 1 次 | ❌ | **LangGraph 框架拥有权**：SqliteSaver 是 LangGraph 内置实现，schema 由框架控制，我们无法改名/移表。强行 fork 框架代码得不偿失 |
| ② tokens.db | 点查 `WHERE token_id=?` | 低频（签发+交换） | ✅ 可以，但不建议 | 可以和 llm_cache.db 共库不同表。但 tokens 生命周期完全不同（Token 吊销=删行，缓存=TTL 过期），分离更安全：清缓存不会误删 Token |
| ③ audit.jsonl | **追加写**，不读不删 | 高频（每操作 1 行） | ❌ | **追加写不该用 SQLite**：JSONL 是 `open + append + close`，零索引开销，O(1) 写入。换成 SQLite 反而要维护索引、处理 WAL 膨胀。审计日志的正确归宿是 **stdout → log collector（ELK/Loki）**，不是数据库 |
| ④ llm_cache.db | 点查 `WHERE cache_key=?` | 每次 LLM 调用 1 次读写 | ✅ 可以，但不建议 | 可以和 tokens.db 共库。但缓存有高频删除（TTL 过期清理），和 Token 的稳定存储混在一起会增加 SQLite 锁竞争 |
| ⑤ cache_db/ (Chroma) | **向量相似度查询** | 低频（首次新问题） | ❌ 根本不可能 | 语义缓存的本质是 `cosine(query_embedding, all_embeddings) < threshold`。SQLite 没有向量索引，只能全表扫。Chroma/Milvus/PGVector 是唯一解 |
| ⑥ chroma_db/ (Chroma) | **向量 + 关键词混合** | 低频（首次 RAG 查询后只读） | ❌ 根本不可能 | 同上。RAG 检索 = `vector_search × 2 + BM25 + RRF + CrossEncoder`，每一步都依赖向量计算。这是向量数据库的领地 |

**真正能做且应该做的合并**：

```
⑤ cache_db/ + ⑥ chroma_db/  →  同一个 Chroma PersistentClient，两个 collection

当前：cache_db/ 和 chroma_db/ 各建一个 Chroma client，各自独立目录
改进：一个 client，collections = ["semantic_cache", "contracts"]
好处：减少一个 Chroma 客户端实例，启动少一次文件扫描
代价：改动 ~10 行，但当前分离也有好处——清缓存不会误删知识库
```

**当前 6 种存储的架构评价**：

| 维度 | 评价 |
|------|------|
| **格式选择** | 全对。SQLite 做点查、JSONL 做追加、Chroma 做向量——每种存储用的都是最适合其访问模式的后端 |
| **数量合理性** | 3 个 SQLite 文件可以争议（tokens + llm_cache 共库），但**每个文件的 schema 完全独立**，分离 = 操作隔离 = 运维安全 |
| **生产演进** | ①→ PostgreSQL（多副本读写）/ ③→ stdout → Loki / ④⑤→ Redis（高 QPS）/ ⑥→ 独立 Milvus 服务 |
| **核心结论** | **不是"能不能统一"，而是"统一会损害什么"**。追加写和大块读写不该共用存储引擎，点查和向量检索不该共用索引结构。当前设计是合理的**多态持久化**（Polyglot Persistence），不是没统一 |

### 5.5 为什么是 PostgreSQL 而不是 MySQL？

> 生产演进选了 PG，不是 MySQL。这不是偏好，是 **4 个硬约束**决定的。

#### 一句话结论

| | MySQL | PostgreSQL | 对本项目的影响 |
|---|-------|-----------|--------------|
| **LangGraph checkpointer** | ❌ 无官方支持 | ✅ `AsyncPostgresSaver` 官方内置 | 如果用 MySQL，checkpoint 要自建表+自写 saver |
| **向量检索** | ❌ 无原生向量索引 | ✅ `pgvector` 扩展（IVFFlat/HNSW） | RAG 向量库可以从 Chroma 迁移到 PG，一次 SQL 查标量+向量 |
| **JSON 处理** | ⚠️ JSON 类型无索引，本质是 TEXT | ✅ `JSONB` + GIN 索引 + 路径查询 `data->>'key'` | Token permissions、audit params 都是 JSON——PG 可以建索引查 |
| **LangChain 生态** | ⚠️ 社区维护，滞后 | ✅ 一线支持，新 feature 先上 PG | `langgraph-checkpoint-postgres` 是官方包 |

#### 逐项展开

**1. LangGraph checkpointer：MySQL 根本没有**

```python
# PostgreSQL — 官方包，一行 import 搞定
from langgraph.checkpoint.postgres import AsyncPostgresSaver

# MySQL — 不存在。需要自己写：
#   - 建表（checkpoints / checkpoint_writes / checkpoint_blobs）
#   - 实现 BaseCheckpointSaver 接口
#   - 处理序列化/反序列化（msgpack）
#   - 处理并发写入的版本冲突
#   工作量：约 300-500 行，且每次 LangGraph 升级都可能 break
```

这是**最硬的约束**。checkpoint 是 Agent 状态持久化的核心，LangGraph 团队只维护了两个官方 saver：`SqliteSaver` 和 `AsyncPostgresSaver`。没有 MySQL 版本。

**2. 向量检索：MySQL 做不了**

demo 的 RAG 用到向量相似度查询（`cosine(embedding, query_embedding)`），语义缓存同理。PostgreSQL 有 `pgvector` 扩展，支持 IVFFlat 和 HNSW 索引，10 万条以内的查询延迟 <5ms。MySQL 至今（2026 年）没有向量索引——可以用 `JSON_ARRAY` 存向量然后全表扫，但那不是"检索"，是自杀。

**3. JSON 处理：MySQL JSON vs PostgreSQL JSONB**

```
Token permissions 在数据库里的存储形式：
  ["query_orders", "get_order_detail", "query_inventory", "query_machine_load"]

# PostgreSQL JSONB — 可以：
SELECT * FROM tokens WHERE permissions @> '["query_orders"]';   -- 包含查询
CREATE INDEX ON tokens USING GIN (permissions);                  -- 建索引

# MySQL JSON — 只能：
SELECT * FROM tokens WHERE JSON_CONTAINS(permissions, '"query_orders"');
-- 走不了索引，全表扫
-- 且 MySQL 的 JSON 函数集是 PG 的子集，复杂路径查询经常写不出来
```

**4. LangChain 生态：PG 是一等公民**

翻 `langgraph` 和 `langchain` 的 requirements：`langgraph-checkpoint-postgres` 是官方维护的，`langgraph-checkpoint-mysql` 不存在。LangChain 的 `SQLChatMessageHistory` 也是 PG 先支持。这是生态惯性——AI 框架的持久化后端默认就是 PG。

#### 什么场景 MySQL 更好？

MySQL 在以下场景比 PG 强——但 demo **不涉及**：

| MySQL 优势 | 本项目是否用到 |
|------------|-------------|
| 主从复制开箱即用（binlog） | ❌ 单机 SQLite，暂时不需要 |
| 读多写少时的简单查询更快 | ❌ 全是点查/点写，差异微乎其微 |
| DBA 和运维工具链更成熟 | ❌ demo 阶段，不是问题 |
| 国内云厂商 MySQL 实例更便宜 | ⚠️ 唯一的真实优势，但 PG 的向量和 JSON 能力值回差价 |

#### 迁移成本评估

| 迁移路径 | 成本 | 说明 |
|---------|------|------|
| SQLite → PostgreSQL | **低**（~100 行改动） | ① `SqliteSaver` → `AsyncPostgresSaver` 换 import；②③④ 用 `psycopg2` 替代 `sqlite3`，SQL 几乎不变（都支持标准 SQL）；⑤⑥ Chroma 不动 |
| SQLite → MySQL | **高**（~500 行改动） | ① 需要自写 `MySQLSaver`；② mysql-connector 替代 sqlite3；③ 所有 JSON 查询改 MySQL 语法；⑤⑥ 向量检索需要额外引入 Milvus/PGVector（如果不想全表扫） |

**所以不是"PG 比 MySQL 好"，而是在 Agent 持久化这个细分领域，MySQL 缺了三块核心积木（checkpointer + 向量 + JSONB）。**

| 制造业业务 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 缺 APS 排产算法、IoT 数据、排产变更闭环 |

### 10.3 差距清单（按优先级）

**P0（制造业主线，必须补）**

| # | 缺失 | 说明 |
|---|------|------|
| M1 | **排产约束求解** | 用 OR-Tools / 启发式做交期-产能-物料约束排产，而非纯 LLM 文本建议 |
| M2 | **实时数据源抽象** | DataSource 接口，CSV→MySQL/MES/IoT 可插拔，支持增量更新 |
| M3 | **human-in-the-loop** | LangGraph `interrupt_before` 关键排产决策人工确认 |
| M4 | **结构化排产结果** | `final_answer` 之外输出 JSON 排产表（订单/优先级/时间/原因），供数值验证 |

**P1（生产化加固）**

| # | 缺失 | 说明 |
|---|------|------|
| M5 | **API 限流** | 网关层 rate limit，防打爆预算 |
| M6 | **Token 签名 + refresh** | JWT 签名防伪造；refresh token 续期 |
| M7 | **评估接 CI** | 每次 commit 自动跑 eval，回归基线门槛 |
| M8 | **自动告警 + 采样** | provider 失败率阈值告警；高 QPS 采样导出 |
| M9 | **排产可视化看板** | Web 界面展示排产表/设备负载/风险标记 |

**P2（纵深完善）**

| # | 缺失 | 说明 |
|---|------|------|
| M10 | **Prompt 版本管理 / A/B** | `prompts/` 版本化 + 分流 |
| M11 | **Langfuse 看板** | 观测 + 评估一体，替代 console 导出 |
| M12 | **评估闭环** | 低分场景自动归档 → 反哺 prompt/参数 |
| M13 | **多环境隔离** | dev/staging/prod 配置分离 |

### 10.4 下一步建议（按性价比）

`M4 结构化排产结果 → M1 约束求解 → M7 CI 持续评估 → M2 数据源抽象 → M3 human-in-the-loop`
