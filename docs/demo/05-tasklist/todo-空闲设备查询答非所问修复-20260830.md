## 事项

问题「帮我查一下空闲的设备」产出答非所问（「需要我帮您查看当前有哪些待排产的订单，或者直接触发一轮排产吗？」），真实 trace `372ae82db7244340`；容器内复现脚本确认可稳定复现。根因链：

1. **evaluate_results 强制 has_order**（`demo/graph/single_agent_graph.py` evaluate_results）：`query_machine_load` 只命中 `has_resource`、未命中 `has_order` → 走 `elif not has_order` → `needs_more=True`，**即使 LLM 已给出正确完整答案**。
2. **正确答案被覆盖**：`needs_more` 把 LLM 拉回继续工具轮（`iteration<4` 时），LLM 在系统 prompt「先查订单再查资源 / 综合给出调度建议」引导下输出反问话术。
3. **generate_answer 复用末条**：第 4 轮后 `generate_answer` 直接取最后一条 assistant 纯文本（反问），丢弃前面正确的设备列表答案。
4. **影响范围**：所有纯资源查询（设备/库存/客户等）同类复现；排产类查询（走 `query_orders` → `has_order=True`）不受影响（冒烟 S10「待排队订单」正常即此因）。

**复现证据**（容器内脚本 dump messages）：

- `[3] tool` 7 台设备空闲表（数据完整）

- `[5]/[6] assistant` ❌ 反问话术（被 generate_answer 复用作 final_answer）

- 放置位置：在 `run_intent`/`app_intent` 写操作强制检查（`single_agent_graph.py:304-321`）**之后**、循环检测之后，避免「跑排产」被提前收尾（写工具未执行）。
- 最小改动（~5 行），不引入意图判断，通用覆盖所有「LLM 已答对」的查询。

**方案 B（已纳入，用户确认根因修复）**：非排产意图 + 已有资源数据 → 提前收尾。复用 `run_intent` 反向判断，**不新增关键词集**（避免 `_STATE_SENSITIVE_KEYWORDS` 大面积误标的历史坑重演）。
