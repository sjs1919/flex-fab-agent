## 3. 头脑风暴素材区（用户输入逐条落盘）

> 用户提供的内容与思路，逐条记录，标注来源。

### 3.1 订单-零件层次（已确认）

- **1 个订单 → 多款零件（part type）**，每款零件有多个件数（quantity，重复件）。
- **排产最小单位 = part 级**（可独立排布的几何单元），订单仅作客户侧聚合/归集容器。
- 合批自由度：同材料零件可跨订单拼舱；跨材料必须拆批。

### 3.2 材料维度（已确认）

- **demo 定 3 种材料**：SLA（光固化树脂）、MJS（聚合物喷射类）、SLM（金属熔化粉末）。
- **材料 = part 身份**：每款零件固定一种材料。
- **跨材料即拆款**：同款零件若用不同材料，拆分成不同零件款（产品 id 不同）。
- 合批第一约束 = 同舱同材料；设备按材料分群（SLA 机 / MJS 机 / SLM 机）。

### 3.3 件数与交付口径（已确认）

- **件数处理：整批优先、可拆兜底**。件数一舱装得下 → 整批不拆；装不满/超舱 → 按数量拆到多舱（60+40），记录拆批来源。
- **交付口径：订单整体看齐**。订单完成时间 = 该订单所有拆分批次中**最后完成（最后到达）的时间** = max(订单各批次完成时间)。
- 拆批管理成本与齐套风险已认知（一部分先到、一部分后到），按订单整体交付口径统一评估。

### 3.4 设备与舱容量（已确认）

- **构建舱 = 正方体**（三维，长宽高均受限），简化：
  - **600 机型** = 舱 600×600×600 mm
  - **450 机型** = 舱 450×450×450 mm
- **零件尺寸**：part 用**长 / 宽 / 高三个独立维度**。
- **允许旋转**：零件可在舱内旋转放置（长不行可能宽可以），判定基于三维而非固定朝向。
- **判定规则**（正方体舱三轴同长，旋转等价于最大维度判定）：
  - `max(长,宽,高) ≤ 450` → 可选 450 或 600 舱
  - `450 < max(长,宽,高) ≤ 600` → 只能选 600 舱
  - `max(长,宽,高) > 600` → 装不下（无法排产，**直接预警**，进入预警清单）
- 先按简单尺寸判定，精细 3D nesting 留阶段 2。
- 备注：与 big-data-obj 600/800 机型有渊源（该处截面积已实测），此处按 demo 需要简化为 600/450 正方体。

### 3.5 时长建模（已确认）

- **单件打印时长由 Z 轴决定**：`单件时长 = Z高 ÷ 工艺速率`。
- **速率默认取最大值**（可配）：
  - SLA = 50 mm/h
  - MJS = 25 mm/h
  - SLM = 15 mm/h
- **打印后延长时间**（静置/后处理默认，`POST_PROCESS_HOURS`）：
  - SLA = 1h（滴干+清洗+UV 固化）
  - MJS = 3h（冷却+去支撑）
  - SLM = 12h（冷却+清粉+去应力热处理+基板切割）
- **静置/后处理时间兼作设备周转占用**（P1-1 定）：机器在静置期间被占，**下一批须等静置完才上机**（SLM 冷却 12h 占用最重）；订单完成（批次完成+延时）与设备可用共用同一延时，不重复计。
- **批次时长 = max(舱内各件单件时长)**（同舱并行、非累加、件数不增加机时；**装料/准备时间忽略**，P0-2 定）。
- MVP 简化：后处理先按"打印后固定延时"计入批次完成时间；后处理独立资源排队留阶段 2。
- 业界要点已认知：后处理是隐藏瓶颈，产能常卡在后处理而非打印。

### 3.6 设备产能（已确认；demo 配置 2026-08-21 减配）

- **demo 配置**：每种工艺 **450 机型 2 台 + 600 机型 1 台**（SLA/MJS 各 3 台；SLM 仅 600 机型 1 台），共 **7 台**。原 40 台（SLA15+MJS15+SLM10）为真实工厂标准配置，降为可配参考。
- **24h 连续生产**（无人值守优势；预留维护余量可后续降为 22h/天）。
- MVP 简化：先按"每台设备每天可用时长=24h"建模，维护日历留后续。

### 3.7 材料-机型对应（已确认；demo 配置 2026-08-21 减配）

**每种工艺的机器配置（demo）**：
- **SLA**：600×1 台 + 450×2 台（共 3 台）
- **MJS**：600×1 台 + 450×2 台（共 3 台）
- **SLM**：仅 600×1 台（金属无 450 小尺寸机型，口径保留）

**合计 7 台**（demo 配置，用户确认 2026-08-21；原 40 台标准工厂配置降为可配参考）。合批时同材料零件可自由选可用机型拼舱（SLM 只能选 600，SLA/MJS 可选 600/450）。

### 3.8 目标函数（已确认）

**优先级排序：交期时间 → 订单优先级 → 舱利用率**
- **交期时间**：交期近的订单优先排（第一排序键）。
- **订单优先级**：**相同交期下，客户优先级/订单权重越大排在越前面**（降序）。
- **订单权重口径（✅ 全部已确认：维度 + 默认值）**：`priority` 字段**直接挂在订单上**，客户等级只是基础分。换算公式（评分制，全部系数可配）：
  ```
  priority = 客户等级基础分 + 加急加分 + 价值加分(金额) + 违约金加分
  ```
  | 维度 | 数据来源 | 默认分（✅ 已确认 2026-08-21） |
  |------|---------|--------|
  | 客户等级基础分 | `orders.客户等级` | S=50 / A=40 / B=25 / C=10 |
  | 加急 | `orders.加急`（新字段） | 是=+30 / 否=0 |
  | 价值加分 | `orders.金额`（新字段） | 金额≥5万→+20 / 否则 0 |
  | 违约金加分 | 客户合同违约金费率（§3.17 实测） | 费率×3000 取整：1%→30 / 0.5%→15 / 0.3%→9 |
  - 排序：交期升序 → priority 降序 → 舱利用（不变）。
  - 交期已作主排序键，权重只在**同交期**时竞争，故不重复放入交期紧迫度。
  - **刻意不纳入** `customers.延期率`（历史延期率）与 `customers.信用分`：
    - **延期率 = 该客户过去订单的历史延期比例**（demo 数据 0.02~0.25：C003 广州航天精工 2%、C001 深圳五金 5%、C004 惠州医疗 25%）。它是**往回看的历史结果**，不是下单时可静态评估的输入。
    - 不纳入原因：① 新老客户**信息不对称**——新客户无历史记录；② 历史表现 ≠ 未来表现，**易放大噪声**；③ 与客户等级（静态分层）**信息重复**。
    - **延期率 ≠ 违约金**：延期率是过去表现（历史），违约金是合同逾期赔付费率（未来成本，§3.17 S1%/A0.5%/B0.3%），后者才是排产代价目标（P0-3）的输入。
  - **注意**：demo 合同中违约金费率恰好由客户等级决定（S1/A0.5/B0.3），两者相关——但违约金作为独立维度保留（真实世界逐合同谈，权重可独立调）。
- **延期代价（P0-3 已确认）**：主目标 = 最小化**加权迟到**：`min Σ(订单金额 × 违约金日费率 × 延期天数)`。违约金日费率按客户等级（合同实测 §3.17：S=1% / A=0.5% / B=0.3% / C=0.3%）→ 客户等级高、金额大 → 延期代价重，优先保其交期。需新增订单字段：**金额**。
- **舱利用率**：仅当**设备排满 / 后面没有排队订单**（产能宽松）时追求填满舱——产能紧张时优先保交期，不为装舱牺牲排程。
- **同订单尽量同舱**：同一订单的多款零件尽量合并进同一构建舱（减少齐套等待，与"交付按最后到达"口径一致）。
- **换料与负载均衡**：换料目标**删除**（P0-4 已确认：设备按工艺分群 §3.7，永不换料）；负载均衡保留为低优先级考虑点，不作为主要优化目标。

### 3.9 交期来源（已确认）

- **交期 = 客户下单时确定的交期**（承诺交期作为输入），排产目标为尽量满足它。
- **交期粒度（P1-3 定）**：按天，交期=截止日 23:59 前完成；24h 窗口内部按小时。
- 系统推导承诺交期（CTP/可承诺量）→ **升级为 v1 功能**（§3.12）。

### 3.10 排版人审批环节（已确认）

- **排产方案生成后，必须经排版人查看并点击"通过"后才上机**（human-in-the-loop，对应行业 M3 缺口）。
- 状态流转：`待审核 → 通过（下达上机）` 或 `驳回（重新排产）`。
- **订单状态模型（P1-4 定）**：`待排队（含未审核）→ 已审核（审批通过）→ 打印中 → 完成`；"未审核"不是独立状态，属待排队；审批通过即进入"已审核"。
- 通过前为待审核态，**不进入生产**。
- 新增角色：**排版人**；审批动作（谁/何时/通过或驳回）记入审计。
- v1 支持"通过/驳回"两态；排版人手动调整排产方案留后续。
- **归属**：排版审核归入**前道人工环节**（§3.15），与切片/装料共用 6 人池。

### 3.11 应急产能预留（已确认）

- **预留 10% 产能**作为应急缓冲，不参与常规排产。
- 用途：**后处理坏件重打**、**坏件修复**、**应急插单**。
- 实现口径：设备日可用产能 = `24h × 90% = 21.6h/天`（求解器只排到 90%）。
- 应急订单走预留产能池；预留用满后按优先级再评估。

### 3.12 新单交期承诺 CTP（已确认）

- **触发**：新批量订单进来时。
- **输入**：排队订单（按交期后延分布）、进行中/在途订单、设备可用产能。
- **输出**：该新单**最短可交付时间**，作为承诺交期报给客户。
- **硬约束：不影响排队订单和在途订单**（现有承诺优先，新单插空，不挤占已有交期）。
- **实现**：新单仅用**空闲产能/时段**插入（现有排产不动），计算最早可交付时间。
- **口径**：承诺交期按**常规可用产能（24h×90%，不含 10% 应急池）**计算——应急池是保命池，不承诺给常规新单。
- **产能基准（P1-4 定）**：现有占用 = **打印中 + 已审核 + 待排队（含未审核）**；可用 = 总产能 − 现有占用。
- 升级说明：原 §3.9"CTP 留后续"升级为 v1 功能。

### 3.13 产能负载评估（已确认）

- **定位**：全局产能核算 / 负载看板。CTP（§3.12）看**单张新单**能否承诺，本评估看**整体负载**：现有订单能不能按期打完、产能够不够。
- **触发**：随时可查（生产管理看板），非仅接单时。
- **输入**：
  - 在途订单（打印中）+ 排产表上的预计完成时间
  - 排队订单（未开始）+ 交期
  - 设备状态：**正在打印**（在途占用）/ **已腾出**（空闲）/ **当天能腾出**（预计空闲时间）
  - 评估时间窗 T（用户示例 24h，**可配**，默认 24h）
- **输出（四段报告）**：
  1. **在途/排队分布**：按交期统计多少在途、多少排队，每个订单预计何时打完
  2. **超期预警**：满负荷运转下各订单预计完成 vs 交期 → 超期订单清单（含在途与排队）
  3. **24h 消化能力**：排除正在打印的机器后，可用产能（已腾出 + 当天腾出 + 剩余时间）vs 排队订单需求 → 能否在 T 内消化完
  4. **产能余缺**：能消化 → 剩余产能多少；不能 → 需要增加多少台机器
- **口径**：
  - 在途订单预计完成 = 当前排产表上的完成时间（读取现成结果，不重排）
  - 排队订单预计完成 = 满负荷 + 按目标函数顺序（交期升序 → priority 降序）推算的累计完成
  - 可用产能 = Σ(已腾出机器 × T) + Σ(当天腾出机器 × (T − 预计腾出时间))，仅统计预计在 T 内腾出的机器
  - 需求产能 = Σ 排队订单所需机时（按材料/机型分群，批次模型粗算，与求解口径一致）
  - 缺机器数 = ⌈缺口产能 ÷ 单台机器 T 窗口产能⌉（按机型分别核算）
- **超期/消化判定 + 应急池关系（三区制，已确认）**：
  - 判定基于**满负荷 100%**（最坏情况：满负荷仍超期/消化不完 = 真产能缺口）
  - **绿**：需求 ≤ 90% 可用 → 常规产能够，不碰应急池
  - **黄**：90% < 需求 ≤ 100% 可用 → 常规紧张，需动用应急池 / 加班才能按期
  - **红**：需求 > 100% 可用 → 产能不足，需加 X 台机器
  - 10% 应急池作缓冲带单独展示，不承诺给常规订单（CTP 同口径）

### 3.14 订单状态跟踪（已确认）

- **触发**：按**订单号**查询单个订单的情况。
- **查询内容**：
  - **在途订单**：预计什么时候完成（来自当前排产表 / 打印进度）
  - **排队订单**：预计什么时候**打上**（开始打印）、什么时候**完成**、**前面还有什么单据**（排队队列中排在该单前面的单）
- **排队顺序口径**：与目标函数一致——**交期升序 → priority 降序**（§3.8），"前面还有什么单据"= 按此顺序排在该订单前面的未开始单据清单。
- **预计时间推算**：满负荷 + 按队列顺序累计产能消耗（同 §3.13 口径），得出该单预计开打 / 完成时间。
- **定位**：产能负载评估（§3.13 看全局）的**单订单下钻视图**；同一次推算、两个视图。

### 3.15 前道·打印前人工环节（已确认资源模型）

- **定义**：打印前的人工环节（与后处理对称）。后处理推迟阶段 2。
- **范围（含排版审核）**：**排版审核**（排版人过排产表、点击通过）+ 切片 / 排版程序 / 文件下发 + 装料 / 上机。= 排产方案通过后、机器开打前的一切人工工作；排版审核（§3.10 审批环节）**归入前道人工环节**。
- **资源**：**6 名人工**（排版员/准备员，数量可配）。
- **人效（拆为三类，计费单位不同；✅ 已确认）**：
  - **① 按"件"计**（随件数线性增长，人效的分子；软件批量生成、人工复核为主）：
    | 活动 | SLA/MJS | SLM |
    |------|---------|-----|
    | 数据核对/模型修复 | 1-2 min | 2-3 min |
    | 加支撑/排版程序 | 2-3 min | 3-5 min |
    | 切片/打印参数 | 1-2 min | 2-4 min |
    | 小计 → **件人效** | ~4-5min/件 → **15 件/人·h** | ~8-10min/件 → **6 件/人·h** |
  - **② 下机+上机准备**（按舱，固定成本）：下机（取件）+ 上机准备（装料/校验）**在静置/周转窗口内一起做**——已涵盖在 P1-1 静置时间（SLM 12h 冷却=整机周转期），**不单列进前道人工池，归设备周转**。
  - **③ 按"方案"计**（每排产一次）：排版审核 0.5h/方案（排版人过审点通过）
  - **完善口径（前道人工池 = ① + ③）**：
    ```
    前道任务时长 = 件数 ÷ (分配人数 × 件人效)     # ① 按件（切片/排版复核）
                + 方案审核时长 ÷ 方案内批次分摊   # ③ 按方案（排版审核）
    # ② 下机+上机准备：静置/周转窗口内一起做（P1-1），归设备周转，不进前道池
    ```
  - 混合综合默认 12 件/人·h（兜底）。**件人效 15/6/12、方案审核 0.5h 已确认（2026-08-21）**。
- **班制**：**3 班倒 × 8h = 24h 覆盖**（6 人 = 每班 2 人）。
- **换班**：每次 **30 分钟无产出** → 3 次/天 → 人工净产能 = `24h − 3×0.5h = 22.5h/天`（每班净 7.5h）。
- **建模**：每个批次打印前有一道**前道任务**，占用人工资源（**非打印设备**）：
  - 前道时长 = `件数 ÷ (分配人数 × 件人效) + 方案审核分摊`（①+③；② 下机+上机归设备周转）
  - **前道完成 → 打印开始**（硬约束）
  - 排版审核（方案审核）= 每排产方案一次，计入 6 人池
- **前道失败无耗材无坏件、可重来**（呼应 big-data-obj 链路任务=打印前准备阶段）。
- **瓶颈判断**：6 人准备 vs 7 台打印设备（demo 配置）——人效低时**前道成为瓶颈**（人工准备堵住机器），**v1 负载评估/CTP 产能核算需同时含前道人工池**（双瓶颈，不能只算设备产能）。
- **与现有模型的关系**：批次时长原含"准备时间"，现**拆出**为前道任务（人工）+ 打印任务（设备）两段，排产表含前道起止时间。

**3) 生产环境模拟器（1min 定时 · A+B 双机制，✅ 已确认 2026-08-21）**
- 定位：独立于智能体的"**世界推进器**"，把静态数据变成动态生产现场，模拟真实生产环境。
- **双机制**：
  - **A 时钟层（固定事件按加速走）**：**1 现实分钟 = 1 模拟小时**（加速比可配）。驱动**确定性的生产推进**：批次执行进度、设备产能消耗/释放、前道人工产能（含班次/换班）、后处理延时、订单随批次完成的流转。
  - **B 事件层（意外事件按分布预排）**：意外事件**按统计分布预排到 sim 时间轴**，到点触发、状态跳变。事件源：
    | 类型 | 事件示例 | 分布/参数 |
    |------|---------|---------|
    | 机器 | 故障 → 维修中 → 恢复；维护停机 | MTBF / MTTR（指数分布） |
    | 人员 | 请假/缺勤（前道人效下降） | 到达率 |
    | 订单 | 新单插单、改交期、撤单、数量/款式变更 | 到达率 |
    | 材料 | 到货、库存不足预警 | 到达率 |
    | 质量 | 批次完成后抽检坏件 → 重打（消耗应急池 §3.11） | 坏件率（由 A 完成时触发） |
- 每 **1min tick**（现实心跳）：① A 层推进 sim 时钟 +1h → 推进批次/产能/人效进度 → 处理到期固定事件；② 检查 B 层事件队列，到点事件触发并落库。
- **所有变更落库 + 写审计**（谁/何时/什么变更）；智能体**只能读到 DB 当前状态、看不到未来**（关键训练性质：agent 通过工具感知世界，不直接操作模拟器）。
- **扰动后重排（✅ C 已确认 2026-08-21）**：重排由**智能体决策**（监控 → 分析 → 调用求解器 → 新方案送审）；**硬性不可行扰动**（故障废掉在跑批次所在设备，排产表物理不可行）由系统给**强"需重排"告警**兜底，agent 须响应；**软性扰动**（插单/请假，排产表仍可行）是否重排完全交给 agent 判断。

**待确认清单**：① 时间口径 ✅（A+B，1min=1simh）；② 重排触发 ✅（C：agent 决策 + 硬性告警兜底）；③ 选型 ✅ MySQL —— **§3.18 全部闭环**

### 3.19 订单预测与大单承诺期（2026-08-21 追加 · 推荐待确认）

- **场景（用户提出）**：客户下**大单**时，需要根据大单给出**承诺期**（何时可交付）。现有 CTP（§3.12）只按"已下单订单"负载计算，**缺订单预测**——未考虑未来订单会抢占产能，承诺期偏乐观。
- **需求 1：订单预测**——基于历史订单，轻量时序预测未来订单量/负载。
  - 方法：统计方法（移动平均 / 指数平滑 / 线性趋势），**不做模型训练**（demo 定位，避开"微调/训练"算法门槛）
  - 粒度：按天；**分材料**（SLA / MJS / SLM）
  - 窗口：默认 7 天（可配）
  - 输出：预测订单量（件数）+ 预测产能占用（机时）
- **需求 2：大单承诺期（预测校准 CTP）**——新大单进来时：
  - 输入：现有占用（打印中 + 已审核 + 待排队）+ **预测未来占用**（预测窗口内预测订单的机时）+ 设备可用产能
  - 硬约束：**不影响已下单订单**（现有承诺优先；预测只作"未来占用"预留）
  - 与现有 CTP（§3.12）关系：现有 CTP = 插空（只看已下单队列）；**预测校准 CTP = 为未来订单预留产能后的承诺**——更保守、更真实
  - 输出：承诺交付日期 + 依据（现有负载 + 预测负载 + 可用产能）
- **触发**：接大单时（预测工具 + CTP 工具联合）
- **待确认项**：① 预测方法（推荐指数平滑）；② 预测窗口（推荐 7 天）；③ 是否分材料（推荐分）；④ 预测占用计入 CTP 的方式（推荐"预留"，即承诺时扣除预测订单机时）；⑤ 大单判定阈值（金额 / 件数，推荐金额≥5万）

### 3.25 Agent 调试台界面（2026-08-21 追加 · 形态 A 已确认）

- **目标**：交互界面收集 **good/bad case** + 可视化执行链路 + 质量打分——既是评测数据沉淀，又是面试演示力（"每次交互留痕、可复现、可回归"）。
- **形态（用户确认）**：静态 HTML 单页，FastAPI 托管。**调试台 = 主页 `GET /`**；主页顶部含**数据看板入口**，点击打开 B8 Dashboard（`GET /dashboard`）。两页面独立、不合并，共享 tracer/cost 数据底座。
- **功能**：
  1. **文本输入交互**：输入框 → 调 `POST /ask`。
  2. **执行流程可视化**：图节点（analyze_intent → select_and_execute → evaluate_results → generate_answer）+ 节点内工具调用；每节点展示**操作 / 入参 / 出参 / 耗时 / 成功·重试**（数据来自 tracer + trajectory_capture）。
  3. **执行后质量打分**：judge（faithfulness + answer_relevancy 0-1）展示；judge 失败降级不计权（已有机制）。
  4. **good/bad case 收集**：
     - **case 类型标注（2026-08-21 用户补充）**：`normal`（真实任务）/ `chitchat`（闲聊，无工具调用且无排产意图）/ `empty`（空跑，工具调用无实质产出）；**good/bad 仅对 normal 判定**；chitchat/empty **专门标注**、默认不参与回测池（可过滤查看）；
     - **自动判定**（阈值默认：answer_relevancy<0.5 或 faithfulness<0.6 或 errors>0 / loop_detected → bad；其余 good）→ 界面自动归类；
     - **人工标注**：界面按钮修正（good↔bad），覆盖自动判定；
     - **落盘沉淀 + 可导出**（重跑评测的 case 池）。
  5. **按 trace_id 回测**（2026-08-21 追加）：
     - case 以 **trace_id 为主键**落盘（每次执行唯一索引，tracer 每次 reset 生成）；
     - **回放**：按 trace_id 查当时完整链路（历史复现，只读）；
     - **重跑回归**：按 trace_id 取 question 在当前 agent 重跑 → 新旧 trajectory + 新旧 judge 分数并排对比（bad case 修复后是否转 good）；
     - **批量回测**：选一批（默认全部 bad case）重跑 → bad→good 转化率 + 平均分对比，**复用 `backtest/runner.py` 回归基线框架**（评分双口径：judge 分数 + 覆盖度）；
     - API：`GET /cases/{trace_id}`（回放）、`POST /cases/{trace_id}/replay`（重跑）。
- **数据底座**：tracer `tool:` span（已有）→ **single_agent_graph 各节点补 `node:` span（手动埋点）** → trajectory_capture 增强（图节点 + 工具调用两级）→ judge（已有）→ 新增 case_collector 模块 → **复用 backtest/runner.py 回归框架**（场景源扩展为 cases.jsonl 按 trace_id 筛选）。
- **API 增量**：`GET /`（主页·调试台）；`GET /dashboard`（数据看板二级页，B8）；`POST /ask` 增强或 `POST /ask/debug`（返回 trajectory + judge + case 判定）；`GET /cases`（列表/筛选 good/bad）；`POST /cases/{id}/label`（人工标注）；`GET /cases/{trace_id}`（回放）；`POST /cases/{trace_id}/replay`（按 trace_id 重跑回测）。
- **待确认（推荐默认）**：① case 存储用 **cases.jsonl**（与 audit.jsonl 同级基础设施存储，不动 MySQL 表结构）；② 打分每次 /ask 后跑 judge（demo 规模成本可接受，且 case 判定需要）。
- **已确认（2026-08-21 澄清）**：① case 存储 = **cases.jsonl**（audit.jsonl 同级，trace_id 主键，**每次 /ask 自动落盘**）；② 打分 = **每次 /ask 自动 judge**（`system_config.case_judge_enabled` 可关）；③ **生产环境开关（要求写入 case_collector.py docstring）**——demo 默认全开；**生产默认关**，开启方式：`case_collection_enabled`/`case_judge_enabled`=true + 采样率 `case_sample_rate`（如 0.1，不全量打分）+ 合规（仅授权租户、question 脱敏）；④ **bad 判定阈值进 system_config 配置化**（`case_bad_relevancy=0.5` / `case_bad_faithfulness=0.6`；errors>0 或 loop_detected 直接 bad；阈值可调）；⑤ **case 去重 = 全保留 + 按 question 分组展示**（组内按时间排列、可回放任意一次），**回测默认取组内最新**（2026-08-21 确认）；⑥ **人工标注优先**：case 存 `auto_label`（自动判定，重跑后更新）+ `label`（人工可覆盖，重跑**不**覆盖），二者不一致界面提示"⚠️ 自动判定已变化"复核（2026-08-21 确认）；⑦ **重跑关联**：新 case 带 `replay_of=<旧trace_id>`，旧 case 带 `replayed_by=[新trace_id...]`（数组，可多次重跑），新旧并排对比，batch 转化率取 `replay_of` 指向的最新一条（2026-08-21 确认）；⑧ **节点父子**：tracer Span 加 `parent_id`，`single_agent_graph` 各节点 `node:` span **包住**内嵌 `tool:` span，`trajectory_capture` 重建"图节点→工具调用"两级树（2026-08-21 确认）；⑨ **方案归属 = 新增 G 组**（§7.7：G1 case_collector / G2 tracer 父子 / G3 节点埋点+两级轨迹 / G4 api 端点 / G5 页面 HTML；**里程碑 = 独立 M6**，依赖 M4/M5，2026-08-21 确认）；⑩ **导出互通**：case_collector 提供 `export_ground_truth()`（cases→eval 格式）/ `export_backtest_scenarios()`（cases→backtest 格式）；backtest 场景源二选一（预设 scenarios.py 或 cases.jsonl），格式由 case schema 派生（2026-08-21 确认）。

## 4. 待整理：排产问题建模（随素材沉淀）

### 决策变量
- 合批：哪些 part 合并进同一构建舱（batch/build）
- 装舱：舱内 part 的排布
- 时间排程：批次 → 设备 + 开工时间

- 材料：同舱必须同材料；一台设备一个批次一种材料（换料成本高）

### 目标函数（分层，已确认 §3.8）
1. **主目标**：按期交付——最小化延期，权重 = 交期紧迫度 × 订单优先级（交期近、优先级高者优先）

3. **次目标**：最大化构建舱利用率（仅产能宽松/无排队时追求填满）
4. **低优先**：换料次数最少、设备负载均衡
