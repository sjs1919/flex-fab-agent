## 第一部分：验证（先跑起来）

### 方式一：Docker 容器（推荐，环境隔离）

```bash
# 1. 构建镜像 + 启动（自动排产调度随 API 启动，前端同源托管）
cd projects/agent-training
docker compose up -d --build

# 2. 验证服务是否正常
curl http://localhost:8000/health

# 3. 发送问题测试
curl -X POST http://localhost:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"query": "查询紧急订单"}'

# 4. 看自动排产调度器状态
curl http://localhost:8000/scheduler/status

# 5. 浏览器打开 Web 控制台
open http://localhost:8000/            # 排产看板
open http://localhost:8000/portal/debug  # 排产调试台

# 6. 查看容器日志
docker logs demo-api

# 7. 停止容器
docker compose down
```

### 方式二：本地 Python 运行

```bash
cd projects/agent-training

# 0. 建表（v2 MySQL 模式，首次需要）
python -m demo.schema.migrate --up

# 1. 地基自检（config/LLM/工具 三层连通，不调 LLM 也能确认数据层 OK）
python -m demo.main --check

# 2. 单次提问（单 Agent 模式）
python -m demo.main "今天先做哪些订单？"

# 3. 多轮对话（同一会话跨轮共享上下文，sqlite 持久化）
python -m demo.main --chat

# 4. 多 Agent 模式（带鉴权 + 审计报告）
python -m demo.main --mode multi "帮我综合评估 ORD001、ORD003、ORD005"

# 5. 预设场景演示（交互式选编号）
python -m demo.main --demo

# ── v2 制造业主线命令 ──

# 6. 求解一轮排产并落库（M2 求解器）
python -m demo.main --init-schedule

# 7. 启动生产模拟器心跳（M3，Ctrl+C 停止）
python -m demo.main --sim

# 8. Prompt 版本回滚
python -m demo.main --rollback v1

# ── v3 新增命令 ──

# 9. 签发 admin token（调试台/写端点鉴权，1h 有效）
python -m demo.auth.mint admin

# 10. 环境变量控制
DEMO_DATA_SOURCE=mysql python -m demo.main --check      # MySQL 模式
AUTO_SCHEDULE_ENABLED=off uvicorn demo.api:app --port 8000  # 关闭自动排产
```

**读什么：** `schema/schema.sql` 全文 → `schema/migrate.py`

**19 张表按所有权分组（写方唯一原则）：**

| 写方 | 表 | 说明 |
|------|-----|------|
| seed + B 层 | customer | 客户（S/A/B/C 等级 + 违约金率） |
| seed + B 层 | orders | 订单（状态/交期/优先级/金额） |
| seed + B 层 | parts | 零件（尺寸/材料/数量/高度） |
| seed + B 层 | machines | 设备（型号/材料/舱尺寸/承重） |
| seed + B 层 | material / inventory | 材料字典 + 材料库存 |
| seed + B 层 | personnel 🆕 | 前道人员（id/姓名/角色/状态 上班|请假） |
| solver | schedule_versions | 排产版本（待审核→已审核/已驳回） |
| solver | batches | 批次表（设备/开始/结束/状态） |
| solver | preprocess_tasks | 前道任务（v3：solver 同事务生成） |
| solver | approvals | 审批记录 |
| simulator | sim_clock / sim_events / state_change_log / bad_parts | 模拟时钟/事件/状态日志/坏件 |
| 运维 | system_config | 系统配置键值对 |

**迁移工具（migrate.py）：**

### 第 9 层 · 排产求解器（`scheduler/`）★ 重点

**读什么：** 按顺序 `snapshot.py` → `verify.py` → `model.py` → `solver.py`

**这是系统的"心脏"——把"LLM 文本建议排产"升级为"数学规划精确求解"。**

#### 9.1 快照（`snapshot.py`）
读一致性快照：从 MySQL 一次性读取订单/零件/设备/库存 → 组装成内存字典 → 传给求解器。**v3 选单口径改为 `status='待排队'` + parts 按待排队订单过滤**——已锁定的订单不再进快照，防重复打包进后续版本。

#### 9.2 约束校验（`verify.py`）
C1-C9 九条硬约束的程序化校验器，纯函数。求解前后都可以调。

```
C1 同舱同材料      C2 容量约束（尺寸/件数/承重）  C3 机型匹配
C4 批次时长=max    C5 整批优先可拆              C6 设备互斥+静置占用
C7 交期 23:59      C8 日可用 21.6h（90%）       C9 前道完成 ≤ 打印开始
```

#### 9.3 模型（`model.py`）★ 核心
两步建模：
1. **装箱**：先把零件按设备 + 材料分组，在版子里装箱（同一版子单材料约束）
2. **CP-SAT**：OR-Tools 约束规划，决策变量 = 每批次的开始/结束时间，目标 = 最小化总延期加权和

**v3 工艺组级部分成功**：某工艺组不可行仅剔除该组批次，其他组照常；meta 记录 `infeasible_groups/infeasible_order_ids`；整版全不可行 → 返回空 batches（不建版本）。

#### 9.4 求解器入口（`solver.py`）
```
snapshot（待排队订单 + 空闲设备）
  → verify（C1-C9 前置校验）
  → 装箱 → CP-SAT 建模 → 求解（solver_max_time_seconds 预算，默认 20s，model 层回落 60s）
  → compute_metrics（准交率/延期数/目标值/批次统计）
  → persist 落库（★ v3 重大改造）：
      ├ 事务开头条件 UPDATE 原子锁定：orders 待排队→已审核（受影响行数不足 → 整体 ROLLBACK）
      ├ INSERT schedule_versions + batches + preprocess_tasks（同事务，前道任务随批次生成）
      ├ 工艺组级部分成功（不可行组订单保持待排队，下轮重排）
      ├ 全不可行 → 不建版本（返回 None，不污染 auto_scheduler._last_version）
      └ 写建版 sim 时刻快照（state_change_log，供 FIFO 超龄计龄）
```

**求解预算三件套**（R-D1）：
1. CP-SAT 预算：`solver_max_time_seconds`（snapshot 参数默认 20s，2026-08-27 性能优化 60→20；model 层未配置时回落 60s）
2. 预算耗尽：返回当前最优可行解 + `timed_out=true`，不抛错
3. 无可行解：输出冲突订单清单，不静默空结果

**关注点：**
- v3 幂等是核心：**订单锁定与批次落库同事务**，从源头防重复排
- 前道任务生成是「缺口 A」：`man_hours = round(件数/(assigned_workers × 件人效) + 方案审核分摊, 2)`，`end_time = 批次 start_time`（C9）

### 第 12 层 · 自动排产调度器（`scheduler/auto_scheduler.py`）🆕 ★ 重点

**读什么：** `auto_scheduler.py` 全部（约 130 行）

**v3 最核心的新增——实现「自动排版 → 自动审批 → 模拟器推进」全链路无人值守。**

```python
class AutoScheduler:
    def __init__(self, interval_ticks=None, approve_top_n=None, enabled=None, reserve_top_n=None):
        self._lock = threading.Lock()    # 排产互斥（CP-SAT 不可并发）
        self._signal = threading.Event() # 事件即时重排信号
        self._thread = threading.Thread(target=self._loop, name="auto-scheduler", daemon=True)

    def start(self):   # enabled=off 时不启动
    def stop(self):    # 设置 stop + signal，join 5s

    def _loop(self):   # 主循环
        while not self._stop.is_set():
            # 事件即时重排优先；否则按 tick 节流（sim_clock.current_sim_time 变化计 tick）
            if self._signal.is_set():
                self._signal.clear(); self._run_locked("event")
            else:
                if sim_time 变化且累计 ≥ interval_ticks:
                    self._run_locked("tick")
            self._stop.wait(SIM_TICK_SECONDS / 4)

    def _run_locked(self, trigger):
        # ① _auto_schedule：run_scheduling + 订单留底守卫
        #   待排队 ≤ top_n → 跳过本轮排产（保留演示样本）
        #   > top_n → 排除最新 N 单（id 降序）不锁定
        # ② _fifo_approve：版本级 FIFO 审批
        #   待审数 > approve_top_n → 更早的自动通过（approver=system）
        #   最早待审版本龄期 ≥ FIFO_AGE_TIMEOUT → 超龄兜底通过
```

**三层触发**：
1. **cron 周期**（主循环）：每 `AUTO_SCHEDULE_TICK_INTERVAL`（默认 3）tick 排一轮
2. **模拟器事件**：`runner` 调 `request_rerun()`（设备故障/插单/延期告警 → 即时重排兜底）
3. **Agent 语义**：`run_scheduling` 工具（已有，保持不动）

**状态留底守卫**（`STATUS_RESERVE_TOP_N=5`）：待排队/已审核每状态保留最新 5 单不被推进，保证演示任意时刻查任意状态都有样本（修复「查所有还在排队的订单」返回空）。

**FIFO 审批修正**（定稿 v1）：persist 锁定后每轮只排新增订单，版本间互不重叠；双机制——常规保留最近 topN 版 + 超龄兜底（最早待审版本龄期 ≥ 24 模拟小时自动通过）。

**关注点：**
- `get_scheduler()` 进程级单例，`api.py` startup 时 `start()`
- 龄期 sim 锚点：persist 事务内读 `sim_clock.current_sim_time` 写 `state_change_log`（唯一通道，不用 wall-clock）

### 第 13 层 · 订单状态机与幂等（v3 全链路自动化核心）

**读什么：** `scheduler/solver.py` 的 `persist()` + `simulator/states.py` + `engine.py` 的订单流转

**为什么单独一层：** v3 的「排程排产全链路自动化」把五个互相引爆的缺口（A 前道生成 / B 人员锁定释放 / C 订单状态 / D 排产幂等 / E 审批门禁）合并解决。这是整个系统正确性的基石。

**五大缺口闭环：**
- **A 前道任务生成**：`solver.persist` 同事务为每批次 INSERT 前道任务 → 状态机从「前道」推进到「待上机」占用机器
- **B 人员锁定释放**：前道任务落库防重复排；批次 前道→待上机 = 释放占用
- **C 订单状态贯穿**：persist 原子锁定 待排队→已审核；驳回回退（带守卫）；拆批完成判定（最新版本已通过批次全完成）
- **D 排产幂等**：事务开头条件 UPDATE + 受影响行数不足 ROLLBACK；同一订单只被打印一次
- **E 审批门禁**：模拟器只推进 `approval_status='通过'` 的批次

**完整闭环时序（无人值守）**：
```
tick0  seed 20 订单→待排队；7 设备空闲
tickN  AutoScheduler 累计 interval_ticks → run_scheduling
   ├ load_snapshot 只取待排队 + parts 按待排队过滤
   ├ solve 贪心装箱 + CP-SAT
   └ persist 写 versions+batches+preprocess_tasks + 原子锁定 待排队→已审核 + 建版 sim 锚点
   → _fifo_approve：早于 topN 自动通过 + 超龄兜底
tick+1 engine.advance_tick：前道→待上机（释放人时）→ 待上机→打印中（锁设备）→ 打印→完成（释放设备）
   └ fire_events：插单/故障 → request_rerun 即时重排
订单完成 → KPI 准交率正确统计
```

### 第 14 层 · 单 Agent 编排（`graph/`）★ 重点

#### 14.1 状态定义（`state.py`）
```python
class AgentState(TypedDict):
    messages: list[dict]       # 对话历史
    tool_results: list[dict]   # 工具调用结果汇总
    iteration: int             # 当前迭代次数（5 轮安全阀）
    final_answer: str          # 最终输出
    evaluation_notes: str      # R3 步骤校验记录
    needs_retry: bool          # R3 是否需要重试
    needs_more: bool           # R3 是否还需要更多数据（v3 写操作意图守卫）
    ready_for_answer: bool     # R3 是否已可汇总（v3 循环守卫）
    compression_count: int     # R4 压缩次数
```

#### 14.2 状态图（`single_agent_graph.py`）★ 重点
**4 个节点 + 1 条条件边组成循环：**
```
analyze_intent → select_and_execute → evaluate_results → generate_answer
       ↑                    ↑                    │
       │                    └──────────┬─────────┘
       │                needs more data?
       │                               │
       │                    data enough │
       │                               ▼
       │                        generate_answer → END
```

**v3 关键机制（这层是 v3 修复最密集的地方）：**

| 机制 | 作用 |
|------|------|
| **写操作意图守卫** | 用户文本含跑排产/审批意图但对应写工具未执行 → `needs_more=True` 强制继续工具轮（修复「先查再审批两步式被截断」） |
| **循环守卫** | 同工具 + 同参数**连续** ≥3 次判定循环（`itertools.groupby`），触发产出 `LOOP_GUARD_FALLBACK_PREFIX` 用户友好兜底（去内部诊断泄漏） |
| **筛选空结果即终态** | `query_orders` 带筛选条件且干净返回「未找到匹配」→ 直接进 `generate_answer`，不再怂恿 LLM 补数据 |
| **审核意图识别** | `_QUERY_VERBS`（查/查询/查看/有哪些…）优先——含查询动词时「审核」为定语非审批谓语，不判写操作（修复「查询已审核批次」答非所问） |
| **延期清单注入** | `_DELAY_TOOLS` 工具结果抽取延期清单注入综合指令（T5a.11） |
| **DSML 标记重试** | 检测 LLM 输出的 `[TOOL:xxx]` 标记 → 清洗后重试，防缓存投毒 |
| **汇总兜底** | 重试耗尽用 `_SUMMARY_FALLBACK_PREFIX` 拼接工具结果，不降级道歉 |

#### 14.3 上下文压缩（`context_compressor.py`）R4
`summarization buffer` 模式：保留 system + 最近 6 条原文，早期消息调 LLM 生成摘要；防孤儿 tool 消息、防摘要叠加膨胀。

#### 14.4 状态持久化（`checkpointer.py`）
sqlite / memory / none 三种模式，由 `CHECKPOINTER` 环境变量选择。

### 第 15 层 · 单 Agent 调用（`agents/single_agent.py`）

**这是单 Agent 的对外入口，连接缓存层 + 图编排 + 观测层。**

```python
def run_single_agent(query, registry=None, thread_id=None):
    # 1. 语义缓存（仅无多轮上下文时启用）
    if thread_id is None:
        hit = semantic_cache.get(query)
        if hit: return {"final_answer": answer, "tool_results": []}

    # 2. 构建图（模块级缓存）
    app = _get_app(registry)

    # 3. 多轮：从 checkpoint 取历史追加；单次：新起 system + user
    # 4. 执行图
    result = app.invoke(initial_state, config)

    # 5. 缓存写入（仅无多轮上下文；v3 缓存门禁）
    if thread_id is None and not _is_cache_poison(final_answer):
        semantic_cache.put(query, result["final_answer"])
    return result
```

**v3 缓存门禁（防止垃圾答案固化）：**
- `_is_state_sensitive(query)`：状态类查询（状态/进度/排队/当前/还剩）→ 走 60s 短缓存（`SEMANTIC_CACHE_STATE_TTL`）
- 缓存写入门禁拦截三类垃圾：DSML 标记文本、`_GRACEFUL_FALLBACK` 道歉、`LOOP_GUARD_FALLBACK_PREFIX` 循环守卫兜底

**关注点：**
- 语义缓存只对 `thread_id=None` 的独立问题生效
- 状态类查询短缓存是 v3 实测教训：口语化「查一下目前待排产的订单」不含强状态词会被当知识类固化 24h

### 第 16 层 · 鉴权（`auth/`）

**四件套：token_exchange.py（STS）→ guard.py（RBAC）→ quota.py（写配额）→ audit_logger.py（审计）**

#### 16.1 Token 交换（`token_exchange.py`）
受 RFC 8693 启发的 STS：签发用户 Token（1h）→ 交换受限子 Token（5min）。子 Token 权限 ≤ 父 Token（防权限升级）。SqliteTokenStore 持久化，重启不丢。

5 角色权限：admin（通配）/ scheduler（全工具）/ reviewer（只读）/ operator（操作级）/ viewer（最小权限）

#### 16.2 RBAC 守卫（`guard.py`）
洋葱型防御第 3 层——工具执行入口的二次验证。三道防线：网关层（JWT）→ 运行时层（RBAC + 配额）→ 工具层（本模块）。

#### 16.3 写配额（`quota.py`）
同 subject 对同一写工具 5min 滑窗内最多 `WRITE_QUOTA_LIMIT`（默认 3）次，超限拒绝 + 审计 `quota_exceeded`。

#### 16.4 本地签发 CLI（`mint.py`）
```bash
python -m demo.auth.mint admin          # 签发 admin token（1h，贴进调试台输入框）
python -m demo.auth.mint scheduler      # 其他角色
```

#### 16.5 审计日志（`audit_logger.py`）
`trace_id` 贯穿全链路，每次操作即时追加 JSONL 到 `audit.jsonl`。`AUDIT_LOG=none` 禁用落盘。

### 第 19 层 · 缓存层（`cache/`）

**两级缓存，统一入口 facade（v3）：**

| 层级 | 实现 | 命中延迟 | 适用场景 |
|------|------|---------|---------|
| L1 精确缓存 | SQLite | <1ms | 完全相同的 prompt |
| L2 语义缓存 | Chroma cosine | ~50ms | 近义改写、相似问题 |

```python
from .cache.manager import cache_manager  # 统一入口（v3 P0-3）

cache_manager.lookup_exact(messages, tools, model, ...)    # L1 精确
cache_manager.store_exact(...)
cache_manager.lookup_semantic(query, threshold)            # L2 语义
cache_manager.store_semantic(query, answer, sensitive=True) # 状态类短 TTL
cache_manager.clear_state_entries()                        # 模拟器 tick 主动失效
cache_manager.bump_scene_version()                         # 状态 L1 缓存失效
```

**v3 语义缓存阈值收紧**：`CACHE_THRESHOLD` 0.25 → **0.10**。实测 0.25 误命中「查一下 X 的信息」模板句跨实体查询（E1「查 C001 客户」对 A4「查 ORD001 订单」dist=0.250 命中→返回错答案），0.10 下误命中全消除。

**v3 状态类短缓存**：`SEMANTIC_CACHE_STATE_TTL=60`（对齐模拟器 tick），状态类查询不做 24h 固化。

### 第 23 层 · 评估（`eval/`）R6 + 三层升级 + RAGAS

**10 组排产场景 ground truth，三层评估体系：**

| 层级 | 指标 | 权重 |
|------|------|------|
| **工具层** | 工具 F1 + 完整性 + 订单召回 + min_tools_called | × 0.5 |
| **轨迹层** | 路径效率 + 重试质量 + 循环检测 | × 0.3 |
| **语义层** | LLM-as-Judge（faithfulness + answer_relevancy） | × 0.2 |

- 聚合：`overall = 工具×0.5 + 轨迹×0.3 + 语义×0.2`，case ≥0.6 算 pass，回归基线 ≥7/10
- `report.py` 单页 HTML 可视化三层指标 + 循环标记
- **v3 RAGAS 回归**（`ragas_regression.py`）：Q1-Q5 四指标不劣化基线（context_precision 0.60 / faithfulness 0.80 / answer_relevancy 0.80 / context_recall 0.90）；实测 0.82 / 1.00 / 0.90 / 1.00 全达标
- 回测（`backtest/`）：5 个历史延期场景

> 评估体系深度解析（ground truth 构造、三层指标实现、LLM-as-Judge 原理、三级降级、聚合公式、报告生成、手工/自动化分工）详见 [v2.0 指南的「评估体系深度解析」专题](./代码阅读指南-v2.0-2026-08-25.md)，v3.0 机制一致不再重复。

## 第三部分：数据流全景（全链路自动化闭环）

以「自动排产调度器触发 → 求解落库 → 模拟器推进 → KPI 看板」为例：

```
1. AutoScheduler._loop 累计 interval_ticks（或事件 request_rerun）
   └─ scheduler/auto_scheduler.py: _run_locked(trigger)
        │
2. 读取一致性快照（仅待排队订单 + 空闲设备）
   └─ scheduler/snapshot.py: load_snapshot()
        └─ tools/data.py: get_connection() + transaction()
             └─ SELECT FROM orders(status=待排队)/parts/machines/inventory
        │
3. 求解（工艺组级部分成功）
   └─ scheduler/verify.py: 前置校验 C1-C9
   └─ scheduler/model.py: 装箱 + CP-SAT 建模
   └─ scheduler/solver.py: solve() → 20s 预算 → 排产表 + 指标
        │
4. persist 落库（单事务，v3 幂等核心）
   └─ scheduler/solver.py: persist()
        ├─ UPDATE orders SET status='已审核' WHERE id IN (...) AND status='待排队'  ← 原子锁定
        │    （受影响行数 < 预期 → 整体 ROLLBACK）
        ├─ INSERT schedule_versions + batches + preprocess_tasks  ← 前道任务随批次生成
        ├─ 全不可行 → 不建版本
        └─ 写建版 sim 时刻快照（state_change_log）
        │
5. FIFO 自动审批（或人工审批）
   └─ auto_scheduler.py: _fifo_approve（早于 topN 自动通过 + 超龄兜底）
   └─ UPDATE schedule_versions SET status='已审核' + batches.approval_status='通过'
        │
6. 模拟器心跳（独立线程，每 60s 一拍）
   └─ simulator/runner.py: SimulatorRunner._tick_loop
        └─ transaction()
             ├─ engine.py: advance_preprocess  ——前道→待上机（审批门禁，释放人时）
             ├─ engine.py: advance_batches     ——待上机→打印中（审批门禁，锁设备）→静置→完成（释放设备）
             ├─ engine.py: advance_orders      ——订单状态机（待排队→已审核→打印中→完成，幂等）
             ├─ engine.py: fire_events         ——B 层：故障/插单 → request_rerun 即时重排
             ├─ observability/dashboard.py: record_kpi_snapshot() ——KPI 落库
             └─ cache/llm_cache.py: bump_scene_version() ——状态缓存失效
        │
7. KPI 看板 + Web 控制台
   └─ observability/dashboard.py: render_static_html()
   └─ web/: DashboardView ECharts 曲线
```

## 第四部分：关键设计决策（为什么这么设计）

| 决策 | 为什么 | 在哪里体现 |
|------|--------|-----------|
| **ToolRegistry 而非 if/elif 链** | O(1) 查找 + 参数白名单 + 注册即用 | `tools/registry.py` |
| **主备 Provider 列表（v3：DeepSeek 主用）** | 失败自动降级，调用方无感；`PRIMARY_PROVIDER` 可运行时重排 | `config.py` + `core/llm_client.py` |
| **dict 消息而非 LangChain 对象** | 全链路直接喂 OpenAI SDK，避免对象转换风险 | `graph/state.py` 注释 |
| **写方唯一原则** | 每张表只有一个写入者，避免并发写冲突 | `schema/schema.sql` 注释 |
| **先快照后求解** | 求解过程中不能有中间状态变更 | `scheduler/snapshot.py` |
| **CP-SAT 而非 LLM 排产** | 精确约束满足是数学规划的地盘 | `scheduler/solver.py` |
| **排产幂等（事务开头原子锁定）** 🆕 | 同一订单只被打印一次，跨轮/重跑/升级不重复打印 | `scheduler/solver.py` persist |
| **前道任务随批次同事务生成** 🆕 | 状态机能从「前道」推进到「待上机」，否则机器永不占用 | `scheduler/solver.py` + `engine.py` |
| **审批门禁** 🆕 | 模拟器只推进已通过版本，驳回版本不产生生产动作 | `simulator/engine.py` |
| **事件驱动模拟器** | 稀疏事件场景 O(事件数) 远快于逐帧 | `simulator/engine.py` |
| **单事务推进 tick** | tick 失败整体回滚，A 层（状态）和 B 层（事件）一致 | `simulator/runner.py` |
| **订单状态机幂等流转** 🆕 | `('打印中','打印中')` 等 no-op，同 tick 多批不抛错 | `simulator/states.py` |
| **自动排产调度器后台线程** 🆕 | 实现全链路无人值守；`threading.Lock` 防 CP-SAT 并发 | `scheduler/auto_scheduler.py` |
| **FIFO 审批 + 超龄兜底** 🆕 | 常规保留 topN 人审；超龄自动通过防长期无新单停滞 | `auto_scheduler._fifo_approve` |
| **各状态留底 topN** 🆕 | 自动推进不推光演示样本，任意状态随时可查 | `auto_scheduler` + `STATUS_RESERVE_TOP_N` |
| **语义缓存阈值 0.10** 🆕 | 0.25 会误命中模板句跨实体查询（查 C001 命中 ORD001） | `config.CACHE_THRESHOLD` |
| **缓存写入门禁** 🆕 | 循环守卫 dump / 拒绝话术 / 兜底道歉永不固化 | `agents/single_agent.py` |
| **循环守卫按同参连续分组** 🆕 | 非全局计数，避免误伤「同工具不同参数」的合法多轮 | `graph/single_agent_graph.py` |
| **写操作意图守卫** 🆕 | 跑排产/审批意图强制工具轮，不被汇总轮截断 | `graph/single_agent_graph.py` |
| **审核意图识别（查询动词优先）** 🆕 | 「查已审核批次」是读操作，不注入审批指令 | `graph/single_agent_graph.py` |
| **credentials 双源** 🆕 | 敏感信息与代码分离：env 优先，回落 gitignored 凭据文件 | `config._env_or_cred` |
| **两级缓存（L1 + L2）统一入口** 🆕 | facade 模式，新增 L3（Redis）不碎片化 | `cache/manager.py` |
| **RAG 懒加载 + 权限过滤** | 非 RAG 问题零开销；confidential 文档按角色过滤 | `tools/registry.py` + `rag/retriever.py` |
| **信任环洋葱防御** | 网关 → 运行时 → 工具层，层层校验 | `auth/guard.py` |
| **延迟批量导出** | 业务代码在 with 块退出后写 token 属性，立即导出会丢数据 | `observability/tracer.py` |

**v3 总结**：从"排产智能体系统"升级为"**自动化 + 可运营**的完整系统"。自动排产调度器实现排产/审批全自动，订单状态机 + 幂等保证生产闭环正确性，Web 控制台把系统能力交付为可操作界面，调试台把 Agent 表现沉淀为可治理的 case 闭环。剩余差距主要在高级制造算法（APS/多目标优化）、生产化运维（CI/日志轮转/水平扩展）和前端工程化（分包懒加载/CI 部署）。

## 第九部分：常见坑与排错（v3 新增）

| 现象 | 根因 | 解决 |
|------|------|------|
| 「查询已审核批次」答非所问 | app_intent 关键词「审核」误判为审批写操作 | 已修复：查询动词（查/查看/有哪些）排除审批判断 |
| 「查所有还在排队的订单」返回空 | 自动排产把待排队全部锁定为已审核 | 已修复：各状态保留最新 topN 样本（STATUS_RESERVE_TOP_N） |
| 「帮我跑一轮排产」不触发 run_scheduling | 写工具未传 token 被 guard 拒绝，LLM 误读为工具不可用 | 已修复：graph 对写工具自签注入 admin token |
| 「先查版本再审批」两步式被截断 | evaluate_results 排产上下文分支直接置 ready_for_answer | 已修复：写操作意图守卫强制继续工具轮 |
| 「查 C001 客户」返回 ORD001 订单信息 | 语义缓存阈值 0.25 误命中模板句跨实体查询 | 已修复：CACHE_THRESHOLD 收紧至 0.10 |
| 审批版本后批次不推进 | 模拟器只认 approval_status='通过' 的批次（审批门禁） | 正常行为：G1 跑完排产先 I1 审批，再查批次/KPI |
| 改代码后仍返回旧答案 | 语义缓存命中旧答案 | `rm -rf demo/data/cache_db demo/data/llm_cache.db` 后重启 |
| seed --reset 后版本残留 | seed 清理表不完整 | 已修复：seed.reset 联动清 schedule_versions/batches/preprocess_tasks/sim_clock |
| 状态类口语查询命中 24h 固化 | 口语「目前/还有/剩」不含强状态词被当知识类 | 已修复：补状态敏感词走 60s 短缓存 |
| 查询「待排产」订单返回空 | 工艺枚举是 SLA/MJS/SLM，不是「3D打印」 | 用 seed 实际枚举；状态口吻词已归一 |
