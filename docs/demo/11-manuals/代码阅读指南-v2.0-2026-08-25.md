## 第一部分：验证（先跑起来）

### 方式一：Docker 容器（推荐，环境隔离）

```bash
# 1. 构建镜像（在 projects/agent-training 目录）
cd projects/agent-training
docker compose build

# 2. 启动容器（后台运行）
docker compose up -d

# 3. 验证服务是否正常
curl http://localhost:8000/health

# 4. 发送问题测试
curl -X POST http://localhost:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"query": "查询紧急订单"}'

# 5. 查看容器日志
docker logs demo-api

# 6. 多轮对话测试
curl -X POST http://localhost:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"query": "ORD004 能按时交付吗？", "thread_id": "my-session-1"}'

# 查看会话历史
curl http://localhost:8000/threads/my-session-1/history

# 7. 停止容器
docker compose down
```

### 方式二：本地 Python 运行

```bash
cd projects/agent-training

# 0. 建表（v2 MySQL 模式，首次需要）
python -m demo.schema.migrate --up

# 1. 地基自检（验证 config/LLM/工具 三层连通，不调 LLM 也能确认数据层 OK）
python -m demo.main --check

# 2. 单次提问（单 Agent 模式）
python -m demo.main "今天先做哪些订单？"

# 3. 多轮对话（同一会话跨轮共享上下文，sqlite 持久化）
python -m demo.main --chat

# 4. 多 Agent 模式（带鉴权 + 审计报告）
python -m demo.main --mode multi "帮我综合评估 ORD001、ORD003、ORD005"

# 5. 预设场景演示（交互式选编号）
python -m demo.main --demo

# ── v2 制造业主线命令 ──

# 6. 求解一轮排产并落库（M2 求解器）
python -m demo.main --init-schedule

# 7. 启动生产模拟器心跳（M3，Ctrl+C 停止）
python -m demo.main --sim

# 8. Prompt 版本回滚
python -m demo.main --rollback v1

# 9. 环境变量控制
DATA_SOURCE=mysql python -m demo.main --check           # MySQL 模式
SEMANTIC_CACHE=off python -m demo.main "..."             # 关闭语义缓存
CHECKPOINTER=memory python -m demo.main --chat            # 内存模式
OTEL_EXPORTER=otel python -m demo.main "ORD001 能按时交付吗？"  # 真 OTel 导出
```

### 第 2 层 · 数据层基建（`schema/`）🆕

**读什么：** `schema/schema.sql` 全文（300 行，15 张表）→ `schema/migrate.py`

**这是 v2 的地基**——把 v1 的 CSV 内存数据升级为 MySQL 关系型数据库。

**15 张表按所有权分组（写方唯一原则）：**

| 写方 | 表 | 说明 |
|------|-----|------|
| seed + B 层 | customer | 客户（S/A/B/C 等级 + 违约金率） |
| seed + B 层 | orders | 订单（状态/交期/优先级/金额） |
| seed + B 层 | parts | 零件（尺寸/材料/数量/高度） |
| seed + B 层 | machines | 设备（型号/材料/舱尺寸/承重） |
| seed + B 层 | material | 材料字典（SLA/MJS/SLM） |
| seed + B 层 | inventory | 材料库存 |
| solver | schedule_versions | 排产版本（待审核→已审核/已驳回） |
| solver | batches | 批次表（设备/开始/结束/状态） |
| solver | preprocess_tasks | 前道任务 |
| solver | approvals | 审批记录 |
| simulator | sim_clock | 模拟时钟 |
| simulator | sim_events | 模拟事件表 |
| simulator | state_change_log | 状态变更日志 |
| simulator | bad_parts | 坏件记录 |
| 运维 | system_config | 系统配置键值对 |

**迁移工具（migrate.py）：**
```python
# schema_version 表管理版本号，up/down 幂等
def up():     # 执行 schema.sql + 记录版本；已达当前版本 no-op
def down():   # 回滚当前版本（DROP 全部业务表）
# CLI: python -m demo.schema.migrate --up | --down | --status
```

**关注点：**
- **写方唯一**是核心设计原则——每张表只有一个写入者，交叉只读。避免并发写冲突和数据不一致
- 全部 `CREATE TABLE IF NOT EXISTS`，幂等建表
- 建表顺序按外键依赖拓扑（父表在前），避免循环依赖
- 迁移模块**不走业务连接池**（DDL 操作用独立连接），这是刻意的架构分离

### 第 4 层 · 工具函数（`order_tools.py` + `resource_tools.py`）

**读什么：** `order_tools.py` 全部 + `resource_tools.py` 全部

**工具 = 纯函数 + 描述。** 纯函数意味着：输入参数，返回字符串，没有 Agent 逻辑，没有副作用。

```python
                 material="", date_from="", date_to="",

    """查询订单列表，支持多字段筛选 + 排序 + limit"""

def get_order_detail(order_id: str) -> str:      # 单个订单完整信息
def get_production_status(order_id: str) -> str:  # 订单当前生产环节

# resource_tools.py —— 资源工具
def query_inventory(material_name="") -> str:  # 材料库存
```

**关注点：**

- R7 改造后 `query_orders` 从 2 字段扩展到 8 字段 AND 组合筛选 + 排序 + limit

### 第 5 层 · 排产工具（`scheduler_tools.py`）🆕

**读什么：** `scheduler_tools.py` 前 50 行（函数签名 + docstring）+ 每个函数的前 10 行

**v2 核心新增**——11 个实装工具 + 2 个占位，使 Agent 能"动手做排产"而不仅是"问答"。

```
实装工具（11 个）：
  ├─ 求解类：run_scheduling       触发排产求解并落库（写工具，需审批）
  ├─ 查询类：query_schedule       查最新/指定排产版本 + 批次表
  │         query_sim_events     查模拟器事件（类型/状态过滤）
  ├─ 审批类：approve_schedule    排版人审批：待审核→已审核/已驳回
  │
  └─ 评估类（M4b）：
            query_load_assessment   设备负载评估（分区颜色 + 利用率）
            query_ctp               可承诺交期：给定订单预计完成时间
            query_order_tracking    订单跟踪：当前环节 + 历史轨迹
            query_preprocess_load   前道负载：待处理任务数 + 产能估算
            query_kpi              KPI 指标（准交率/在制数/利用率/延期数）
            query_forecast         需求预测（分材料日级，M5a）
            query_yield             良率分析（规则基 + 建议）
```

**关注点：**
- 写工具（`run_scheduling`/`approve_schedule`）需要权限，读工具开放
- 审计在 registry 治理层统一落，handler 保持纯业务（单一职责）
- 工具函数返回 Markdown 表格，与 order_tools 风格一致（LLM 友好）
- 评估类工具复用 `scheduler.assessment` 纯函数计算层，避免重复逻辑

### 第 6 层 · 工具注册中心（`tools/registry.py`）★ 重点

**读什么：** `registry.py` 全部

**这是连接 Agent 和工具的桥梁。** 为什么要有注册中心？因为 week1 是硬编码 if/elif 链（O(n) 线性查找），注册中心改为 O(1) 字典查找。

```python
class ToolRegistry:
    def register(self, name, description, parameters, handler, ...):
        """注册工具：Schema + Handler 一起注册"""
        self._tools[name] = ToolSchema(...)     # 存元数据（给 LLM 看的）
        self._handlers[name] = handler          # 存函数（执行用的）

    def get_tool_defs(self) -> list[dict]:
        """返回 OpenAI Function Calling 格式的工具列表"""

    def execute(self, name, arguments, token=None, audit=None):
        """执行工具，五步：① 参数白名单 ② RBAC 校验 ③ sandbox 重试 ④ 调 handler ⑤ tracer 记录"""
```

**build_default_registry() 注册了约 18 个工具：**
- 3 个订单工具 + 3 个资源工具（v1）
- 1 个 RAG 工具 `search_knowledge_base`（懒加载）
- 11 个排产工具（v2 新增：求解/查询/审批/评估/预测/良率）

**关注点：**
- `register()` 一次调用完成 Schema + Handler 绑定，不会出现"定义了但没实现"
- `execute()` 的**参数白名单**是关键安全机制——LLM 可能传多余参数，白名单过滤保安全
- `execute()` 的 **RBAC 校验**是洋葱型防御的第 3 层
- **sandbox 集成**（R1）：每个工具调用包裹超时 + 指数退避重试
- **RAG 懒加载**——注册时不加载重依赖，首次调用才拉 jieba/chromadb/reranker
- v2 工具数从 7 扩展到 18，注册中心模式零修改扩展

### 第 7 层 · 工具沙箱（`tools/sandbox.py`）R1

**读什么：** `sandbox.py` 全部（约 90 行）

**关注点：**
- `run_with_retry(handler, args, tool_name)` — 每个工具调用包裹在这个函数里，对上层透明
- 超时控制：用 `threading.Timer` 做跨平台超时，默认 10s（`TOOL_TIMEOUT`）
- 指数退避重试：1s → 2s → 4s，最多 3 次（`TOOL_MAX_RETRIES`）
- 返回三元组 `(result_str, success, retries)` — registry 不感知重试细节
- 全部重试失败时返回结构化错误（而非崩溃），LLM 收到错误后可换策略

**为什么不是裸 try/except：** 异常捕获只兜底一次，Agent 没法知道"这次失败是不是偶发的"。重试 + 退避让瞬时故障自愈。

### 第 8 层 · LLM 调用基座（`core/llm_client.py`）

**读什么：** `llm_client.py` 全部

**这是 Agent 的"大脑"——所有 LLM 调用都走这里的统一入口。**

```python
def call_llm(messages, tools=None, max_tokens=500, temperature=0.3):
    """统一 LLM 调用，内置主备自动降级。遍历 PROVIDERS，第一个成功即返回"""
    for p in PROVIDERS:
        try:
            client = OpenAI(..., http_client=httpx.Client(trust_env=False))
            with tracer.span("llm:call", provider=p["name"], model=p["model"]):
                resp = client.chat.completions.create(...)
            # L1 精确缓存：调用前查，命中直接返回
            # 调用成功后写入缓存 + cost_tracker 计费
            return resp
        except Exception as e:

    raise RuntimeError(f"所有 provider 均失败")
```

**关注点：**
- `trust_env=False`：绕过 Windows 系统代理残留
- 主备降级对调用方透明——调用方不关心当前用的是豆包还是 DeepSeek
- token 用量记录在 span 的 attributes 里，随观测层导出
- **L1 精确缓存**（`llm_cache.py`）：相同 prompt 命中 <1ms，0 token
- **LLM 连接池**：provider 级 httpx 连接池，keep-alive 60s
- **成本熔断**：`CostTracker` 累计超预算抛 `BudgetExceededError`

### 第 9 层 · 排产求解器（`scheduler/`）🆕 ★ 重点

**读什么：** 按顺序 `snapshot.py` → `verify.py` → `model.py` → `solver.py` → `assessment.py`

**这是 v2 的"心脏"——把 v1 的"LLM 文本建议排产"升级为"数学规划精确求解"。**

#### 9.1 快照（`snapshot.py`）
读一致性快照：从 MySQL 一次性读取订单/零件/设备/库存 → 组装成内存字典 → 传给求解器。为什么要快照？求解过程中不能有中间状态变更，一次性读取保证数据一致性。

#### 9.2 约束校验（`verify.py`）
C1-C9 九条硬约束的程序化校验器，纯函数。求解前后都可以调——求解前做前置检查（不满足直接返回冲突，不浪费求解时间），求解后做结果验证。

```
C1 同舱同材料      C2 容量约束（尺寸/件数/承重）  C3 机型匹配
C4 批次时长=max    C5 整批优先可拆              C6 设备互斥+静置占用
C7 交期 23:59      C8 日可用 21.6h（90%）       C9 前道完成 ≤ 打印开始
```

#### 9.3 模型（`model.py`）★ 核心
两步建模：
1. **装箱**：先把零件按设备 + 材料分组，在版子里装箱（同一版子单材料约束）
2. **CP-SAT**：OR-Tools 约束规划，决策变量 = 每批次的开始/结束时间，约束 = C6 设备互斥 + C7 交期 + C8 日产能，目标 = 最小化总延期加权和

#### 9.4 求解器入口（`solver.py`）
```
snapshot → verify（前置校验）→ 装箱 → CP-SAT 建模 → 求解（60s 预算）
  → compute_metrics（准交率/延期数/目标值/批次统计）
  → persist 落库（schedule_versions + batches，状态=待审核）
```

**求解预算三件套**（R-D1）：
1. CP-SAT 预算：`solver_max_time_seconds`（默认 60s）
2. 预算耗尽：返回当前最优可行解 + `timed_out=true`，不抛错
3. 无可行解：输出冲突订单清单（超尺寸/超承重），不静默空结果

#### 9.5 产能评估（`assessment.py`）M4b
只读聚合计算层，5 个排产工具复用：
- `zone_color`（设备分区颜色）/ `t_window_availability`（时间窗口可用率）
- `compute_ctp`（可承诺交期）/ `preprocess_load`（前道负载）
- `kpi_metrics`（KPI 指标：准交率/在制数/利用率/延期数/良率）

纯函数独立可测；拼装层连库读取后复用纯函数。

**关注点：**
- 为什么用 CP-SAT 而不是 LLM 排？——精确约束满足问题是数学规划的地盘，LLM 做定性分析、CP-SAT 做定量求解，互补
- 为什么先装箱再排程？——同一版子的零件并行打印（单版单材料），这是 3D 打印的物理约束
- 求解时间预算 60s 是排产场景的经验值：工业级排产 30s-5min 都可接受

### 第 10 层 · 生产模拟器（`simulator/`）🆕 ★ 重点

**读什么：** 按顺序 `clock.py` → `events.py` → `states.py` → `engine.py` → `runner.py`

**模拟器 = 动态世界**。求解器给的是静态最优方案，模拟器让时间流动起来，看方案在真实生产扰动下的表现。

#### 10.1 事件驱动模型
```
订单到达 → 前道处理 → 前道完成 → 待上机 → 打印中 → 静置中 → 完成
                  ↓                        ↓
              人工班次（换班 30min）     设备故障（随机）
```
每个状态变更是一个事件（scheduled → fired → handled），事件驱动而非逐帧推进。

#### 10.2 A 层 + B 层（`engine.py`）
每 tick 单事务内推进两层：
- **A 层（状态推进）**：批次状态机流转（打印中→静置中→完成 / 待上机→打印中）+ 前道推进 + 订单到期标记
- **B 层（事件触发）**：到点的 scheduled 事件被触发，执行 handler（如 machine_failure → 标记设备不可用 + 触发"需重排"告警）

**班次系数**：3 班倒 × 8h，每班换班 30min 无产出 → 净 22.5h/天 = SHIFT_FACTOR = 0.9375

#### 10.3 心跳运行器（`runner.py`）
独立线程主循环：
- 每 `SIM_TICK_SECONDS`（默认 60s = 1 sim 小时）推进一拍
- 每 tick bump `llm_cache` 的 `scene_version`，状态相关精确缓存失效（R-3）
- 连续失败熔断：同一事件连续失败 10 次停止心跳，防脏数据卡死（D2）
- 线程私有 Tracer 实例（全局 tracer 非线程安全），span `simulator:tick`

#### 10.4 种子数据（`seed.py`）
写方之一：初始化业务表的基础数据。模拟器 B 层也是写方（订单到达/restock 等）。

**关注点：**
- 为什么用事件驱动而非逐帧？——事件驱动 O(事件数)，逐帧 O(时间分辨率 × 实体数)，前者在稀疏事件场景高效得多
- 为什么单事务推进？——tick 失败整体回滚，保证 A 层和 B 层的一致性，不会出现"状态变了但事件没记"
- 模拟器和求解器的关系：求解器规划未来，模拟器推演当下；Agent 两者都能调（静态方案 + 动态状态）

### 第 15 层 · RAG 混合检索（`rag/`）

**RAG 是 Agent 的"知识库"**——合同条款、延期记录等非结构化知识。

### 第 16 层 · 缓存层（L1 + L2）

**两级缓存，互补覆盖两种复用场景：**

| 层级 | 实现 | 命中延迟 | 适用场景 |
|------|------|---------|---------|
| L1 精确缓存 | SQLite | <1ms | 完全相同的 prompt |
| L2 语义缓存 | Chroma cosine | ~50ms | 近义改写、相似问题 |

- L1 缓存 key：MD5(messages + tools + model + max_tokens + temperature)
- L2 阈值：cosine distance ≤ 0.20 命中
- 语义缓存仅对无多轮上下文的独立问题生效（多轮答案依赖前文，不可复用）

### 第 19 层 · 统计预测（`forecast/`）🆕 M5a

**读什么：** `models.py`（纯函数）→ `forecaster.py`（聚合入口）

**预测模型（纯函数）：**
- 移动平均：窗口 N 天均值
- 指数平滑：α 可调（默认 0.3，用户 2026-08-23 确认）

**聚合入口：**
- `history_daily()`：orders JOIN parts 按 order_date 逐日聚合，分材料统计件数 + 机时
- `forecast()`：读 system_config（forecast_method / forecast_window / smoothing_alpha）→ 调 models → 逐日分材料预测

**口径**：机时 = Σ(height ÷ rate × quantity)。仅支持 MySQL 模式（CSV orders 无 order_date 列）。

**关注点：**
- 为什么纯函数 + 聚合入口分离？——纯函数可单测、可替换，聚合层只负责读 DB + 调模型 + 格式化
- 为什么用指数平滑而不是更复杂的模型？——demo 阶段数据量小（15 条订单），指数平滑足够且可解释；生产数据量大后可升级为 Prophet / LSTM

### 第 20 层 · 评估（`eval/`）R6 + 三层升级

**10 组排产场景 ground truth，三层评估体系：**

| 层级 | 指标 | 权重 |
|------|------|------|
| **工具层** | 工具 F1 + 完整性 + 订单召回 + min_tools_called | × 0.5 |
| **轨迹层** | 路径效率 + 重试质量 + 循环检测 | × 0.3 |
| **语义层** | LLM-as-Judge（faithfulness + answer_relevancy） | × 0.2 |

- `min_tools_called`：该调 N 个工具、实际少于 N → 工具分直接 0
- 语义层降级：无检索上下文时 faithfulness = 0，relevancy 用关键词启发式兜底
- 聚合：`overall = 工具×0.5 + 轨迹×0.3 + 语义×0.2`，case ≥0.6 算 pass，回归基线 ≥7/10
- `report.py` 单页 HTML 可视化三层指标 + 循环标记
- 回测（`backtest/`）：5 个历史延期场景，按人工复盘结论覆盖度评分

### 专题 · 评估体系深度解析（自动打分 + 人工校准）

> 本节深入 `eval/` 模块的每个齿轮：ground truth 怎么构造、三层指标怎么计算、LLM-as-Judge 怎么工作、报告怎么生成、人工在哪介入。
> 对应文件：`ground_truth.json` + `metrics.py` + `trajectory.py` + `trajectory_capture.py` + `judge.py` + `judge_prompt.py` + `runner.py` + `report.py`

#### 一、评估数据集（ground_truth.json）

**10 组排产场景，每组含 5 类标注字段：**

| 字段 | 类型 | 用途 |
|------|------|------|
| `id` | str | case 编号（eval_001 ~ eval_010） |
| `scenario` | str | 场景名称，用于报告展示 |
| `query` | str | 用户问题（输入） |
| `expected_tools` | list[str] | 期望调用的工具列表（工具层 F1 计算基准） |
| `expected_order_ids` | list[str] | 期望出现在答案中的订单号（订单召回基准） |
| `checks` | dict | 完整性校验：`must_contain` / `must_not_contain` / `min_tools_called` |

**场景分布**：
- 排产优先级 / 紧急订单识别 / 单订单详情 / 客户信用评估 / 材料库存影响
- 合同条款 RAG / 设备瓶颈 / 客户专项 / 多条件综合 / 延期记录查询

**怎么读 ground truth**：直接打开 `demo/eval/ground_truth.json`，每个 case 就是一份"输入 + 标准答案骨架"。注意：标准答案不是完整答案文本，而是**约束条件**——这样 LLM 回答措辞可以变，但核心信息必须命中，避免"答案写死了导致 LLM 稍微换个说法就判错"。

**怎么加新 case**：在 `cases` 数组里追加一个对象，填好 6 个字段即可。建议每个新场景先跑通、确认预期，再加入 ground truth——避免 case 本身就有问题。

#### 二、第 1 层：工具层（`metrics.py`）— 全自动，零 LLM 调用

**4 个指标，加权 0.3 + 0.5 + 0.2 = 工具层总分：**

| 指标 | 权重 | 计算方式 | 代码位置 |
|------|------|---------|---------|
| 工具调用 F1 | × 0.3 | `2 × precision × recall / (precision + recall)`，去重后集合运算 | `tool_call_accuracy()` |
| 回答完整性 | × 0.5 | `must_contain` 全部命中 + `must_not_contain` 全部未命中，逐条算通过率 | `answer_completeness()` |
| 订单召回率 | × 0.2 | 预期订单号出现在答案里的比例 | `compute_all_metrics()` |
| **min_tools_called 惩罚** | — | 实际调用工具数 < 最低要求 → **工具分直接清零** | 第 53-55 行 |

**为什么 min_tools_called 是硬惩罚**：这是 R6 修复的核心 bug——原来的 F1 计算中，如果 Agent 只调了 1 个工具但刚好是期望的之一，F1 可能还不错（比如 0.5），但实际上它漏掉了必要的维度（比如只查了订单没查库存）。min_tools_called 强制保证"该调几个工具就得调几个"，调少了直接 0 分。

**怎么看单个 case 的工具层分数**：
```bash
python -m demo.eval.runner --case eval_001 --no-judge
# 输出里 tool.xxx 就是工具层各指标
# completeness_details 能看到每一条 must_contain / must_not_contain 的通过情况
```

#### 三、第 2 层：轨迹层（`trajectory_capture.py` + `trajectory.py`）— 全自动

轨迹层回答一个问题：**Agent 走的路径效率高不高？**

##### 3.1 轨迹重建（`trajectory_capture.py: rebuild_trajectory`）

先从两个数据源重建有序的工具调用序列：

| 数据源 | 拿什么 | 为什么需要 |
|--------|--------|-----------|
| `tracer.get_summary()["spans"]` | 工具调用的**时序顺序** + 耗时 + 成功/重试状态 | span 按时间顺序排列，能还原"先调了 A 再调了 B" |
| `tool_results`（Agent state） | 每次调用的**参数** + 返回结果预览 | span 里没有参数和结果，需要从 state 补 |

**匹配算法**：按 span 的顺序遍历，从 tool_results 里按顺序消费同名工具记录（因为同一工具可能被调多次）。

**循环检测**：同一工具被调用 >= 3 次 → 标记 `loop_detected=True`。

**输出结构**：
```python
{
  "calls": [            # 有序的调用序列
    {"tool": "query_orders", "arguments": {...},
     "duration_ms": 12.5, "success": True, "retries": 0, "order": 1},
    ...
  ],
  "total_tool_calls": 5,   # 总调用次数
  "distinct_tools": 3,     # 不重复工具数
  "loop_detected": False,  # 是否检测到循环
  "errors": 0,             # 失败次数
}
```

##### 3.2 轨迹打分（`trajectory.py: compute_trajectory_score`）

3 个指标，加权 0.4 + 0.4 + 0.2：

| 指标 | 权重 | 计算方式 | 含义 |
|------|------|---------|------|
| 路径效率 | × 0.4 | `1 - 0.2 × 冗余调用数`，同工具多出来的每次扣 0.2 | 同一工具反复调 = 效率低 |
| 重试质量 | × 0.4 | `1 - 0.2×总重试 - 0.3×总失败`，全失败直接 0 | 工具挂了多少次、重试了多少次 |
| 循环检测 | × 0.2 | 检测到循环直接 0 分，否则 1.0 | 死循环是最严重的路径问题 |

**怎么读轨迹层结果**：看 `total_tool_calls` 和 `distinct_tools` 的差距——差距越大，冗余调用越多。如果 `loop_detected=True`，那就是 Agent 在某个问题上绕圈子了，需要查 prompt 或工具描述。

#### 四、第 3 层：语义层（`judge.py` + `judge_prompt.py`）— LLM 自动打分 + 降级兜底

语义层回答：**答案忠实于上下文吗？回答精准吗？**

##### 4.1 两种模式：有 context vs 无 context

| 模式 | 触发条件 | 评分项 |
|------|---------|--------|
| **有检索上下文** | tool_results 里有 search_knowledge_base 结果 | faithfulness + answer_relevancy |
| **无检索上下文** | 没有 RAG 工具调用 | 只评 answer_relevancy（faithfulness 标记未评估、不计分） |

这是**自适应设计**——没有上下文就没法评忠实度（总不能凭空说它编造吧），所以语义分自动降为 relevancy 单项。

##### 4.2 LLM-as-Judge 工作原理

```
输入：question + [context] + answer
  ↓
构造 judge 消息（system prompt + user prompt）
  ↓
调 call_llm(temperature=0.0, max_tokens=200)
  ↓
解析 JSON 输出 → {"faithfulness": 0.8, "answer_relevancy": 0.9}
```

**为什么复用 `call_llm`**：和 demo 共用同一 LLM 调用层，自动享受主备 fallback + 连接池 + 成本追踪。不需要为 judge 单独接一套 LLM 基础设施。

**Judge 的提示词（`judge_prompt.py`）**：
- system prompt：定义两个维度的评分标准 + JSON 输出格式要求
- user prompt：填入问题 + 上下文 + 答案，让 judge 打分
- 无 context 版本：单独的 relevancy system prompt

##### 4.3 三级降级机制（从左到右兜底）

```
真实 LLM-as-Judge
  ↓ 失败（LLM 异常 / JSON 解析失败）
关键词启发式（_judge_relevancy_only）
  ↓ 连启发式都算不出（问题太短无有效词）
默认 0.5 分
```

- **第 1 级**：真实 LLM 打分（正常路径）
- **第 2 级**：LLM 挂了 → 关键词命中率兜底（问题分词，统计答案里命中了多少个 ≥2 字的词）
- **第 3 级**：连关键词都提取不出来 → 给 0.5 中性分

**保证**：judge 永远不会抛异常中断评估，最差情况是降级给 0 分或 0.5 分。

##### 4.4 怎么手动复核 judge 结果

judge 不是绝对真理，对存疑的 case 可以手工复核：

1. 跑单个 case：`python -m demo.eval.runner --case eval_006`
2. 看输出里的 `answer_preview`（答案前 150 字）+ semantic 各维度分
3. 如果觉得 judge 打分不合理：
   - 检查答案全文（在 `final_answer` 里）
   - 检查 context（RAG 检索了什么片段）
   - 调整 judge prompt 或 case 的 checks（比如加 must_contain）
   - 最终以人工判断为准，LLM-as-Judge 是辅助不是裁决

#### 五、聚合公式与通过标准

```
工具层 overall_score = tool_f1 × 0.3 + completeness × 0.5 + order_hit × 0.2
轨迹层 trajectory_score = path_efficiency × 0.4 + retry_quality × 0.4 + loop_score × 0.2
语义层 semantic_score = 有context ? (faithfulness + relevancy)/2 : relevancy

overall = 工具 × 0.5 + 轨迹 × 0.3 + 语义 × 0.2
pass = overall ≥ 0.6
回归基线 = 10 个 case 中 ≥ 7 个 pass
```

**权重为什么是 0.5 / 0.3 / 0.2**：
- 工具层最重（0.5）：工具都调错了，回答再漂亮也没用——这是 Agent 的基本功
- 轨迹层次之（0.3）：路径效率影响成本和延迟，但不影响正确性
- 语义层最轻（0.2）：忠实度和相关性重要，但受 LLM 本身波动影响大，权重太高会让评估不稳定

#### 六、运行器（`runner.py`）— 串起所有层

**完整评估流程（单个 case）：**

```
1. tracer.reset() + cost_tracker.reset()   清空上一轮
2. run_single_agent(query)                  跑 Agent（或 run_supervisor 多 Agent 模式）
3. 提取 actual_tools 从 tool_results
4. ── 工具层：compute_all_metrics(case, answer, actual_tools)
5. ── 轨迹层：rebuild_trajectory(trace, tool_results) → compute_trajectory_score()
6. ── 语义层：judge_semantic_quality(query, context, answer)
7. 聚合 overall_score
8. 标记 pass / fail
9. tracer.flush() + 打印一行结果
```

**批量流程（10 个 case）：**
- 逐个 case 串行跑
- 每个 case 结束打印一行（通过/分数/各层分/耗时）
- 最后打印汇总（通过数/平均分/分层健康度/回归检查）

**语义缓存默认禁用**：`run_eval()` 开头强制 `SEMANTIC_CACHE=off`。为什么？因为缓存命中会跳过整图执行，评估测的是"当前代码的能力"而不是"缓存里的旧答案"。曾被陈旧缓存污染导致首跑 3/10 vs 重跑 10/10。

**重要参数**：

| 参数 | 效果 |
|------|------|
| `--case eval_001` | 只跑单个 case（调试用，省时间） |
| `--mode multi` | 多 Agent 模式跑（测 Supervisor） |
| `--no-judge` | 跳过 LLM-as-Judge（省钱 + 提速，语义分降级） |
| `--report` | 跑完生成 HTML 报告 |

#### 七、HTML 报告（`report.py`）— 可视化

**单页自包含 HTML**，内联 CSS，零外部依赖，直接双击打开就能看。

**报告内容**：
- 顶部汇总条：通过数 / 综合评分 / 三层均值
- 详细表格：case 列表（ID / 场景 / 综合分进度条 / 工具层 / 轨迹层+循环标记 / 语义层 / 耗时）
- 失败行标红（fail 类）
- 循环标记：🔴 检测到循环 / ✅ 正常

**生成命令**：
```bash
python -m demo.eval.runner --report
# 输出到 demo/eval/reports/ 目录
```

#### 八、手工 vs 自动化分工（什么环节需要人介入）

| 环节 | 自动化 | 人工介入 | 什么时候需要人工 |
|------|--------|---------|-----------------|
| ground truth 编写 | ❌ | ✅ | 新增 case、修改预期答案约束 |
| 工具层打分 | ✅ | ❌ | —（纯规则，零歧义） |
| 轨迹层打分 | ✅ | ❌ | —（结构化计算） |
| 语义层打分 | ✅（LLM） | ✅（复核） | 分数异常低/高、存疑的 case |
| 聚合与通过判定 | ✅ | ✅（边界 case） | overall 在 0.6 附近徘徊的 |
| 回归基线检查 | ✅ | ✅（退化分析） | 低于 7/10 时人工排查根因 |
| HTML 报告生成 | ✅ | ✅（解读） | 拿给业务方/面试时讲解 |

**一句话总结**：工具层和轨迹层是纯自动化、零争议；语义层 LLM 打主力，但人保留最终复核权；ground truth 和退化分析必须人来做。


## 第四部分：关键设计决策（为什么这么设计）

| 决策 | 为什么 | 在哪里体现 |
|------|--------|-----------|
| **ToolRegistry 而非 if/elif 链** | O(1) 查找 + 参数白名单 + 注册即用 | `tools/registry.py` |
| **主备 Provider 列表** | 第一个成功即返回，失败自动降级，调用方无感 | `config.py` + `core/llm_client.py` |
| **dict 消息而非 LangChain 对象** | 全链路直接喂 OpenAI SDK，避免对象转换风险 | `graph/state.py` 注释 |
| **写方唯一原则** 🆕 | 每张表只有一个写入者，避免并发写冲突和数据不一致 | `schema/schema.sql` 注释 + 各模块写职责 |
| **先快照后求解** 🆕 | 求解过程中不能有中间状态变更，一次性读取保证一致性 | `scheduler/snapshot.py` |
| **CP-SAT 而非 LLM 排产** 🆕 | 精确约束满足是数学规划的地盘；LLM 做定性分析、CP-SAT 做定量求解，互补 | `scheduler/solver.py` |
| **事件驱动模拟器** 🆕 | 稀疏事件场景 O(事件数) 远快于逐帧 O(时间×实体数) | `simulator/engine.py` |
| **单事务推进 tick** 🆕 | tick 失败整体回滚，保证 A 层（状态）和 B 层（事件）的一致性 | `simulator/runner.py` |
| **Dashboard 分层：落/查/兜** 🆕 | 写方唯一 + 读侧只读 + 零依赖兜底（静态 HTML 无需 CDN） | `observability/dashboard.py` |
| **纯函数 + 拼装层分离** 🆕 | 核心计算逻辑可单测、可替换；拼装层只负责读 DB + 调模型 + 格式化 | `scheduler/assessment.py` + `forecast/` |
| **两级缓存（L1 + L2）** | 精确命中 <1ms + 语义命中 ~50ms，互补覆盖两种复用场景 | `cache/llm_cache.py` + `cache/semantic_cache.py` |
| **RAG 懒加载** | 非 RAG 问题零开销，不加载 jieba/chromadb/reranker | `tools/registry.py` + `rag/retriever.py` |
| **信任环洋葱防御** | 网关 → 运行时 → 工具层，层层校验，任一层被突破还有下一层 | `auth/guard.py` |
| **延迟批量导出** | 业务代码在 with 块退出后写 token 属性，立即导出会丢数据 | `observability/tracer.py` |

## 第五部分：持久化全景（v2 升级版）

> v2 涉及 9 种持久化（v1 是 6 种），分布在 3 个地方。理解它们才能看懂「重启不丢」「跨容器恢复」「看板历史」的实现。

### 全景一览

| # | 存储 | 类型 | 位置 | 管理模块 | 用途 | 生产演进 |
|---|------|------|------|---------|------|---------|
| ① | `checkpoints.db` | SQLite | `RUNTIME_DIR/` | `graph/checkpointer.py` | 多轮对话上下文 | PostgreSQL |
| ② | `tokens.db` | SQLite | `RUNTIME_DIR/` | `auth/token_exchange.py` | STS Token 持久化 | Redis |
| ③ | `audit.jsonl` | JSONL 文件 | `RUNTIME_DIR/` | `auth/audit_logger.py` | 审计日志 | ELK / Loki |
| ④ | `llm_cache.db` | SQLite | `RUNTIME_DIR/` | `cache/llm_cache.py` | L1 精确缓存 | Redis |
| ⑤ | `cache_db/` | Chroma | `RUNTIME_DIR/` | `cache/semantic_cache.py` | L2 语义缓存 | Redis + bge-large-zh |
| ⑥ | `chroma_db/` | Chroma | `RUNTIME_DIR/` | `rag/knowledge_base.py` | RAG 知识库 | Milvus / PGVector |
| ⑦ | **业务库** 🆕 | **MySQL** | **demo_scheduling** | **多模块（写方唯一）** | **订单/零件/设备/排产/模拟/配置 15 张表** | **MySQL 8.0+（主从+连接池）** |
| ⑧ | **KPI 快照** 🆕 | **MySQL 表** | **kpi_snapshot** | **observability/dashboard.py** | **KPI 时间序列** | **时序数据库（TimescaleDB）** |
| ⑨ | **成本 + Trace** 🆕 | **MySQL 表** | **cost_records / trace_records** | **observability/dashboard.py** | **Query 粒度成本 + trace 摘要** | **ClickHouse / Loki** |

> ⑦⑧⑨ 都在同一个 MySQL 实例的 demo_scheduling 库里，但属于不同用途、不同写方。
