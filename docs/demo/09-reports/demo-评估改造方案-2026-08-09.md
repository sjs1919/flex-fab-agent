## 〇、总体思路

demo 评估体系已成型（⭐⭐⭐⭐⭐），但相对制造业智能体行业基线仍有 13 项缺口。本方案按**「重问题优先 → 分阶段推进」**落地：

```
Phase A  重度问题修补（阻碍评估真实性的基础问题，最优先）
  │
Phase B  制造业主线缺口（M1-M4）——让 Agent「更会排产」
  │
Phase C  生产化缺口（M5-M8）——让 demo「更接近生产」
  │
Phase D  深化评估体系本身（CI 持续化 + 逐工具规则 + 检索阈值 + 评估闭环）
```

每个 Phase 含：目标 / 任务拆分（T 编号）/ 验收标准 / 关联报告依据。

## 一、Phase A：重度问题先修补（P0 基础）

> **依据：** 过程定位报告「发现但未修的问题」——这些问题阻碍评估/回测的真实性，必须先修。

### A1. 火山豆包主 provider 配额超限（429 AccountQuotaExceeded）

**现状：** 每次评估先试主 provider（火山豆包）失败 429 → 再切 DeepSeek，超时严重；回归基线无法在真实主 provider 下跑。

| 项 | 内容 |
|----|------|
| **任务** | A1.1 把 DeepSeek 设为第一 provider（临时，等火山配额恢复）<br>A1.2 火山配额恢复后重跑 `python -m demo.eval.runner --report` 拿真实回归基线 |
| **验收** | `--check` 显示第一 provider 为 DeepSeek；真实回归基线 ≥7/10 |
| **动作对象** | 修环境/账户（非代码） |

### A2. orders.csv 缺 `客户等级`/`工艺` 列（R7 参数空转）

**现状：** R7 的 `customer_level`/`process` 筛选参数已实现，但 CSV 无这两列，过滤全空——排产/客户评估场景无法真正按等级筛选。

| 项 | 内容 |
|----|------|
| **任务** | A2.1 给 orders.csv 补 `客户等级`（S/A/B/C）和 `工艺`（如 3D打印/CNC/热处理）列<br>A2.2 数据补全后，回补 `tools/test_order_tools.py` 断言命中（当前是「记录真实行为」占位） |
| **验收** | `query_orders(customer_level="A")` 能筛出 A 级客户订单；对应测试改为断言命中 |
| **动作对象** | 修数据（代码超前于数据，补数据优先） |

### A3. 回测真实跑通

**现状：** `backtest/` 模块已实现（5 场景 + 覆盖度评分），但真实跑依赖 LLM 且从未跑过。

| 项 | 内容 |
|----|------|
| **任务** | A3.1 跑 `python -m demo.backtest.runner`（需真实 LLM + DeepSeek 优先）<br>A3.2 若某个场景覆盖度过低，分析是 Agent 理解问题还是场景设计问题 |
| **验收** | 5 场景全部跑出覆盖率；基线 ≥0.6 达成 |
| **动作对象** | 验证（模块已实现） |

**Phase A 完成标志：** 无阻碍评估/回测真实性的遗留问题，真实回归基线可跑。

## 二、Phase B：制造业主线缺口（M1-M4，最高优先）

> **依据：** 缺失评估报告 P0 四项 + 技术专家「单点快照推理 → 实时数据闭环」判断。

### B1. M4 结构化排产结果（先做，性价比最高）

**现状：** `generate_answer` 只输出 LLM 文本建议，无结构化排产表——无法数值验证排产正确性。

| 项 | 内容 |
|----|------|
| **任务** | B1.1 `graph/state.py` 加 `schedule_plan` 字段（JSON）<br>B1.2 `generate_answer` 在文本建议之外，输出结构化排产表（订单/优先级/建议时间/原因）<br>B1.3 评估层新增「排产结果校验」：JSON 排产表是否满足交期/优先级约束 |
| **验收** | 评估报告的每个 case 含结构化排产表；排产正确性可数值断言（如 ORD003 是否排第一） |
| **对应角色** | 开发者/测试者 |

### B2. M1 排产约束求解（制造业核心）

**现状：** 纯 LLM 文本给排产建议，无数值求解——交期/产能/物料约束没有硬校验。

| 项 | 内容 |
|----|------|
| **任务** | B2.1 引入 OR-Tools 或启发式求解器，做交期-产能-物料约束排产<br>B2.2 区分**硬约束**（交期不可晚于、物料不可缺）和**软约束**（优先级、设备负载均衡）<br>B2.3 LLM 建议与求解器结果交叉校验：LLM 生成 → 求解器验证/修正 |
| **验收** | 对 eval_001（今天先做哪些订单）求解器给出满足约束的排产序列；与 LLM 建议一致性可对比 |
| **对应角色** | 技术专家/AI 专家/架构 |
| **依赖** | B1（结构化排产结果是求解器输入） |

### B3. M2 实时数据源抽象（从快照到闭环）

**现状：** `tools/data.py` 读静态 CSV 快照，无实时源——无法验证「数据更新后决策是否自适应」。

| 项 | 内容 |
|----|------|
| **任务** | B3.1 抽象 `DataSource` 接口（`load_orders()` 等从 CSV 改为接口）<br>B3.2 CSV 实现保留（默认）；新增 DB/IoT 实现（可插拔）<br>B3.3 支持增量更新（数据变更后 Agent 决策可重新评估） |
| **验收** | 换数据源实现不改工具接口；构造「订单状态变化」场景验证 Agent 决策随数据更新 |
| **对应角色** | 技术专家/架构/DBA |
| **依赖** | — |

### B4. M3 human-in-the-loop（人机协同确认）

**现状：** 图全程自动，关键排产决策无人确认。

| 项 | 内容 |
|----|------|
| **任务** | B4.1 用 LangGraph `interrupt_before` 在关键决策节点暂停<br>B4.2 人工确认接口（确认/修改/拒绝排产方案）<br>B4.3 确认后恢复执行（checkpointer 已支持恢复） |
| **验收** | 排产建议前暂停，人工确认后继续；评估层对「人工干预后的决策」单独打分 |
| **对应角色** | AI 专家/架构 |
| **依赖** | B1（结构化排产结果是人工确认的对象） |

**Phase B 完成标志：** demo 从「能排产」升级为「约束正确 + 实时响应 + 人机协同」的制造业排产 Agent。

## 三、Phase C：生产化缺口（M5-M8，生产级加固）

> **依据：** 缺失评估报告 P1 五项。

### C1. M5 API 限流

**现状：** `api.py` 无限流，恶意请求可打爆 LLM 预算。

| 项 | 内容 |
|----|------|
| **任务** | C1.1 网关层加 rate limit（按 IP/租户，如 10 req/min）<br>C1.2 超限返回 429 + 结构化错误 |
| **验收** | 连续请求超阈值被拒绝；审计记录限流事件 |
| **对应角色** | 安全审查 |

### C2. M6 Token 签名 + refresh

**现状：** Token 无签名（篡改即伪造）；单 Agent 模式 RBAC 放行；无 refresh。

| 项 | 内容 |
|----|------|
| **任务** | C2.1 Token 加 HMAC/JWT 签名，防篡改<br>C2.2 `FORCE_AUTH` 开关：单 Agent 模式也强制鉴权（补 week6 README P0 #2）<br>C2.3 refresh token 续期机制 |
| **验收** | 篡改 Token 被拒；FORCE_AUTH=true 下单 Agent 无 token 被拒；过期可 refresh |
| **对应角色** | 安全审查 |

### C3. M7 评估接 CI（持续评估）— 载体：**本地**

**现状：** `run_all_tests.py` 已实现，但需手动跑，无 CI 集成。

**决策（用户已定）：** CI 载体放**本地**——用本地脚本/cron 定时触发 `run_all_tests.py`，不做云端 CI（GitLab / GitHub Actions）。

| 项 | 内容 |
|----|------|
| **任务** | C3.1 建本地定时任务（Windows 计划任务 / cron）定时跑 `run_all_tests.py`<br>C3.2 每次本地 commit 后可选 pre-commit 钩子触发单测<br>C3.3 回归基线 7/10 作为门槛，不过则告警/阻断 |
| **验收** | 定时任务自动触发评估；回归基线结果落盘可查；失败有告警 |
| **对应角色** | 测试者/运维 |
| **依赖** | A1（真实回归基线可跑） |

### C4. M8 自动告警 + 采样

**现状：** `observability/` 有 trace/成本/审计，缺自动告警和采样。

| 项 | 内容 |
|----|------|
| **任务** | C4.1 provider 失败率阈值告警（如 >20% 告警）<br>C4.2 高 QPS 采样导出（生产流量采样，降存储）<br>C4.3 成本超预算告警（已有熔断，补告警） |
| **验收** | 模拟 provider 连续失败触发告警；采样率可配置 |
| **对应角色** | 运维/DBA |

**Phase C 完成标志：** demo 具备生产级限流/鉴权/CI/告警四件套。

## 四、Phase D：深化评估体系本身（最后，评估闭环）

> **依据：** 过程定位报告遗留待办（P1 #4/#5）+ AI 专家「评估结果反哺 Agent 行为」核心建议。

### D1. 逐工具结果质量规则（P1 #4）

**现状：** R3 有通用校验（非空/非错误），未按工具定制规则。

| 项 | 内容 |
|----|------|
| **任务** | D1.1 定义逐工具规则（如「query_orders 必须 ≥1 条」「search_knowledge_base rerank > 0.5」）<br>D1.2 不达标自动重试/降级（结合现有 needs_retry 机制） |
| **验收** | 各工具规则可配置；不达标触发重试路径 |
| **对应角色** | 开发者/测试者 |

### D2. 检索质量阈值（P1 #5）

**现状：** rerank 分全 <0.5 时仍喂 LLM，无「低质量检索」标记。

| 项 | 内容 |
|----|------|
| **任务** | D2.1 `rag/retriever.py` 加 rerank 分阈值检测<br>D2.2 全 <0.5 标记「低质量检索」，不喂 LLM（改走兜底/提示重新提问） |
| **验收** | 低质量检索被拦截；评估层能识别「检索失败」case |
| **对应角色** | 开发者/测试者 |

### D3. min_tools_called 是否强制 fail（坑 9 遗留）

**现状：** min_tools 不满足只降工具层分，不强制 case 判失败（completeness 高权重可能拉高整体）。

| 项 | 内容 |
|----|------|
| **任务** | D3.1 决策：min_tools 不满足时 case 是否直接判 fail<br>D3.2 若强制，在 `runner.py` 聚合处加硬校验 |
| **验收** | 决策明确并落地；测试断言同步 |
| **对应角色** | 评估标准设计 |

### D4. 评估闭环（AI 专家核心建议）

**现状：** 评估只出「打分报告」，低分场景无反馈回路。

| 项 | 内容 |
|----|------|
| **任务** | D4.1 低分 case 自动归档（JSONL 落盘，含完整轨迹）<br>D4.2 归档 case 可一键复现（重新跑并对比）<br>D4.3 反哺 prompt/参数（低分模式 → 建议 prompt 调整） |
| **验收** | 低分 case 归档可查；复现脚本跑通；prompt 调整建议输出 |
| **对应角色** | AI 专家/测试者 |

**Phase D 完成标志：** 评估从「打分」升级为「发现 → 复现 → 反哺」的闭环。

### D5. 轨迹层阈值与扣分标准细化（2026-08-09 新增，实测遗留 1）

**现状：** 真实回归基线轨迹层 0.56 < 0.6——eval_001 单 case 调 20+ 次工具（路径发散），`path_efficiency` 对「工具结果大但合理」的调用按冗余扣分，疑似过度惩罚；`retry_quality` 对 sandbox 自动重试（如 RAG 首次超时重试）也扣分，但那是环境预热非 Agent 错误。

| 项 | 内容 |
|----|------|
| **任务** | D5.1 复盘轨迹层低分 case（eval_001/004/005/010）的工具调用序列，区分「真冗余」与「合理多步推理」<br>D5.2 评估 `path_efficiency` 扣分是否过度（同工具多次调用是否都是冗余，还是 LLM 分步获取不同数据）<br>D5.3 评估 `retry_quality` 是否该区分「sandbox 自动重试（环境）」与「Agent 主动重试（策略）」<br>D5.4 若标准失真则调整扣分公式（属修评估标准，复用决策准则） |
| **验收** | 轨迹层低分有明确归因（真冗余 vs 合理多步）；扣分标准与实际 Agent 行为对齐 |
| **对应角色** | 评估标准设计/测试者 |
| **来源** | 9.8 节遗留观察「轨迹层 0.56 < 0.6」 |

### D6. 评估前清 L1 缓存（2026-08-09 新增，实测遗留 3）

**现状：** 真实评估时 LLM 调用命中 L1 精确缓存（同 prompt 复用旧结果），导致评估结果失真——改造前跑过的 case 命中「关键词启发式 era」的缓存，语义分显示旧值。验收时清缓存后 eval_002 语义才从缓存值变为真实 judge 分 1.00。

| 项 | 内容 |
|----|------|
| **任务** | D6.1 `run_all_tests.py` / `demo.eval.runner` 增加 `--no-cache` 或评估前自动 `clear()` L1 缓存<br>D6.2 CI 持续评估（C3）强制评估前清 L1，保证每次结果真实 |
| **验收** | 评估前自动清 L1；CI 评估结果不被旧缓存污染 |
| **对应角色** | 测试者/运维 |
| **来源** | 9.8 节遗留观察「L1 缓存影响评估」 |

## 五、阶段执行顺序总结

| 阶段 | 内容 | 优先级 | 主要依赖 |
|------|------|--------|---------|
| **Phase A** | 重问题修补（火山 429 / CSV 缺列 / 回测真实跑） | P0 | — |
| **Phase B** | 制造业主线（B1 结构化 → B2 约束求解 → B3 实时数据 → B4 人机协同） | P0 | A 完成 |
| **Phase C** | 生产化（C1 限流 → C2 JWT → C3 CI → C4 告警） | P1 | A1 完成 |

**依赖链**：
```
A1(真实回归) → C3(CI) 
B1(结构化排产) → B2(约束求解) → B4(人机协同)
B1(结构化排产) → D 系列（评估深化需要结构化输入）
```

**并行度建议**：Phase A 的 A2（数据补列）可独立先行；Phase B 的 B3（数据源抽象）与 B1/B2 无强依赖可并行；Phase D 的 D1/D2 有依赖（都动 retriever/graph）需串行。

### 坑 17：上下文压缩后孤儿 tool 消息 400（真实 bug，回测暴露）

**如何发现**：跑真实回测 bt_002 时，上下文压缩后 LLM 调用报 `BadRequestError: 400 "Messages with role 'tool' must be a response to a preceding message with 'tool_calls'"`，DeepSeek 和火山都失败。

**根因**：`compress_messages` 按位置切片保留最近 KEEP_RECENT 条，若切片起点落在 tool 消息上（它对应的 assistant tool_calls 消息被摘要化删掉），这条 tool 消息成为孤儿。OpenAI 协议要求 tool 消息必须紧跟含 tool_calls 的 assistant 消息，孤儿 tool 消息直接 400。

**根因归属**：【理解 Agent 过程】——压缩器改变了消息流结构，破坏了 OpenAI 消息顺序约束。过程定位文档坑 9「根因 B」只提到压缩改变末条 role 导致死循环，实际还有更直接的：孤儿 tool 消息 400。

**解决**：新增 `_sanitize_tool_messages()`——压缩后丢弃所有无前置 assistant(tool_calls) 的孤儿 tool 消息（其上下文已被摘要替代，留着只会 400）。TDD：先写 `test_compress_messages_drops_orphan_tool_messages`（断言压缩结果无孤儿 tool）→ FAIL → 实现 → PASS。

**动作对象**：**修代码**（真实 bug，生产风险）。

### 坑 18：上下文压缩不幂等，摘要无限叠加膨胀（真实 bug，评估暴露）

**如何发现**：跑真实三层评估时，日志持续打印 `[上下文压缩] 1 条历史消息 → 1 段摘要（5698 → 15137 字符）`，且字数不降反涨、L1 缓存重复命中——压缩在循环触发。

**根因**：`recent`（最近 KEEP_RECENT 条）里保留了大段 tool 结果（>MAX_CHARS），压缩只摘要化旧消息，总字数不变 → `should_compress` 仍 True → 每次 select_and_execute 前都压缩一次 → 摘要不断叠加，字数持续膨胀。

**根因归属**：【自身】（指标/算法设计缺陷）——压缩器没有幂等校验，压缩后不保证字数低于阈值。

**解决（两轮迭代）**：
- **第一版（收紧窗口）**：压缩后若超阈值，把 recent 窗口减半递归压缩。**实测死循环**——当 recent 里全是超大 tool 消息（keep 减到 1 仍有超大 tool 消息时），收紧窗口无法让字数降到阈值下，且重试只执行一次不递归，返回超阈值结果 → 下次 select 又触发压缩 → 死循环（eval_006 卡住暴露）。
- **最终版（截断收敛）**：压缩后仍超阈值时，调用 `_truncate_large_messages(compressed, MAX_CHARS)`——保留每条消息的 role/tool_call_id 结构（防破坏 OpenAI 消息顺序），超长 content 替换为占位引用「[结果已截断，详见历史摘要]」，保证总字数收敛到预算内。实测压缩后 67 字符 ≤ 阈值，不再触发。

TDD：`test_compress_messages_idempotent`（断言压缩后字数 ≤ MAX_CHARS）→ FAIL → 第一版实现 → 测试 PASS 但真实 eval_006 卡死 → 改为截断实现 → PASS + 真实收敛。

**动作对象**：**修代码**（真实 bug，会导致评估/回测变慢 + token 浪费 + 潜在死循环）。

## 九、低分根因：设计如此 vs 度量失真（评估体系核心方法论）

> 2026-08-09 追加。针对真实回归基线 4/10 未达标，从「现状是设计还是失真」和「如何判定是否调整」两个层面回答。

### 9.1 低分根因分解

| 现象 | 是设计还是失真 | 依据 |
|------|--------------|------|
| 非 RAG case 语义层 = 0.00 | **设计如此**（但有失真嫌疑） | 坑 5 决策：faithfulness 需要检索 context，无 context 时保守给 0。这是「无法评估即低分」的保守原则 |
| answer_relevancy 用关键词启发式兜底 | **设计如此**（明显失真） | 非 RAG case 的答案可能相关但没命中关键词 → 被低估。相关性本不需要检索 context，不该用关键词近似 |
| 工具/轨迹层波动（eval_001 两次 0.52→0.36） | **非设计，是 LLM 随机性** | 清了 L1 缓存后工具调用路径不同，DeepSeek 每次决策有随机性 |
| min_tools 不足只降工具层、不强制 fail | **设计如此**（坑 9 决策） | 当时明确接受「completeness 高权重可能拉高整体」的现状 |

### 9.2 对照行业需要（关键差异点）

行业 2026 的 LLM-as-Judge 实践（参考 `Agent评估行业实践与demo现状分析-2026-08-08.md`）里，**answer_relevancy 是独立于检索 context 的指标**——它评估「答案是否命中问题核心」，不需要 RAG 上下文就能打。

当前设计把 faithfulness（需 context）和 answer_relevancy（不需 context）**绑在一起**，无 context 时两者都退化 → 非 RAG 场景的语义质量被系统性低估。**这是设计偏离行业实践的明确点。**

### 9.3 三步决策法：如何判定是否需要调整

**第一步：先问「低分是 Agent 真差，还是标准度量失真？」**
- 人工打开 eval_001/002 的实际答案，看答案本身是否合理、相关、完整
- 如果答案实际是对的，只是没命中 must_contain 子串 / 没调够工具 → **标准失真**
- 如果答案真的一塌糊涂（答非所问）→ **Agent 问题**，标准没错

**第二步：分层看指标失真的程度**
- **语义层失真最明显**：非 RAG case 应独立评估 answer_relevancy，faithfulness 仅对有 context 的 case 计权（语义层按「是否有 context」自适应）
- **轨迹层**：eval_001 轨迹 0.40 是冗余调用扣分，需看是不是过度惩罚（调了合理工具但工具结果较大也算冗余？）
- **工具层**：相对可靠（F1 是客观的），但要确认 expected_tools 是否合理

**第三步：再决定动哪个对象（复用过程定位报告的决策准则）**
- 标准度量失真 → **修评估标准**（调整语义层自适应加权、answer_relevancy 独立评估）
- Agent 真差 → **修代码/prompt**（不改标准迁就）
- 数据定义脱节 → **改数据**

### 9.4 改造建议（给后续 Phase 参考）

**当前首要动作不是急着改指标，而是先做「人工对照」**——拿 eval_001/002 的实际答案，判断到底是标准失真还是 Agent 问题。如果确认是标准失真，优先调整两处：

1. **语义层自适应**：无 context 的 case，faithfulness 不参与（或权重归零），answer_relevancy 用真实 judge 而非关键词兜底 → 语义分不再系统性为 0
2. **回归基线分层化**：不只用「7/10 综合通过」一个数，而是按层设基线（工具 ≥0.7 / 轨迹 ≥0.6 / 语义 ≥0.5），避免单层失真的掩盖

**核心判断**：设计如此 ≠ 不需要调整。设计如此的是「保守给 0」的原则，但偏离行业实践的是「相关性依赖检索 context」的耦合，后者值得调整。

### 9.5 行业如何逐一解决这些指标问题

| 指标问题 | demo 现状 | 行业解法（2026） | 说明 |
|---------|----------|----------------|------|
| answer_relevancy 依赖 context | 无 context 时关键词启发式 | **独立评估**：DeepEval/LangSmith 的 answer_relevancy 都是独立的，与 RAG context 无关，单独用 LLM 打「答案是否覆盖问题意图」分 | 行业不把 relevancy 和 faithfulness 绑一起 |
| faithfulness 无 context 给 0 | 保守给 0 | **按数据可用性自适应**：有 context 才评 faithfulness；无 context 时该项不计入总分（或权重归 0），而非给 0 拖累整体 | 「无法评估」≠「得 0 分」，行业区分「未评估」和「评估为差」 |
| 单一综合基线掩盖单层失真 | 7/10 综合 | **分层基线 + 分层看板**：工具/轨迹/语义各设阈值，任何一层不达标即告警（Langfuse/Phoenix 的 eval 面板都是分层展示） | 综合分会被高权重层掩盖低分层的退化 |
| LLM 随机性导致的波动 | 单次跑 | **多次采样取均值 / 温度 0**：评估用 temperature=0 或跑 N 次取平均，降随机性（Arize/Promptfoo 都支持） | judge 打分别用真实 LLM 随机性污染 |
| 评估结果反哺 | 只出报告 | **评估闭环**：低分 case 自动归档 → 复现 → 反哺 prompt/参数（Agent-as-a-Judge，ICML 2025） | 评估的价值在闭环，不在打分本身 |

**追问：那你为什么这么设计？**

> 答：这是「无法评估即低分」的保守原则——faithfulness 没有参照物时不能瞎给分。但我对照了行业 2026 实践发现一个偏差：answer_relevancy 在行业里是独立于 context 的指标，我把它和 faithfulness 绑在一起，无 context 时两个都退化。所以这是设计偏离行业实践的点，值得调整，不是「设计如此就接受」。

#### 坑 21：压缩器 `old` 为空时跳过截断，RAG case 上下文持续膨胀（真实 bug，评估暴露）

#### 坑 22：eval_006 RAG case 死循环——纯文本轮 iteration 不递增（真实 bug，评估暴露）

**如何发现**：坑 21 修复后重跑全量评估，eval_006（延期记录 RAG）仍卡死 14+ 分钟，日志压缩循环 179 次。

**完整定位过程（systematic-debugging + codegraph 通读）**：

**Step 1 · 观察症状**：日志序列 `压缩 → 摘要（5747→7875）→ L1缓存命中(LLM调用) → 截断 → 摘要（5747→8018）→ L1缓存命中 → ...`，压缩 179 次，摘要字数每次 +143 单调递增。

**Step 2 · 排除压缩器**：单独测 `_truncate_large_messages` 收敛正常（43042→3049），静态模拟 5 次压缩都收敛到 5056 ≤ 阈值。压缩器本身不无限循环。

**Step 3 · 排除图 iteration 安全阀（第一次误判）**：最小复现（mock LLM 返回固定 tool_call）LLM 调用 6 次，iteration 到 5 强制结束。**误以为图安全阀正常**。

**Step 4 · 决定性证据（debug stream 打节点序列）**：
```
select_and_execute iteration:1 → evaluate iteration:1
select_and_execute iteration:2 → evaluate iteration:2
select_and_execute iteration:2 → evaluate iteration:2   ← iteration 卡死在 2！
select_and_execute iteration:2 → evaluate iteration:2
... 消息数 7→14→9→14 震荡（压缩截断回落 → LLM 又加）
```

**iteration 卡死在 2，select_and_execute 反复执行**。

**Step 5 · 根因（读代码第 59-61 行）**：
```python
# select_and_execute 里
if not msg.tool_calls:
    state["messages"].append({"role": "assistant", "content": msg.content or ""})
    return state        # ← 纯文本轮直接 return，不执行 iteration += 1！
...
state["iteration"] += 1   # ← 只在工具调用分支执行
```

**纯文本轮（LLM 直接返回文本、不调工具）时 `iteration` 不递增**。配合：
1. iteration=2 时，LLM 命中 L1 缓存返回**纯文本**（RAG 结果被压缩截断 → LLM 数据不全 → 说不全直接回文本）
2. `evaluate_results` 数据不足 → `needs_more=True`
3. `should_continue`：`needs_more and iteration<4`（2<4 True）→ select
4. select 开头压缩 → LLM 又命中缓存返回纯文本 → iteration 仍 2 → 死循环

**根因归属**：【理解 Agent 过程】（核心）——**这是坑 11 的变体**。坑 11 修的是「数据充足时清 needs_more 残留」；这里是「纯文本轮 iteration 不递增 + needs_more 永真」的组合。坑 11 时用 `_disable_compression` 隔离了压缩干扰，没暴露这个路径；真实 RAG 场景（大 tool 结果 + 压缩截断 + L1 缓存命中）把「纯文本轮不递增」放大成死循环。

**修正计划（待确认，用户决策后执行）**：
1. **纯文本轮也递增 iteration**（首选）：`select_and_execute` 里 `if not msg.tool_calls` 分支也 `state["iteration"] += 1`，保证纯文本轮计入安全阀
2. **needs_more 路径限次**：`should_continue` 里 `needs_more` 最多触发 N 次（如 iteration≥3 强制 generate）
3. **evaluate_results 循环检测**：同一 tool 结果重复 ≥N 次 → 清 needs_more + 强制 generate
4. **压缩截断时提示 LLM 停止检索**：`_truncate_large_messages` 截断后，让 LLM 基于已有数据作答而非重新检索

**动作对象**：待修代码（本轮未修，用户确认修正方向）
