> **日期**：2026-08-28 · **状态**：待评审 · **作者**：Agent 开发工程师（codegraph 全链路核验）
> **关联**：[rq-排程排产需求.md §3.15](../01-requirements/rq-排程排产需求.md) · [2026-08-27-自动排产调度器.md](../04-plans/2026-08-27-自动排产调度器.md) · [2026-08-28-前道任务生成-design.md](./2026-08-28-前道任务生成-design.md)

## 0. 需求（用户原话定稿）

**完整排程排产自动化闭环**：

```
下单 → 订单待排队 → 贪心算法自动生成批次 → 批次自动审批 → 批次排版（锁定前道人员）
→ 批次上机（锁定设备、释放前道人员）→ 批次打印完成 → 释放设备 → 订单完成
```

**判定标准**：全链路无人值守，同一订单**只被打印一次**，设备/人员占用释放正确，订单状态贯穿流转。

## 2. 核心架构：订单状态机驱动闭环

### 2.1 订单状态机（缺口 C 定稿）

```
待排队 ──persist 生成批次──▶ 已审核（锁定，防重复排）──批次上机──▶ 打印中 ──批次全部完成──▶ 完成
   ▲                              │
   └──版本驳回（回退）──────────┘
```

| 流转 | 触发 | 位置 | 附注 |
|------|------|------|------|
| 待排队→已审核 | **persist 生成批次时**（同事务） | `solver.persist` | 排产即锁定，早于审批 → 天然防重复排 |
| 已审核→打印中 | 批次「待上机→打印中」 | `engine.advance_batches` step3 | 拆批时**任一批**上机即打印中 |
| 打印中→完成 | 批次「静置中→完成」 | `engine.advance_batches` step2 | 拆批须**全部批次**完成（防提前完成） |
| 已审核→待排队 | 版本**驳回** | `approve_schedule` | 版本驳回 → 订单回待排队可重排 |

> **为什么 persist 就锁定而非审批通过才锁定**：FIFO 保留 top20 待审，若审批通过才锁定，版本 1 的订单在版本 2 重排时仍是待排队 → 被重复包含。persist 锁定才能从源头杜绝重复排。

### 2.2 状态写入

`orders.status` 更新 + `state_change_log`（`states.log_state_change`）同事务写：
- persist（source=solver）
- advance_batches（source=simulator）
- approve_schedule 驳回（source=agent）

新增 `ORDER_TRANSITIONS`（对齐 `states.py` 风格），非法流转抛错。

## 3. 五缺口设计

### A. 前道任务生成（机器空闲根因）

见 [2026-08-28-前道任务生成-design.md](./2026-08-28-前道任务生成-design.md)，要点不变：
- `persist` 同事务每批次生成 1 条 `preprocess_tasks`
- `man_hours = 件数÷(人×件人效)+方案审核分摊`；`end_time = 批次 start_time`（C9）
- 无可行解批次（start_time=None）跳过

### B. 前道人员锁定/释放（v1 产能级）

| 流程点 | 语义 | 实现 |
|--------|------|------|
| persist 生成前道任务 | **锁定** `assigned_workers` 人·产能 | 人时计入 `preprocess_load().remaining_man_hours` |
| 批次 前道→待上机 | **释放**该任务占用 | `advance_preprocess` 推进后任务脱离「前道」批次 |

- 池占用率由 `preprocess_load().utilization` 观测（已实现）。
- `personnel` 表不改；**个体级绑定（具体人 ↔ 批次）属 P2-4**，v1 用产能级表示。

### C. 订单状态流转

见 §2.1。关键实现：
- `load_snapshot` 选单条件从 `status != '完成'` **改为 `status='待排队'`**（`snapshot.py:74`）——已审核/打印中/完成的订单不再进求解。
- `persist` 事务内 `UPDATE orders SET status='已审核' WHERE id IN (该版本全部批次 order_ids 去重)`。
- `approve_schedule` 驳回：同版本批次关联订单 `已审核→待排队`（回退可重排）。
- `engine.advance_batches` step2 完成时：拆批订单**全部批次完成**才置完成。

### D. 排产幂等（防重复打印，核心）

**问题**：现状每轮 `run_scheduling` 全量重排所有未完成订单 → 版本 1..20 含相同订单 → FIFO 逐个自动通过 → **同一订单被多版本重复打印**。

**方案**（与 C 联动，双保险）：
1. **源头**：`load_snapshot` 只取 `status='待排队'` 订单；persist 锁定为已审核 → 后续版本自然不含它。
2. **兜底**：`solve()` 入口再校验一次——若快照订单已在任何**非驳回**版本的批次中出现（`JSON_CONTAINS(batches.order_ids)`），跳过不排（防 agent 手动触发 / 并发竞态）。

**FIFO 修正**：persist 锁定后每轮只排**新增**订单，版本间订单**互不重叠** → FIFO 自动通过早期版本是安全的（各版推进各自订单）。`AUTO_APPROVE_TOP_N` **定稿为 5**（2026-08-28 用户确认 3~5）：保留最近 5 版待审、更早自动通过，生产约 15 模拟小时内启动，保留少量人工干预窗口。

### E. 审批门禁（模拟器只推进通过版本）

`advance_batches` step3 与 `advance_preprocess` 的 SQL 追加 `AND b.approval_status='通过'`：
- **前道→待上机**（`engine.py:127-130`）：`WHERE b.status='前道' AND b.approval_status='通过' AND pt.end_time<=%s`
- **待上机→打印中**（`engine.py:75-77`）：`WHERE b.status='待上机' AND b.approval_status='通过' AND start_time<=%s AND machine_id IN (...)`
- 打印中→静置→完成不受影响（已上机批次必已通过）；设备故障回退（打印中→待上机）后 approval_status 仍通过 → 可重新上机。

## 4. 完整闭环时序（无人值守）

```
tick0  seed：40 订单 → 待排队；7 设备空闲
tickN  AutoScheduler._loop 累计 interval_ticks
   → _auto_schedule：run_scheduling
       ├ load_snapshot：只取待排队订单（D/C）
       ├ solve：贪心装箱 + CP-SAT 分配 machine_id/start_time
       └ persist：写 schedule_versions + batches + preprocess_tasks（A）
                 + 订单 待排队→已审核（C）
   → _fifo_approve：早于 topN 的版本自动通过（approval_status→通过）
tick+1  engine.advance_tick
   ├ advance_preprocess：通过版本批次 前道→待上机（E+B：锁→释放人时）
   ├ advance_batches step3：通过版本批次 待上机→打印中（E：锁设备）→ 订单→打印中
   ├ advance_batches step1/2：打印中→静置中→完成（释放设备）→ 订单→完成
   └ fire_events：插单/故障 → request_rerun 即时重排
订单完成 → KPI 准交率正确统计（order→完成 日志补齐）
```

**同一订单只出现在一个版本、只打印一次**（D）+ **未审批版本永不推进**（E）+ **状态贯穿**（C）→ 全链路无人值守闭环成立。

| 层 | 验证 |
|----|------|
| 单测（persist） | 生成后：preprocess_tasks 行数=有解批次行数；订单→已审核；重复 persist 不重复含单 |
