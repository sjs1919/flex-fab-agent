## 0. 需求（用户原话定稿）

**完整排程排产自动化闭环**：

```
下单 → 订单待排队 → 贪心算法自动生成批次 → 批次自动审批 → 批次排版（锁定前道人员）
→ 批次上机（锁定设备、释放前道人员）→ 批次打印完成 → 释放设备 → 订单完成
```

**判定标准**：全链路无人值守，同一订单**只被打印一次**，设备/人员占用释放正确，订单状态贯穿流转。

## 2. 核心架构：订单状态机驱动闭环

### 2.1 订单状态机（缺口 C 定稿）

```
待排队 ──persist 生成批次──▶ 已审核（锁定，防重复排）──批次上机──▶ 打印中 ──通过且有解批次全部完成──▶ 完成
   ▲                              │
   └──版本驳回（回退）──────────┘
```

| 流转 | 触发 | 位置 | 附注 |
|------|------|------|------|
| 待排队→已审核 | **persist 生成批次时**（同事务） | `solver.persist` | 排产即锁定，早于审批 → 天然防重复排；**工艺组级部分成功（2026-08-28 确认 u-d-1）：`solve_scheduling` 任一组不可行（`model.py:260-263`）仅剔除该组批次（不入 result），其他组照常——建版只含有解批次、只锁定有解批次订单，不可行组订单保持待排队下轮重排**；**整版全不可行（`result['batches']` 为空）→ 不建版本、相关订单全部保持待排队**（防刷屏，与 D-3 一致）；建版即锁定全部相关（有解批次）订单 |
| 已审核→打印中 | 批次「待上机→打印中」 | `engine.advance_batches` step3 | 拆批时**任一批**上机即打印中 |
| 打印中→完成 | 批次「静置中→完成」 | `engine.advance_batches` step2 | 拆批须**订单所属最新版本的全部「通过」且 `start_time` 非空批次**完成（防提前完成）；驳回残留/无可行解批次不计入；**陈旧版本批次不影响完成判定**（升级/重跑 v53 陈旧前道批次与新版并存，跨全库判定会永久卡死订单） |
| 已审核→待排队 | 版本**驳回** | `approve_schedule` | 版本驳回 → 订单回待排队可重排 |

> **为什么 persist 就锁定而非审批通过才锁定**：FIFO 保留最近 topN（现状代码 top20，定稿 5）待审，若审批通过才锁定，版本 1 的订单在版本 2 重排时仍是待排队 → 被重复包含。persist 锁定才能从源头杜绝重复排。

### 2.2 状态写入

`orders.status` 更新 + `state_change_log`（`states.log_state_change`）同事务写：
- persist（source=solver）
- advance_batches（source=simulator）
- approve_schedule 驳回（source=agent）

**版本建版 sim 时刻锚点**（FIFO 超龄兜底计龄用，D-2）：**拍板唯一通道**——persist 事务内读 `sim_clock.current_sim_time` 快照，写 `state_change_log` `entity_type='version'`/`field='created'`/`source='solver'`（`schema.sql:236` source 枚举已含 solver，通道已存在）；**不碰 `params_json`/`result_json`**（避免新增键污染排产快照回读，原「复用 JSON 字段或 state_change_log」二选一收敛为一）。**缺失回落定义**：① persist 读 `sim_clock` 无行（`clock.py` 未初始化抛 `RuntimeError`）时**跳过写锚点**（不抛错、不回落 wall-clock——wall-clock 与 sim 时间无映射）；② `_fifo_approve` 对**无锚点版本**（存量/测试直插版本）回落：**视为已超龄，最迟下一轮 FIFO 通过**（保证不因缺锚点而停滞）。`schedule_versions` 现有列仅 `created_at=NOW()`（`solver.py:110`）且 `sim_clock` 无 `tick_count`，**新增 sim 时刻不增列，schema 不改**。

新增 `ORDER_TRANSITIONS`（对齐 `states.py` 风格），非法流转抛错。**幂等约定**：`('打印中','打印中')`、`('完成','完成')` 定义为 **no-op**（不抛错、不重插 log）——同一订单多批**同 tick** 陆续上机/完成时，第二次写不触发 ORDER_TRANSITIONS 异常，否则会使整个 tick 事务回滚（对齐 `states.py:34-40`）。engine step2 的订单完成 UPDATE 追加 `AND status='打印中'`，受影响行数 0 即跳过（幂等）。

## 3. 五缺口设计

### A. 前道任务生成（机器空闲根因）

见 [2026-08-28-前道任务生成-design.md](./2026-08-28-前道任务生成-design.md)，要点不变（**唯一例外：`assessment.py` 观测口径改动见 §3.B**——design.md:49「preprocess_load 负载评估逻辑本次不改」、:98「assessment.py 不改」、:113「自动审批 FIFO 很快通过」三处与定稿矛盾，本轮起以本定稿 §3.B/§3.D 为准，design.md 相应位置已加 supersede 标注）：
- `persist` 同事务每批次生成 1 条 `preprocess_tasks`
- `man_hours = 件数÷(人×件人效)+方案审核分摊`；**方案审核分摊钉死：persist 在版本批次循环内先算 `share = round(0.5/N, 4)`（N=该版本批次总数）再写入每批次 `man_hours`**（`assessment.py:129-134 preprocess_task_hours` 现无 N 参数、把 `plan_review_hours` 平加为每任务 0.5，须增 `n_batches` 参数或改收 share 实参，否则「每任务 0.5h 多加」在 SUM 口径下未真修复）；`end_time = 批次 start_time`（C9）
- **工艺组级部分成功（见 §3.D，2026-08-28 确认 u-d-1）**：不可行工艺组批次被 `solve_scheduling` 剔除（不入 result）→ 无 preprocess 产出；有解批次正常生成前道任务；**整版全不可行（`result['batches']` 为空）→ 不建版本、无 preprocess 产出**（防刷屏）

### B. 前道人员锁定/释放（v1 产能级）

| 流程点 | 语义 | 实现 |
|--------|------|------|
| persist 生成前道任务 | **生成落库防重复排**（观测**随审批通过后计入**，待审窗口不计池占用） | 写 `preprocess_tasks` 行；`preprocess_load().remaining_man_hours` 仅统计**未完成且已通过**的前道任务 |
| 批次 前道→待上机 | **释放**该任务占用 | `advance_preprocess` 推进后任务脱离「前道」批次 → `remaining_man_hours` 下降 |

- 池占用率由 `preprocess_load().utilization` 观测（已实现）。
- **观测口径对齐写入口径**：`preprocess_load`（`assessment.py`）改读落库 `SUM(man_hours)`（`man_hours` 列已存在，含方案审核分摊），**不再**用 `_per_part_eff('mix')=12` 从 part_count 重算——原重算口径按统一 mix=12 使 **SLA/MJS（真值 15）负载偏高约 25%、SLM（真值 6）负载低估约 2 倍**，且旧重算口径方案审核分摊按**每任务 0.5h**（非 0.5/N 平摊）多加——**该问题随 persist 落库按 `share=round(0.5/N,4)` 写入已根治**（见 §3.A），SUM 口径正确性不再依赖函数默认值；改读落库后「人时计入 `remaining_man_hours`」成立。
- **SUM 口径须保留「未完成」过滤**：`SUM(man_hours)` 仅统计未完成前道任务——联 `batches` 过滤 **`status='前道'` 且 `approval_status='通过'`**，或 `pt.end_time > now` 双条件（二选一，建议前者）；否则前道→待上机后任务永久计入、占用率单调上涨，「批次前道→待上机即释放人时」永不成立。
- **「锁定」表述修正**：persist 生成即落库仅防重复排（排产快照），**人时观测随审批通过后计入**——待审窗口（最长 `FIFO_AGE_TIMEOUT=24h`）内通过过滤后池占用为 0 属预期「假空闲」，与上表「生成落库防重复排、观测随审批通过后计入」一致。
- **下游口径闭合（CTP/负载评估/KPI 前道段）**：待审窗口「假空闲」（池占用=0、`eta_clear=None`→`compute_ctp_from_db` 回落 `_now()` 报乐观 CTP、负载评估/KPI 前道占用报 0%）为改口径后的**已知乐观偏差**。**拍板：CTP/负载评估/KPI 前道段统一沿用「未完成+已通过」新口径，并在输出标注乐观偏差、影响时长上限 = `FIFO_AGE_TIMEOUT`（24 模拟小时）**——偏差有界且随审批通过自动消除；**不另设 compute_ctp 第二套未过滤口径**（避免双口径不一致）。**u-d-2（CTP 保守下界）已评估未启用**（2026-08-28，见 §7）：维持乐观口径 + 偏差≤24h 标注；如业务要求保守下界，再启用 compute_ctp 前道队列「含待审 SUM」作下界。
- `personnel` 表不改；**个体级绑定（具体人 ↔ 批次）属 P2-4**，v1 用产能级表示。

### C. 订单状态流转

见 §2.1。关键实现：
- `load_snapshot` 选单条件从 `status != '完成'` **改为 `status='待排队'`**（`snapshot.py:74`）——已审核/打印中/完成的订单不再进求解。
- `persist` 事务内锁定**仅覆盖有解批次订单**：从**内存** `result['batches']`（`start_time` 非空，见 §3.A）收集订单集合——`batches` 表**无 `order_id`/`version_id` 列**，实为 `order_ids VARCHAR(512)` JSON 文本 + `schedule_version_id`（`schema.sql:145-146`），**不写 SELECT 关联 SQL 字面（照抄必报 Unknown column）**——用一条条件 UPDATE **原子锁定**：`UPDATE orders SET status='已审核' WHERE id IN (<该版订单集合>) AND status='待排队'`；**受影响行数 < 预期订单集 → 整个事务 ROLLBACK**（不做部分剔除——剔除需删同事务已插入的批次/前道行，会产生「版本只含部分订单」不一致态；整版回滚后败者轮下轮重排补齐）。**锁定 UPDATE 置于事务开头**（先订单行锁再插批次，统一与 engine/approve 锁序，防死锁窗口）。**不经过 `assert_transition`/`ORDER_TRANSITIONS` 守卫**（避免已审核→已审核抛 ValueError 使整事务回滚，直接条件 UPDATE 即可）。——**工艺组级部分成功（2026-08-28 确认 u-d-1）：不可行组批次被 `solve_scheduling` 剔除，有解批次订单锁定为已审核，不可行组订单不锁定、保持 `待排队` 下轮重排**；**整版全不可行（`result['batches']` 为空）→ 不建版本、全部相关订单保持 `待排队`**（防刷屏）。
- `approve_schedule` 并发竞态（通过/驳回双写）：现 `SELECT version.status` 无 `FOR UPDATE` 也无受影响行数校验（`scheduler_tools.py:119-126`），FIFO「通过」+人工「驳回」并发时可能产生「**订单待排队 + 版本已审核**」撕裂态 → 对版本行加 `SELECT ... FOR UPDATE` 串行化通过/驳回，或条件 `UPDATE schedule_versions SET status=%s WHERE id=%s AND status='待审核'` 校验受影响行数=1；**并发驳回回退（已审核→待排队）只在拿锁后执行**。
- `approve_schedule` 驳回：同版本批次关联订单 `已审核→待排队`（回退可重排），UPDATE 带 **`AND status='已审核'` 守卫**（防并发下把已上机/已完成订单拉回待排队致重复打印）。
- `engine.advance_batches` step2 完成时：拆批订单**所属最新版本**的全部**「通过」且 `start_time` 非空批次**完成才置完成（驳回残留/无可行解批次不计入；**陈旧版本批次不计入**，防升级/重跑场景永久卡死）；**归属判定钉死实现**：`order_ids` 为 `VARCHAR(512)` JSON 文本（`schema.sql:146`），**禁 `LIKE '%ORD001%'` 前缀假匹配（误配 ORD0010）**，用 `JSON_CONTAINS(CAST(order_ids AS JSON), JSON_QUOTE(%s), '$')` 或 **Python json_list 聚合判定（engine.py 现有做法）**；订单写用条件 `UPDATE ... AND status='打印中'` 幂等（见 §2.2）。

### D. 排产幂等（防重复打印，核心）

**问题**：现状每轮 `run_scheduling` 全量重排所有未完成订单 → 版本 1..20 含相同订单 → FIFO 逐个自动通过 → **同一订单被多版本重复打印**。

**方案**（与 C 联动，双保险）：
1. **源头**：`load_snapshot` 只取 `status='待排队'` 订单；**`snapshot.py` 的 parts 查询同步按待排队订单过滤**（`WHERE order_id IN (SELECT id FROM orders WHERE status='待排队')`）——否则已审核订单零件仍被 `pack_parts`（`model.py:41-83`）打包进后续版本（0 单快照也会因 parts 全量重排而复含已锁订单）；persist 锁定为已审核 → 后续版本自然不含它。
2. **兜底**：`solve()` 是**纯函数无 DB**（`solver.py:131-188`），兜底校验**移入 persist 事务**（与订单锁定同事务**开头**原子执行）：从**内存** `result['batches']` 收集有解批次订单集合，条件 `UPDATE orders SET status='已审核' WHERE id IN (<该版订单集合>) AND status='待排队'` **原子锁定**，**受影响行数 < 预期订单集 → 整个事务 ROLLBACK（不做部分剔除，防「版本只含部分订单」不一致态）**（防 agent 手动触发 / 并发竞态）。**锁定 UPDATE 置于事务开头**（先订单行锁再插批次），**不经过 `assert_transition`/`ORDER_TRANSITIONS` 守卫**；`WHERE status='待排队'` 行锁串行化并发；agent 路径 `run_scheduling`（`scheduler_tools.py:36-55`）不持 `AutoScheduler._lock`（`auto_scheduler.py:94-104`），**统一入口**：所有写路径（模拟器 loop 与 agent 工具）共用同一 persist 事务入口，不直接调裸 `solve()`。
3. **空版本/全无解跳过（防刷屏兜底）**：persist 跳过建版本的条件为「`result['batches']` 为空」——`solve_scheduling` **按工艺组独立求解，某组不可行（`model.py:260-263`）仅剔除该组批次（不入 result），其他组照常**（**工艺组级部分成功**，2026-08-28 确认 u-d-1）；**全部组不可行 → `result['batches']` 为空 → 跳过建版本**（防「整版无可行解」每轮重排重复建版刷屏、FIFO 逐个自动通过空版、`load_latest_batches` 长期展示空排产表）；`_infeasible_schedule`（`model.py:564-574`）仅在全不可行兜底时使用。**meta 记录 `infeasible_groups`/`infeasible_order_ids`**，供 `run_scheduling` 输出无解订单清单（NFR-01 求解可行性）。废弃 `solver.py:109-114` 无条件建版本行。**返回契约**：空跳过时 persist 返回 **None/0（不含版本号）**，`run_scheduling` 空池/全无解时返回「**无待排订单/全无解，未建版本**」文案（不含版本号）并输出冲突订单（NFR-01 求解可行性），CLI 不打印版本号、`auto_scheduler._last_version` 不被污染（`auto_scheduler.py:112-114` 正则 `版本 (\d+)` 不匹配即不更新）。

**FIFO 修正（重定语义）**：persist 锁定后每轮只排**新增**订单，版本间订单**互不重叠** → FIFO 自动通过早期版本是安全的（各版推进各自订单）。因「空版本/全无解跳过」不再产生空版，**弃用「按全部待审版本含空版计数」改法**（部署专家 6 版×3 tick=18h 的推算仅在该改法下成立），改**双机制**：
- ① 常规：待审版本按序保留最近 `AUTO_APPROVE_TOP_N`（**定稿 5**，2026-08-28 用户确认 3~5）版，早于 topN 自动通过；
- ② **超龄兜底**：最早待审版本（首版）龄期 ≥ `FIFO_AGE_TIMEOUT`（env `FIFO_AGE_TIMEOUT`，默认 24 模拟小时，见 §5 `demo/config.py`）即自动通过——解决「v1 锁定全部订单后无新单 → 无 ≥6 个有批次版本 → 永不启动」的停滞（`auto_scheduler.py:124-132` 现只统计 EXISTS batches 版本，按 `order_arrival_rate=2 单/天` 约 60 模拟小时才启动，原「约 15h」不成立）。
- **龄期计算须有 sim 时间锚点**：`schedule_versions` 现有列仅 `created_at=NOW()`（`solver.py:110`）、`sim_clock` 无 `tick_count`，**不得用 wall-clock `created_at` 或 `MIN(batches.start_time)` 作锚点**（求解器基准日为最早交期前 7 天，`start_time` 可早于 persist；wall-clock 与 sim 时间无映射）。改：**persist 事务内读 `sim_clock.current_sim_time` 快照，写 `state_change_log` `entity_type='version'`/`field='created'`/`source='solver'`（唯一通道，不碰 params/result JSON，见 §2.2）**；`_fifo_approve` 按「**当前 sim 时间 − 建版 sim 时间**」计龄，**无锚点版本回落视为已超龄最迟下轮通过**；persist 读 `sim_clock` 无行时**跳过写锚点不抛错**；**超龄计龄追加非负校验**（建版时刻晚于当前 sim 时间不计龄，防御 seed 未清/时钟回拨，见 §5 seed.reset 联动清理）。**schema 不改**。

启动验收口径见 §4/§6（seed 20 单无插单，最早待审版本最迟 建版 sim 时刻 + `FIFO_AGE_TIMEOUT` 内通过，含采样粒度容差）。

### E. 审批门禁（模拟器只推进通过版本）

`advance_batches` step3 与 `advance_preprocess` 的 SQL 追加 `AND b.approval_status='通过'`：
- **前道→待上机**（`engine.py:127-130`）：`WHERE b.status='前道' AND b.approval_status='通过' AND pt.end_time<=%s`
- **待上机→打印中**（`engine.py:75-77`）：`WHERE b.status='待上机' AND b.approval_status='通过' AND start_time<=%s AND machine_id IN (...)`
- 打印中→静置→完成不受影响（已上机批次必已通过）；设备故障回退（打印中→待上机）后 approval_status 仍通过 → 可重新上机。

**前道任务残留**：驳回/未通过版本 `preprocess_tasks` 永不被推进（E 门禁拦截），若按 `end_time>now` 单独计数会持续计入池占用（`assessment.py:241-242`）→ 占用率虚高。轻改优先：`preprocess_load` 联 `batches` 过滤 **`status='前道'` 且 `approval_status='通过'`**（**未完成 + 已通过**双条件，见 §3.B 观测口径），驳回后池占用自然回落。
**驳回回退守卫**：`approve_schedule` 驳回回退 UPDATE 带 `AND status='已审核'`（见 §3.C），防并发下把已上机/已完成订单拉回待排队致重复打印。

## 4. 完整闭环时序（无人值守）

```
tick0  seed：20 订单 → 待排队；7 设备空闲（验证不可行路径时加压到 40）
tickN  AutoScheduler._loop 累计 interval_ticks
   → _auto_schedule：run_scheduling
       ├ load_snapshot：只取待排队订单 + parts 按待排队过滤（D/C）
       ├ solve：贪心装箱 + CP-SAT 分配 machine_id/start_time
       └ persist：写 schedule_versions + batches + preprocess_tasks（A，不可行组无批次无前道）
                 + 事务开头条件 UPDATE 原子锁定 待排队→已审核（工艺组级部分成功：仅锁定有解批次订单，不可行组订单保持待排队下轮重排，受影响行数不足即 ROLLBACK，C）
                 + result['batches'] 为空（全不可行）跳过建版本（返回 None/0，D）
                 + 读 sim_clock.current_sim_time 写建版 sim 时刻快照（state_change_log 唯一通道，FIFO 计龄锚点，见 §2.2）
   → run_scheduling：空池/全无解时返回「无待排订单/全无解，未建版本」（不含版本号），CLI/_last_version 不被污染（D）
   → _fifo_approve：早于 topN 的版本自动通过 + 最早待审版本「当前 sim 时间 − 建版 sim 时间」≥ FIFO_AGE_TIMEOUT 兜底通过（approval_status→通过）；无锚点版本视为已超龄最迟下轮通过
tick+1  engine.advance_tick
   ├ advance_preprocess：通过版本批次 前道→待上机（E+B：锁→释放人时）
   ├ advance_batches step3：通过版本批次 待上机→打印中（E：锁设备）→ 订单→打印中
   ├ advance_batches step1/2：打印中→静置中→完成（释放设备）→ 订单→完成
   └ fire_events：插单/故障 → request_rerun 即时重排
订单完成 → KPI 准交率正确统计（order→完成 日志补齐）
```

**启动验收口径（可实测）**：seed 20 单、无插单 → 最早待审版本 `approval_status='通过'` 的 **sim 时刻 ≤ 建版 sim 时刻 + `FIFO_AGE_TIMEOUT` + 2×`interval_ticks`×1h**（**T=建版 sim 时刻**，即 persist 事务内 `sim_clock.current_sim_time` 快照；+2×`interval_ticks`×1h 容忍 `_loop` 采样粒度——tick 逐点采样下首版通过最迟落在超龄判定后的下一采样点）；常规有新增单场景 → 早于 topN=5 的版本逐个自动通过。e2e 按此断言。

**同一订单只出现在一个版本、只打印一次**（D）+ **未审批版本永不推进**（E）+ **状态贯穿**（C）→ 全链路无人值守闭环成立。
