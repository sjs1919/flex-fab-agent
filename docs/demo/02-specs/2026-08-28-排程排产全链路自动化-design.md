# 排程排产全链路自动化 · 设计规格

> **日期**：2026-08-28 · **状态**：待评审 · **关联**：[rq-排程排产需求.md §3.15](../01-requirements/rq-排程排产需求.md)、[2026-08-28-前道任务生成-design.md](./2026-08-28-前道任务生成-design.md)（缺口 A 细化）

## Context

用户要求**完整排程排产环节自动化**：

```
下单 → 订单待排队 → 贪心算法自动生成批次 → 批次自动审批 → 批次排版（锁定前道人员）
→ 批次上机（锁定设备、释放前道人员）→ 批次打印完成 → 释放设备
```

现状：环节 1、2、3、6、7 已自动闭环；**环节 4 缺失（前道任务不生成）**；环节 4/5 的「锁定/释放前道人员」无资源语义；**环节终点「订单完成」缺失（订单 status 永远卡「待排队」）**。

|---|------|------|----------|
| 1 | 下单 → 待排队 | ✅ | `seed.py:170-189`、`events.py:119-122` |
| 2 | 贪心生成批次 | ✅ | `model.py:41 pack_parts` + `solver.py:131 solve`；`auto_scheduler.py:106` |
| 3 | 批次自动审批 | ✅ | `auto_scheduler.py:118-135 _fifo_approve` |

| — | 订单状态流转（终点） | ❌ | 全库仅 `engine.py:306` 一处 `UPDATE orders`（改 due_date），status 从不流转 |

## 三个缺口

- **A 前道任务不生成** → 批次卡「前道」→ 机器永不占用。细化见 [前道任务生成-design.md](./2026-08-28-前道任务生成-design.md)。
- **B 前道人员锁定/释放无资源语义** → `preprocess_tasks` 仅 `assigned_workers` 数字，无占用/释放状态；`personnel` 只有 上班/请假，与前道任务无关联。
- **C 订单状态从不流转** → `approve_schedule` 不碰订单；批次上机/完成不联动订单；KPI 准交率依赖的 `order→完成` 日志全库无人写入。

本规格将 B 与 C 纳入，A 复用前道任务生成文档方案。

## 缺口 B：前道人员锁定 / 释放

### 设计（v1：产能级；个体级留待 P2-4）

前道人员池「锁定/释放」用**产能语义**表达，与现有 `preprocess_load`（`assessment.py:234-262`）口径一致：

| 流程点 | 语义 | 实现 |
|--------|------|------|
| 批次生成前道任务 | **锁定** `assigned_workers` 人·产能 | `persist` 生成 `preprocess_tasks`（人时计入池占用） |
| 批次 前道→待上机 | **释放**该任务占用 | `advance_preprocess`（`engine.py:125-139`）推进后任务不再属于「前道」批次 |

- **池占用率** = `preprocess_load().utilization`（`remaining_man_hours / 净产能`），已实现，无需新表。
- **personnel 表不改**：`上班/请假` 仍由 `_fire_leave` 独立驱动；请假时 `workers` 减少由 `_preprocess_params` 读取 system_config 保持 v1 简化（请假联动产能另记，本次不扩）。
- **个体级绑定**（哪个具体人被哪个批次占用）属 P2-4「前道进求解器」范围，本次不做。

### 与模拟器状态机关系（不变）

批次状态机 `前道→待上机→打印中` 已存在（`states.py:12-18`），缺口 A 生成任务后闭环自然打通。

## 缺口 C：订单状态流转

### 流转表

`orders.status` 枚举已存在（`schema.sql:42`）：`待排队 → 已审核 → 打印中 → 完成`。补三个写方：

| 触发点 | 订单流转 | 实现位置 | 写入 |
|--------|----------|----------|------|
| 审批通过（版本级） | 待排队 → 已审核 | `approve_schedule`（`scheduler_tools.py:107-137`），action=通过时 | `orders.status` + `state_change_log`（source=agent/solver） |
| 批次待上机→打印中 | 已审核 → 打印中 | `engine.advance_batches` step3（`engine.py:79-86`） | `orders.status` + `state_change_log` |
| 批次静置中→完成 | 打印中 → 完成 | `engine.advance_batches` step2（`engine.py:52-66`） | `orders.status` + `state_change_log` |

### 关键规则

1. **订单 → 已审核**：审批通过时，把该版本全部批次关联订单（`order_ids`）中状态为 `待排队` 的置为 `已审核`。
2. **订单 → 打印中**：批次上机时，其 `order_ids` 中状态为 `已审核` 的置为 `打印中`（幂等，不覆盖已完成）。
3. **订单 → 完成**（**多批拆分场景**）：一个订单可能拆到多个批次（`source='拆批'`）。**仅当该订单关联的全部批次 `status='完成'` 时才置订单完成**，防「订单提前完成」错误。实现：批次完成时查 `SELECT DISTINCT order_ids FROM batches WHERE 含该order_id AND status != '完成'`，为空才置完成。
4. **准交率口径**：写入 `state_change_log` `entity_type='order' AND new_value='完成'`，正好补齐 `kpi_metrics`（`scheduler_tools.py:388`）依赖的日志（当前无写方，靠批次 post_process_end 兜底）。
5. **驳回**：版本驳回时不改订单状态（订单继续留在待排队参与下一版）。

### 订单状态机守卫

新增 `ORDER_TRANSITIONS = {(待排队→已审核), (待排队→已审核→打印中), (打印中→完成)}`（对齐 `states.py` 风格），非法流转抛错，防竞态。

## 测试与验收

| 层 | 验证 |
|----|------|
| 单测（scheduler_tools） | `approve_schedule` 通过后：关联订单 status=已审核、日志落 state_change_log；驳回不改订单 |
| 单测（engine） | 批次上机 → 订单打印中；批次完成（含拆批多批次）→ 订单完成；未全完成的拆批订单**不**提前完成 |
| 单测（states） | 订单非法流转（待排队→完成）抛 ValueError |
| 集成 | `run_all_tests.py` 全绿；smoke：下单→审批→上机→完成全链订单状态正确推进 |
| 门禁 | `python run_all_tests.py` 全过 + `docker compose build` 成功才可提请部署 |
