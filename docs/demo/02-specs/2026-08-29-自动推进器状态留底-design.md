# 自动推进器各状态留底 topN · 设计规格

> **日期**：2026-08-29 · **状态**：待评审 · **关联**：[2026-08-28-排程排产全链路自动化-定稿-v1.md](./2026-08-28-排程排产全链路自动化-定稿-v1.md)（auto_scheduler 来源）、[rq-排程排产需求.md](../01-requirements/rq-排程排产需求.md)

## Context

2026-08-29 调试台演示时，用户问「查一下所有还在排队的订单」，agent 返回**空结果**（工具查不到任何待排队订单）。

根因：`auto_scheduler`（自动推进器）每 `interval_ticks` 自动排产，`solver.persist` 把**全部**待排队订单原子锁定为「已审核」，待排队被清空。随后自动审批 + 模拟器推进，订单持续流向「已审核→打印中→完成」。演示数据长期跑后，各状态样本被自动推进「推光」，导致状态类查询（待排队/已审核等）查不到数据。

用户需求：**自动推进器在推进时，每个订单状态保留最新至少 top5 订单不被推进**，保证任何时刻查任意状态都有最新样本。其他推进入口（手动排产、模拟器推进）保持原样正常通过。

## 现状覆盖矩阵（代码逐点验证）

| # | 推进点 | 谁触发 | 代码证据 | 问题 |
|---|--------|--------|----------|------|
| 1 | 待排队 → 已审核 | auto_scheduler 排产 | `auto_scheduler.py:107-117 _auto_schedule` → `scheduler_tools.py:37 run_scheduling` → `solver.py:136-145 persist` 原子 `UPDATE orders SET status='已审核' WHERE id IN(...) AND status='待排队'` | **排空**：`load_snapshot` 只取 `status='待排队'`（`snapshot.py:74-78`），persist 把全部锁定 → 待排队归 0 |
| 2 | 版本审批 | auto_scheduler | `auto_scheduler.py:119-164 _fifo_approve`（版本级 topN + 超龄兜底） | 审批通过后批次可上机，已审核订单被模拟器逐步消耗 |
| 3 | 已审核 → 打印中 → 完成 | 模拟器 | `engine.py:32-96 advance_batches`（step3 上机、step1-2 完成） | **其他入口**：正常业务流转，本次不守卫 |
| 4 | 手动排产 / agent 工具 | 用户/agent | `scheduler_tools.py:37 run_scheduling(triggered_by="agent")` | **其他入口**：本次不守卫，行为不变 |

## 缺口

1. **待排队被排空**（核心缺口，演示 bug 根因）：`persist` 无差别锁定所有待排队订单，auto_scheduler 自动排产后待排队恒为 0。
2. **已审核无保底**：自动审批 + 模拟器推进持续消耗已审核，新单不流入时已审核会被推光。

## 设计

### 方案总则：守卫只在 auto_scheduler 链路内，其他入口零影响

所有守卫逻辑封装在 `auto_scheduler.py`；`run_scheduling` 仅增加**可选参数**（默认 None 时行为与现状完全一致），不动 solver/snapshot/engine/states。

### 缺口 1：待排队保底（排产入口）

auto_scheduler 自动排产时，把「最新 top_n 待排队订单」排除出本次求解输入，它们保持待排队不被锁定。

| 项 | 实现 |
|----|------|
| 排产排除 | `run_scheduling(triggered_by, exclude_order_ids=None)`：`load_snapshot()` 后按 exclude_order_ids 过滤 `snapshot["orders"]` + `snapshot["parts"]`，其余照常 solve/persist |
| 保底跳过 | auto_scheduler `_auto_schedule`：查待排队订单数，若 **≤ top_n** 直接跳过本轮排产（保留全部待排队样本，避免空排产浪费）；若 **> top_n**，取最新 top_n 的 id 传给 `exclude_order_ids` |
| 最新口径 | **已拍板 R1=A（2026-08-29）**：订单 `id` 降序取 top_n（id 越大=越新，自增稳定） |
| 效果 | 待排队恒保留最新 top_n 订单，任意时刻可查 |

### 缺口 2：已审核保底（审批入口）

auto_scheduler `_fifo_approve` 审批前，查已审核订单数，若 **≤ top_n** 则跳过本轮自动审批（版本继续待审核，不促成已审核被上机消耗）。

- 注意：已审核→打印中由模拟器推进（其他入口），本守卫只保证 auto_scheduler **不主动**加剧已审核耗尽；已通过版本的批次仍随模拟器自然流转（符合「其他入口通过」）。
- 有 `FIFO_AGE_TIMEOUT` 超龄兜底兜底：长期待审版本不会永久卡死，超龄后仍自动通过。

### 打印中 / 完成

由模拟器自然流转，天然有样本（有在跑批次即有打印中，完成会累积），**不守卫** ✓。

### 配置

| 键 | 默认 | 说明 |
|----|------|------|
| `STATUS_RESERVE_TOP_N` | 5 | 各状态保留的最新订单数，与审批用 `AUTO_APPROVE_TOP_N`（版本级）解耦 |

## 实现改动点（汇总）

| 文件 | 改动 |
|------|------|
| `demo/config.py` | 新增 `STATUS_RESERVE_TOP_N`（env，默认 5） |
| `demo/tools/scheduler_tools.py` | `run_scheduling` 加可选参数 `exclude_order_ids=None`：load_snapshot 后过滤 orders+parts |
| `demo/scheduler/auto_scheduler.py` | `_auto_schedule`：待排队 ≤ top_n 跳过排产；> top_n 时取最新 top_n id 传 `exclude_order_ids`。`_fifo_approve`：审批前已审核 ≤ top_n 跳过本轮 |
| 测试文件 | `test_scheduler_tools.py`（exclude 过滤单测）、`test_auto_scheduler.py`（排产跳过/审批保底单测） |

**不改**：`solver.py` / `snapshot.py` / `engine.py` / `states.py`（其他入口零影响）。

## 测试与验收

| 层 | 验证 |
|----|------|
| 单测（run_scheduling） | `exclude_order_ids` 传入后：求解输入不含被排除订单；persist 不锁定它们（状态保持待排队）；不传参数行为与现状一致 |
| 单测（auto_scheduler） | 待排队 ≤ top_n → 本轮不排产（无新版本）；待排队 > top_n → 排产排除最新 top_n，待排队保留 top_n；已审核 ≤ top_n → 跳过审批 |
| 集成 | `run_all_tests.py` 全绿；容器内 seed 20 单 + auto_scheduler 开跑多轮，查各状态订单数：待排队 ≥ top_n、已审核/打印中/完成均有样本 |
| 门禁 | `python run_all_tests.py` 全过 + `docker compose build` 成功才可提请部署（门禁4） |

## 风险与待确认项

| # | 项 | 说明 | 建议 |
|---|----|------|------|
| R1 | 「最新 top_n」排序口径 | A：订单 `id` 降序（id 越大越新）；B：进待排队时间（`state_change_log` status→待排队 的 MAX(sim_time)，语义精确但需多表查询、空历史兜底） | ✅ **已拍板 A（2026-08-29）** |
| R2 | 待排队 ≤ top_n 跳过排产的语义 | 该批待排队订单会一直保留到有新订单流入，排产被延后 | 符合需求（保留样本优先），演示场景可接受 |
| R3 | 已审核保底强度 | 已通过版本的批次仍随模拟器推进，已审核可能被推低（其他入口不受控）；守卫只保证 auto_scheduler 不主动加剧 | 符合「其他入口通过」；如需强保证需动 engine（本次不做） |
| R4 | top_n 值 | 用户口径「top5」 | 默认 5，`STATUS_RESERVE_TOP_N` 可配置 |
