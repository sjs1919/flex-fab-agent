# 排程排产 demo 重构方案 v1

> **定位**：第二阶段「重构 demo 方案」正式文档。把 demo 从「纯 LLM 文本排产建议 + CSV 静态数据」升级为「MySQL 业务库 + 环境模拟器 + OR-Tools CP-SAT 求解器 + LLM 在环解释」的动态排产系统。
> **依据**：[`rq-排程排产需求.md`](../01-requirements/rq-排程排产需求.md)（头脑风暴全文）、[`排程排产需求规格-v1-2026-08-21.md`](../02-specs/排程排产需求规格-v1-2026-08-21.md)
> **现状基线**：`demo/代码阅读指南.md`（18 层代码导读 + 静态分析）+ 代码直接阅读（registry/data/api/config/auth）
> **状态**：v1 草案，待评审

---

## 0. 决策汇总

| 决策点 | 定案 |
|--------|------|
| 数据库 | **MySQL**（独立 database，与 big-data-obj 同栈） |
| 时间机制 | **A+B**：固定事件按加速时钟 **1min=1simh**；意外事件按统计分布预排 |
| 重排触发 | **C**：agent 决策重排 + 硬性不可行时系统强告警兜底 |
| 求解器 | OR-Tools CP-SAT（目标）；LLM 在环解释 |
| 数据层 | `tools/data.py` 加 DataSource 抽象，`DEMO_DATA_SOURCE=csv\|mysql` 切换 |
| 新工具 | 注册进现有 `ToolRegistry`（排产/负载评估/CTP/订单跟踪/审批） |
| 数据性质 | **重做**（非迁移）：现有 CSV 是混合工艺 8 台设备，需求是纯 3D 打印 7 台（demo 配置）+ part 层 |
| 订单预测 | **⭐ 新增**（2026-08-21 追加）：轻量时序（统计方法非训练），按天分材料，窗口默认 7 天；**预测校准 CTP（大单承诺期）**= 现有占用 + 预测未来占用 + 可用产能，不影响已下单订单 |

**关键边界**：MySQL 只管**业务数据**。demo 现有的 6 种基础设施存储**不动**（见 §2.2）。

### 1.3 数据差距（现有 CSV vs 新需求）

| 维度 | 现有 CSV | 新需求 | 处理 |
|------|---------|--------|------|
| 工艺 | 混合（3D打印/CNC/表面处理） | 纯 SLA/MJS/SLM | 新种子数据 |

## 2. 目标架构

### 2.1 四层 + 数据流

```
            ┌─────────────────────────────────────────────────┐
            │  环境模拟器 Simulator（独立进程 · 1min tick）       │
            │  A 时钟层：sim_clock 推进 1h/tick → 批次/设备/人效  │
            │  B 事件层：分布预排事件队列 → 故障/插单/请假/坏件     │
            │  硬性不可行检测 → 生成"需重排"告警                  │
            └───────────────┬─────────────────────────────────┘
                            │ 写状态 + 事件 + 审计
            ┌───────────────▼─────────────────────────────────┐
            │  MySQL 业务库（唯一事实来源）                       │
            │  主数据 · 运行数据 · 配置表 · 事件/审计              │
            └──────┬───────────────────────────────┬──────────┘
                   │ 读当前状态                      │ 读当前状态
          ┌────────▼────────┐              ┌────────▼────────┐
          │ 排产求解器        │              │ LLM 智能体（现有） │
          │ OR-Tools CP-SAT  │  ←工具调用→  │ LangGraph 编排    │
          │ 触发式重排        │              │ 审批·解释·决策     │
          └─────────────────┘              └─────────────────┘
```

**数据流（核心叙事）**：
1. 模拟器每 1 现实分钟推进世界（A 时钟 + B 事件），全部落库 + 审计。
2. 智能体**只能通过工具读 DB 当前状态**，看不到未来——每一次决策都像真实车间对"眼前状态"做判断。
3. 排产求解器是 agent 的**工具**：agent 判断"该重排了"→ 调 `run_scheduling` → 新排产表 → 排版人审批 → 上机。
4. 求解结果由 LLM 解释（复用现有单 Agent 图）。

### 2.2 存储边界（什么进 MySQL，什么不动）

| 存储 | 现状 | 处置 |
|------|------|------|
| **业务数据**（customer/orders/parts/machines/material/batches） | CSV | **迁 MySQL**（本次重构） |
| **运行数据**（schedule_versions/前道任务/审批/事件/状态变更日志） | 无 | **新增进 MySQL** |
| **配置表**（system_config） | 硬编码在需求文档 | **新增进 MySQL** |
| checkpoints.db（LangGraph） | SQLite | **不动**（框架拥有权，见 README §5.5） |
| tokens.db（STS） | SQLite | **不动**（Token 生命周期独立） |
| llm_cache.db / cache_db / chroma_db | SQLite / Chroma | **不动**（点查 + 向量检索，见 README §5.4） |
| audit.jsonl | JSONL | **不动**（追加写不该进 SQL，见 README §5.4） |

> **向量库确认（2026-08-21，用户拍板）**：合同 RAG 的 chroma_db/cache_db 保持现有简单向量库，**不迁 MySQL**——向量检索与业务主数据是两类存储，MySQL 只放关系型业务数据。

> 说明：README §5.5 说"生产演进选 PG 不选 MySQL"——那针对的是 **LangGraph checkpointer/向量/JSONB**。业务主数据用 MySQL 与真实业务栈同构，两者不冲突。

## 5. 环境模拟器设计

### 5.1 进程形态

- 独立线程（demo 单进程内起 thread，`--sim` 启动）或独立进程（`demo.simulator` 模块单独跑）。
- 1 现实分钟 tick：`time.sleep(60)` 循环，或测试时 `SIM_TICK_SECONDS` 环境变量加速心跳（测试/演示用，如 5s tick，不影响 sim 时间口径）。

### 5.2 A 时钟层（固定事件按加速走）

每个 tick（1 现实分钟 → +1 sim 小时）：
1. `sim_clock.current_sim_time += 1h`
2. **推进批次**：遍历状态=打印中的批次，`progress += 1h`，达到 `end_time` → 转静置中，排 `post_process_end`；达到 → 完成（触发坏件抽检）。
3. **推进设备**：遍历打印中设备，批次完成 → 设备转空闲（或按 C6 静置期间被占）。
4. **推进前道**：遍历前道任务，按分配人数 × 人效累积，完成 → 该批次可上机（C9 前道完成 ≤ 打印开始）。
5. **班次/换班**：按 3 班倒 × 8h × 换班 30min 折算人工产能（净 22.5h/天）。
6. **订单到期**：sim 时间过交期截止日 → 标记逾期（在途/排队都算，供负载评估超期预警）。

### 5.3 B 事件层（意外事件按分布预排）

| 事件 | 分布/参数（配置表） | 触发效果 |
|------|---------------------|---------|
| machine_failure | MTBF 指数（默认 ~96 sim h）；MTTR 指数（默认 ~2 sim h） | 设备→故障→维修中；在跑批次**中断**；若设备无法恢复该批次 → **硬性不可行 → 生成需重排告警**（C 兜底） |
| repair_done | MTTR 到点 | 维修中→空闲（可再分配） |
| new_order | 到达率（默认每天 ~2 单，含加急概率） | 插入 orders + parts → 待排队（软性扰动，agent 判断是否重排） |
| order_change | 到达率 | 改交期/撤单/数量变更 → 更新订单（撤单把未打批次退回到待排队池） |
| leave / back | 到达率（前道工人） | 请假→人效下降（6 人池减员）；回岗恢复 |
| restock | 到达率 | 材料库存到货 |
| scrap | 批次完成时按坏件率（默认 5%）抽检 | 坏件→需重打→**消耗应急池 §3.11**→生成新重打任务（硬性，自动进入待排队） |

事件生成方式：**开工时按分布预排下次事件时间戳**，放进 `sim_events` 队列（status=scheduled）；A 层每 tick 检查到点事件 → 触发（status=fired）→ 写 `state_change_log`。

### 5.4 状态机

```
机器：空闲 → 打印中 → 静置中(C6) → 空闲
              ↕ 故障 → 维修中 → 空闲
订单：待排队(含未审核) → 已审核 → 打印中 → 完成
前道工人：在岗 → 请假 → 在岗（6 人池动态人数）
批次：前道 → 待上机(审批通过) → 打印中 → 静置中 → 完成 / 坏件(需重打)
```

### 5.5 硬性不可行检测（C 兜底）

每 tick 检查：在跑批次所在设备 status=故障且维修无法在本批次交期内恢复 → 该批次标记"受影响"，生成**强"需重排"告警**（写 sim_events，agent 通过工具可见）。软性扰动（插单/请假）**不自动重排**——agent 决定。

## 6. 排产求解器设计

### 6.1 定位

`demo/scheduler/` 新模块，OR-Tools CP-SAT。**agent 的工具**，非常驻进程：agent 调 `run_scheduling` 时按当前 DB 快照求解，输出排产表写回 MySQL（新 schedule_version）。

### 6.2 建模（对齐需求规格 §6/§7/§8）

**输入**：当前未完成订单 + 零件 + 可用设备 + 前道人工池（从 MySQL 读）。

**决策变量**
- 合批：哪些 part 进同一 batch（隐式：用可选性 + 容量约束表达）
- 设备分配：batch → machine（按工艺分群 C3）
- 时间排程：batch.start / batch.end

**硬约束（C1-C9）**
- C1 同舱同材料；C2 容量（max(长,宽,高)≤舱边 + Σ投影面积×0.7 + 件数上限 + Σ件重≤承重）；C3 机型匹配；C4 批次时长=max(单件时长)；C5 整批优先可拆；C6 设备互斥 + 静置占用；C7 交期按天 23:59；C8 日可用=24h×90%；C9 前道完成 ≤ 打印开始。

**目标（§7 分层）**
1. **主目标**：`min Σ(订单金额 × 违约金日费率 × 延期天数)`（P0-3，违约金费率 = customer.penalty_rate，金额 = orders.amount）
2. **偏好**：同订单同舱（软约束惩罚项）
3. **次**：舱利用率（仅产能宽松时）
4. **低**：负载均衡
> CP-SAT 需要数值目标：加权迟到为线性项（金额×费率是常量系数 × 延期天数变量），可直接建模。

**排序键**（非求解内，用于排队口径/订单跟踪展示）：`交期升序 → priority 降序`（§3.8/§3.14）。

**输出**：`schedule_versions.result_json`（每个 part→批次→设备→开工/完成）+ `batches` 表 + 指标（准交率/舱利用率/延期清单/超尺寸预警清单）。

**无可行解**：返回冲突订单清单（超尺寸 max>600 直接预警进入预警清单，不静默忽略）。

### 6.3 触发方式（决策 C）

- 由 agent 经工具触发（`run_scheduling`）；模拟器只在**硬性不可行**时生成告警事件，不直接调求解器。
- 初始排产：`--init-schedule` 一键生成第一版。

### 6.4 订单预测模块设计（⭐ 新增 · 2026-08-21 追加）

**定位**：`demo/forecast/` 新模块，独立于求解器。补"大单承诺期"缺预测的盲区（rq §3.19）：现有 CTP 只看已下单订单负载，未考虑未来订单抢占产能 → 承诺期偏乐观。

**输入**：历史订单（MySQL `orders` 表，按天 + 分材料聚合：件数、机时）。

**方法**：统计轻量时序（移动平均 / 指数平滑，可配），**不做模型训练**（demo 定位，避开"训练/微调"算法门槛；demo 数据规模也不支持）。

**输出**：未来 N 天（默认 7，可配）预测负载：
- 预测订单量（件数，分材料 SLA/MJS/SLM）
- 预测产能占用（机时，分材料/机型）

**用途——预测校准 CTP（大单承诺期）**：
```
承诺期 = 现有占用（打印中 + 已审核 + 待排队）
       + 预测未来占用（预测窗口内预测订单机时）
       + 新大单自身机时
       → 最早可交付日期（按 90% 常规口径，不影响已下单订单）
```

**实现**：纯函数 + 配置参数（`forecast_method` / `forecast_window`）进 system_config。

- **用途**：`query_forecast` 工具 + `query_ctp` 增强——预测校准 CTP（现有占用 + 预测占用 + 新大单 → 承诺交付日期）。
- **配置**：`forecast_method`（ma/exponential，默认 exponential）、`forecast_window`（默认 7 天）进 system_config。
- **边界**：纯统计、无训练；预测只作"未来占用"预留，不影响已下单订单（现有承诺优先）。

**B5. 良率/坏件闭环（⭐ B7 · 2026-08-21 确认入案）**
- **数据**：模拟器 B 层 scrap 事件（B2）触发重打时，坏件记录落 `bad_parts` 表带根因维度：设备 id / 批次 / 材料 / 关联 MTBF 故障事件（sim_events）。
- **工具**：`query_yield`（只读）——良率按设备/批次/材料下钻 + 根因归因（哪台设备故障多→良率低、哪批坏件多、某材料坏件率高）。
- **LLM 解读**：归因结果 → 工艺改善建议（烂设备→检修、材料→换料），docstring 写清触发条件（沿用现有风格）。
- **口径**：`query_kpi` 良率=总数（1−坏件/完工）；`query_yield`=下钻+归因，同一 `bad_parts` 来源，口径一致。
