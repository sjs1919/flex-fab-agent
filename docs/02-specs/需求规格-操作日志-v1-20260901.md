# 需求规格：统一操作日志（Operation Log）v1

- 版本：v1
- 日期：2026-09-01
- 状态：待评审
- 对应需求：Web 控制台四类操作（自动推进 / 模拟器 / 手工 / 调试台）日志落库 + 分页查询界面 + 集成到 tab 页

---

## 1. 背景与目标

### 1.1 背景

演示环境中四类操作目前**无统一日志**：

- 自动推进（auto_scheduler）与模拟器（simulator）是后台线程，动作只打 stdout，`docker logs` 可见但不可查询、不可筛选。
- 手工操作与调试台操作走 HTTP，分散落在 `cost_record` / `trace_record` / `state_change_log` 等角度不同的表，无法在一个界面统一回溯"系统刚才发生了什么"。

### 1.2 目标

1. 将四类操作统一落库到一张 `operation_log` 表。
2. 提供一个**分页 + 类别 / 时间范围 / 关键字筛选**的查询界面。
3. 界面作为新 tab「操作日志」集成进 Web 控制台（PortalView）。

## 2. 四类操作定义（来源分类）

| category | 含义 | 覆盖动作 |
|----------|------|---------|
| `auto` | 自动推进（auto_scheduler 后台线程） | 触发排产、生成新版本、自动审批（通过/驳回）、调度器异常/熔断 |
| `simulator` | 模拟器（simulator runner 后台线程） | tick 推进且有事件 fired；tick 异常/熔断 |
| `manual` | 手工操作（HTTP，用户经 Web/API 手动触发） | /schedule/load、/schedule/approve、/sim/start、/sim/stop、/config、/resources/*、/ask、/threads/* 及只读查询类 |
| `debug` | 调试台操作（HTTP，/debug/*） | /debug/cases、/debug/trace/{id}、/debug/rerun/{id}、/debug/judge/{id}、/debug/stats、/debug/cases/{id}/label |

**已确认的粒度决策**：自动类（模拟器心跳 / 自动调度跳过）这类高频"例行无事发生"记录**不落库**，只落关键动作。

## 3. 范围

### 3.1 范围内

- `operation_log` 建表（schema v5 增量迁移）
- 统一写入模块 `observability/operation_log.py`（record + query）
- HTTP 中间件自动拦截 手工 + 调试台 两类并落库
- auto_scheduler / simulator 线程关键动作埋点
- `GET /logs` 分页筛选查询接口
- 前端 `LogView.vue` 新 tab + 分页界面 + api/log.ts
- 后端单测 `test_operation_log.py`

### 3.2 范围外（明确不做）

- 不迁移历史日志（从部署后起记）
- 不做日志清理 / 归档 / 导出
- 不做自动轮询刷新（界面手动「刷新」按钮）
- 不区分操作者账号（单机演示无登录体系）
- 不记录"跳过型"自动日志

## 4. 数据层设计

### 4.1 新表 `operation_log`（schema v5）

```sql
CREATE TABLE IF NOT EXISTS operation_log (
    id          BIGINT AUTO_INCREMENT COMMENT '日志 id',
    category    ENUM('auto','simulator','manual','debug') NOT NULL COMMENT '来源类别',
    action      VARCHAR(64)  NOT NULL COMMENT '语义动作名（如 自动排产触发/模拟器tick/手动排产/调试重跑）',
    status      ENUM('ok','fail') NOT NULL DEFAULT 'ok' COMMENT '结果（跳过型不落库，故无 skip）',
    summary     VARCHAR(255) NOT NULL COMMENT '一句话摘要',
    detail_json TEXT         NULL COMMENT '扩展明细 JSON',
    sim_time    DATETIME     NULL COMMENT 'sim 时间（线程类有，HTTP 类可空）',
    real_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '现实时间',
    trace_id    VARCHAR(32)  NULL COMMENT '关联 trace（HTTP 操作）',
    relate_id   VARCHAR(64)  NULL COMMENT '关联对象 id（版本/事件/订单）',
    PRIMARY KEY (id),
    KEY idx_oplog_realtime (real_time),
    KEY idx_oplog_category (category, real_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='统一操作日志（四类来源）';
```

- `detail_json` 用 `TEXT` 存 JSON（沿用 `kpi_snapshot.metrics_json` 模式，兼容 MySQL 8.4，不启用 DB JSON 类型）。
- 索引覆盖默认排序（real_time）与类别筛选（category + real_time）两种主要访问路径。

### 4.2 迁移

- `schema/migrate.py`：`CURRENT_VERSION` 4 → 5，注册 `_MIGRATIONS[5]`（建 operation_log 表，up/down）。

## 5. 写方设计

### 5.1 统一写入模块 `observability/operation_log.py`

```
record_operation(category, action, status="ok", summary="",
                 detail=None, sim_time=None, trace_id=None, relate_id=None) -> int
query_operations(category=None, start=None, end=None, keyword=None,
                 page=1, page_size=20) -> {total, items}
```

- 复用 `tools/data.py` 的 `transaction()` 写、`get_connection()` 读。
- `detail` 为 dict，自动 `json.dumps(default=str)`。
- `query_operations` 排序 `real_time DESC`；keyword 模糊匹配 `action / summary / trace_id`；参数可空，全部走参数化查询。

### 5.2 HTTP 中间件（api.py，覆盖 manual + debug）

- 在现有 `trace_id_middleware` 之后新增，响应完成后异步落库（不阻塞响应）。
- **排除路径**：静态资源（`/assets/*`、`/` 根、`/{full_path:path}` 静态兜底）、`/health`、`/logs` 自身、`/debug/admin-token`。
- **分流规则**：
  - `/debug/*` → `category=debug`
  - `/schedule/*`、`/sim/*`、`/config`、`/resources/*`、`/ask`、`/threads/*` → `category=manual`
  - 其余 → 不记录
- **语义动作名**：维护小映射表 `{path_pattern: 中文动作名}`，覆盖主要端点，未命中项用 `METHOD /path` 概括。示例条目：

  | path_pattern | action |
  |--------------|--------|
  | `POST /schedule/load` | 手动排产加载 |
  | `POST /schedule/approve` | 排产审批 |
  | `POST /sim/start` | 模拟器启动 |
  | `POST /sim/stop` | 模拟器停止 |
  | `PUT /config` | 修改配置 |
  | `POST /ask` | 智能问答 |
  | `POST /debug/rerun/{id}` | 调试重跑 |
  | `POST /debug/judge/{id}` | 调试判定 |
  | `PUT /debug/cases/{id}/label` | 用例打标签 |
  | `PUT /resources/personnel/{id}/status` | 修改人员状态 |

  映射表具体条目以实施时现有端点为准补充完整。
- **status**：响应码 `<400` → `ok`；`>=400` → `fail`。
- **trace_id**：取当前 request_context 中的 trace_id 写入。

### 5.3 后台线程埋点

- `scheduler/auto_scheduler.py`：
  - 触发排产（实际执行，非跳过）→ `action=自动排产触发`
  - 生成新版本 → `action=自动排产生成版本`，`relate_id=版本号`
  - 自动审批通过/驳回 → `action=自动审批`，`relate_id=版本号`
  - 调度器异常/熔断 → `status=fail`
  - **跳过型不落**（待排队≤留底等）。
- `simulator/runner.py` `run_tick()`：
  - `events_fired > 0` → `action=模拟器tick`，`summary=推进1h 事件N条`，`sim_time=当前sim时间`
  - tick 异常 / 连续失败熔断 → `status=fail`

## 6. 查询 API `GET /logs`

```
GET /logs?category=auto|simulator|manual|debug&start=2026-09-01&end=2026-09-02&keyword=排产&page=1&page_size=20

→ 200 {
    total, page, page_size,
    items: [{ id, category, action, status, summary, detail_json,
              sim_time, real_time, trace_id, relate_id }]
}
```

- `start` / `end` 为 DATETIME，过滤 `real_time` 区间。
- `page_size` 上限 100，默认 20。
- 查询自身不落日志（middleware 排除 `/logs`）。

```
┌─ 操作日志 ────────────────────────────────────────────────┐
│ [类别▾] [时间范围 ▍▍] [关键字…] [查询] [刷新]              │
├───────────────────────────────────────────────────────────┤
│ 现实时间      │ 类别    │ 动作      │ 状态   │ 摘要       │
│ 09-01 01:45   │ 自动    │ 触发排产  │ ✅成功 │ 版本 v12 … │
│ 09-01 01:44   │ 模拟器  │ 模拟器tick│ ✅成功 │ 推进1h 事件2│
│ 09-01 01:43   │ 手工    │ 手动排产  │ ✅成功 │ 版本 v11 … │
│ 09-01 01:40   │ 调试    │ 调试重跑  │ ❌失败 │ trace …   │
├───────────────────────────────────────────────────────────┤
│ ← 1 2 3 4 … →   每页 [20▾]   共 128 条                     │
└───────────────────────────────────────────────────────────┘
```

- 筛选栏：类别 `el-select`（全部/自动/模拟器/手工/调试）、时间范围 `el-date-picker` daterange、关键字 `el-input`（搜 action/summary/trace_id）、「查询」「刷新」按钮。
- 表格列：现实时间 / 类别（色 tag：自动橙、模拟器蓝、手工绿、调试紫）/ 动作 / 状态（tag：成功绿、失败红）/ 摘要 / 模拟时间 / trace_id。
- 分页 `el-pagination`（current-page、total、page-size 10/20/50/100 可切）。
- 加载时机：进入 tab 首次渲染时拉一次 + 「刷新」手动拉，不自动轮询。
- 空态：无数据时表格展示空提示。

## 9. 风险与注意

- middleware 与 `trace_id_middleware` 的执行顺序：新增中间件需在 trace 上下文建立后取 trace_id。
- 静态资源请求频繁，middleware 需在路径判断阶段尽早短路，避免无效落库开销。
- 后台线程落库不依赖 HTTP 上下文，`sim_time` 需从 sim_clock 显式读取。
- 落库失败不能影响主链路：`record_operation` 内捕获异常只告警不抛出（参考 runner `_record_kpi_snapshot` 的旁路设计）。
