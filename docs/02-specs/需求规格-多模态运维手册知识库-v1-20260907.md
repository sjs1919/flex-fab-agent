## 1. 背景与目标

### 1.1 背景

现有 RAG 只服务合同场景，能力边界很窄（摸底结论，2026-09-07）：

| 现状 | 位置 | 问题 |
|------|------|------|
| 只加载 `*.txt` | `flex_fab_agent/rag/knowledge_base.py:49` | PDF / Word / 图片全部无法入库，连 markdown 都没走 |
| 无任何解析依赖 | `requirements-flex-fab-agent.txt`、`requirements.txt` | 无 pypdf / PyMuPDF / python-docx / OCR / pillow |
| 无上传通道 | 全仓 `UploadFile` / `multipart` 零命中 | 语料只能人工拷进 `flex_fab_agent/data/` |
| 灌库是「一次性全量」 | `knowledge_base.py:82`（`count>0` 即整体复用） | 不支持增量，新增文档必须删库重建 |
| metadata 只有 `source` | `knowledge_base.py:95` | 无页码 / 章节 / 图片引用，无法给可跳转的溯源 |
| 权限是文件名硬编码 dict | `knowledge_base.py:30` | 手册增多后不可维护 |
| BM25 索引与 collection 冻在进程内单例 | `rag/retriever.py:135` `_rag_state` | 新增文档后不刷新，需重启进程 |

可直接复用的既有资产：

- 混合检索四步：向量召回 + BM25（jieba + BM25Okapi）+ RRF(k=60) + Cross-Encoder 重排 —— `rag/retriever.py:118 retrieve_hybrid`
- Reranker `BAAI/bge-reranker-base`（`retriever.py:22`）、Embedding `BAAI/bge-small-zh-v1.5`（`knowledge_base.py:26`）
- HF 离线优先加载工具 `core/hf_utils.py:46 / :80`
- 工具注册与懒加载模式 `tools/registry.py:258-271`
- 调试台 trace span 树可视化（检索过程会自动出现在链路里）—— `web/src/views/DebugView.vue:51`
- RAGAS 四指标回归框架 `eval/ragas_regression.py`，可扩展为手册问答质量门禁

### 1.2 目标

1. 支持导入 **PDF / Word / 图片** 三类多模态手册资料，按手册分类管理（机器使用手册 / 生产运维手册 / 故障恢复手册 / 其他）。
2. 图片内容可被检索到（见第 2 节三级策略）。
3. 在**调试台**增加手册管理与手册问答功能，支持上传、查看解析结果、人工标注修正。
4. Agent 可通过工具检索手册作答，答案带**可定位的溯源**（手册名 + 页码/章节，图片可点开原图）。

## 2. 已确认决策

### 2.1 图片处理三级策略 ✅ 已确认（2026-09-07 用户确认）

图片（独立图片文件、PDF/Word 内嵌图、扫描版 PDF 页面）按三级递进处理：

| 级别 | 触发条件 | 处理动作 | 入库内容 | 来源标记 |
|------|---------|---------|---------|---------|
| **L1 OCR 打底** | 所有图片默认走 | 本地 OCR 抽取文字，并基于抽取结果生成一段摘要 | OCR 文本 + 摘要 | `ocr` |
| **L2 自动图注兜底** | OCR 无文字 / 文字量低于阈值 / 置信度低于阈值（如流程图、接线图、纯示意图） | 自动调用多模态 LLM 生成中文图注 | LLM 图注 | `vlm` |
| **L3 人工标注重生成** | 界面上人工判定「识别不准」 | 人工可编辑说明文本，或触发 LLM 重新生成图注；确认后**重新 upsert 向量库** | 人工文本 或 重生成图注 | `human` / `vlm_regen` |

设计要点：

- 三级结果都写入**同一个图片资产记录**，`caption_source` 字段标记来源，便于统计各级占比和评估 OCR 质量。
- L2 的触发阈值（字数下限、OCR 置信度下限）必须**可配置**，走 `/config` 白名单（`api.py:185`）。
- L3 重生成必须**幂等**：同一图片重复标注只保留最新版本，向量库按 `asset_id` upsert 而非追加，避免同一张图产生多条互相竞争的向量。
- L1 的「摘要」与 L2 的「图注」都是**给检索用的文本代理**，答案里应引用原图位置而不是把代理文本当原文呈现。

### 2.2 手册规模与解析执行方式 ✅ 已确认（2026-09-07 用户确认）

**规模：数十份，含大扫描件（图片型 PDF）。**

由此**锁定异步架构**（不是可选项）：

- 单份大扫描件的 OCR + 图注耗时在分钟到几十分钟量级，前端 axios timeout 仅 120s（`web/src/api/debug.ts:1`），同步解析必然超时 → **导入端点只落任务并立即返回，解析在后台执行**。
- `manual_import_job` 表**必做**（第 5.3 节），前端轮询进度。
- 必须有**分阶段进度**（upload / parse / ocr / caption / index）而非单一百分比 —— 几十分钟的任务只显示「解析中」无法判断是在跑还是卡死。
- 必须有**失败重试**且能从失败阶段续跑，不要求整份重解析。
- 必须有**并发上限**：数十份批量导入若同时起 OCR 会打满 CPU，需串行或限流队列。
- 必须有**单图失败降级**：某张图 OCR/图注失败 → 只记录该图失败，不让整份手册解析失败。

### 2.3 导入方式 ✅ 已确认（2026-09-07 用户确认）

**界面上传 + 服务器目录扫描，两条路径都做。**

| 场景 | 路径 | 说明 |
|------|------|------|
| 首次批量入库（数十份，含大扫描件） | 目录扫描 | 文件拷到约定目录（建议 `RUNTIME_DIR/manuals_inbox/`，随挂卷持久化），界面点「扫描导入」→ 批量建任务入队 |
| 日常补充单份 | 界面上传 | multipart 上传 → 存入同一目录 → 建单个任务入队 |

设计要点：

- **两条路径在「建任务」之后完全共用同一套异步解析流程**，不做两套解析逻辑。差异只在文件如何到达磁盘。
- 目录扫描必须**幂等**：按 `file_hash` 判重（`manual_doc.file_hash`），已入库的文件重复扫描跳过并在结果里报告「跳过 N 份」。
- 目录扫描需**支持子目录**并可用目录名作为分类默认值（如 `manuals_inbox/故障恢复/xxx.pdf` → category=recovery），减少逐份手填分类。
- 上传端点需限制**文件类型白名单**（pdf/docx/png/jpg）与**单文件大小上限**（可配置），拒绝时给明确错误。
- 扫描导入是写操作，走 `require_admin`（`api.py:274`）；上传同理。
- 上传的原始文件与扫描的原始文件**存同一处**，后续「查看原页/原图」的静态访问路径统一。

### 2.4 多模态 LLM 接入方式 ✅ 已确认（2026-09-07 用户确认）

**不锁定单一供应商。新增一套与现有文本 provider 同构的「多模态 provider 主备表」，靠参数/环境变量选择与回落。**

现有文本链路的既有模式（照此复刻，不另立门派）：

| 既有件 | 位置 | 作用 |
|--------|------|------|
| `PROVIDERS` 列表 | `config.py:116` | **列表顺序即 fallback 顺序**，三家均 OpenAI 兼容，代码层只差 base_url + api_key + model |
| `PRIMARY_PROVIDER` | `config.py:115` | 环境变量指定谁提到最前，无需改代码 |
| `available_providers()` | `config.py:150` | 过滤 `enabled` 且 key 非占位符 |
| `call_llm` fallback | `core/llm_client.py:123-131` | 遍历 PROVIDERS，第一个成功即返回，失败自动切下一个；支持 routing policy 覆盖遍历顺序 |
| 测试注入 | `core/test_llm_client.py:68` | monkeypatch `lc.PROVIDERS`，不发真实调用 |

**新增对应件（同构）**：

| 新增件 | 位置 | 说明 |
|--------|------|------|
| `VISION_PROVIDERS` 列表 | `config.py`（紧随 `PROVIDERS` 之后） | 每项同样是 `{name, enabled, api_key, base_url, model, note}`；顺序即主备回落顺序 |
| `PRIMARY_VISION_PROVIDER` | `config.py` | 环境变量把指定多模态 provider 提到最前，与 `PRIMARY_PROVIDER` 用法一致 |
| `available_vision_providers()` | `config.py` | 同 `available_providers()` 的过滤口径 |
| `call_vision()` | 新建 `core/vision_client.py` | 复刻 `llm_client.call_llm` 的遍历回落 + 连接池 + 缓存；入参为「图片 + 提示词」，出参为中文图注文本 |

设计要点：

- **候选条目预置但默认按可用性启用**：火山方舟标准端点（`/api/v3` + doubao vision，复用 `VOLC_API_KEY`）、海外 vision（需 `HTTPS_PROXY=http://127.0.0.1:3450`）、本地 VLM 各作为一项预置进列表，`enabled` 由环境变量控制。哪家有额度就把它设成主用，**不需要改代码**。
- **图片入参统一走 OpenAI 兼容的 `image_url` + base64 data URI**，这样各家差异仍收敛在 base_url + model 三元组内，与文本链路的假设一致。
- **必须带缓存**：缓存键 = 图片内容 hash + 提示词版本。L3 人工触发重生成时**显式跳过缓存**，否则「重新生成」拿回同一条旧图注。数十份大扫描件重跑时缓存能省掉绝大部分调用费用。
- **全部 vision provider 都不可用时降级为 D 方案**：该图只记录位置与 `caption_source=none`，标记 `review_status=flagged` 进人工队列，**不让整份手册解析失败**（与 2.2 的单图失败降级一致）。
- 单测按 `core/test_llm_client.py:68` 的方式 monkeypatch `VISION_PROVIDERS`，不发真实多模态调用。
- 供应商具体型号与额度确认属**实施期配置工作**，不再阻塞需求定稿。

### 2.5 手册权限分级 ✅ 已确认（2026-09-07 用户确认）

**手册分权限（public / confidential 两档），并同步修复「经 /ask 检不到 confidential」的既有 bug。**

手册级权限模型：

- `manual_doc` 增 `access` 字段：`public`（默认）| `confidential`。
- 分类与权限**解耦**：同是故障恢复手册，可有的 public 有的 confidential，由导入时（上传表单 / 目录规则 / 后续编辑）指定，不按 category 一刀切。
- confidential 手册的可见范围沿用现有角色白名单 `CONFIDENTIAL_ROLES={"admin","reviewer"}`（`retriever.py:27`），不另立矩阵。

### 2.7 手册版本管理 ✅ 已确认（2026-09-07 用户确认）

**同一手册允许多版本并存可查，可手动切换，但检索默认只命中当前激活版本。**

- 用 **设备型号** 分组多个手册版本：`manual_doc` 增 `device_model`（型号）+ `version` + `is_active`。
- 一个 `device_model` 同一时刻**仅一个激活版本**；导入新版本时旧版本不删除、不自动下线，只是 **`is_active` 置 false**（默认不检旧版）。
- 检索默认只命中 `is_active=1` 的手册，避免同一问题从多个版本各召回一段互相打架；版本切换由「激活哪一版」驱动，而非检索时指定版本。
- 界面：手册列表按设备型号分组展示各版本，可标「当前」「历史」，提供「设为当前版本」操作（写操作，`require_admin`）。
- **历史版本向量是否下线可选**：若激活新版本时把旧版本向量一并删掉，「版本切换」就名存实亡（历史版本在库但查不到）。故 v1 保留旧版本向量与索引，仅靠 `is_active` 过滤排除出检索；只有当切换是「回滚到上一版」时才需要旧版可检，v1 已覆盖。旧版本向量显式删除做成「删除手册」动作的一部分（见 C4 范围：删除单版本 = 从库里删对应手册）。
- 去重改为 `device_model + version` 维度：`file_hash` 仍用于「同一文件重复导入」的幂等跳过；但不同 `device_model` 或不同 `version` 的同文件允许分别入库（若需）。
- **可手动切版本对比**：激活版 + 历史版在同一型号组内可见，详情可对比（哪两个字段可比、比对界面到设计阶段细化）。

### 2.8 手册库与合同库分离 ✅ 已确认（2026-09-07 用户确认）

**手册与合同分两个向量集合、两个检索工具，不共用 collection，避免召回互相稀释与工具 description 误导。**

| 维度 | 合同库 | 手册库 |
|------|--------|--------|
| collection | `kb_contracts_delay`（`knowledge_base.py:25`） | 新建 `kb_manuals` |
| 工具 | `search_knowledge_base` | 新建 `search_manual` |
| 覆盖语料 | 合同条款 / 延期记录 | 设备使用手册 / 运维手册 / 故障恢复手册 |
| 权限 | `DOC_PERMISSION`（改数据驱动后由合同表驱动） | `manual_doc.access` |

- **懒加载**：`search_manual` 在 `tools/registry.py` 沿用 `_search_kb` 的懒导入模式（`tools/registry.py:258-271`），建表时不拉 chromadb/jieba/sentence_transformers。
- **工具 description**：`search_manual` 的 description 明确写「设备使用手册、生产运维手册、故障恢复手册、报警代码、维护保养」等关键词，并注明「查合同条款请用 search_knowledge_base」，让 LLM 按问题域选对工具、不串味。
- **权限判定共用**：两库共用 `retriever._allowed_sources` 的数据驱动权限判定（2.6），只是数据来源不同（合同表 vs `manual_doc.access`）。

### 2.9 答案溯源粒度 ✅ 已确认（2026-09-07 用户确认）

**页码 + 章节标题都存**，答案能同时给「第 N 页」与「第 X.Y 节」，且可点开原页/原图。

- metadata 含 `page_no` + `section`（章节标题，嵌套标题用 `A / A.1 / A.1.1` 路径拼接）。
- 切分策略按文档类型自适应：
  - **PDF**：以页为主、页内按章节细切；每 chunk 带 `page_no`，章节目录能解析出来则一并带上。
  - **Word（.docx）**：以标题层级为主、跨页连续；每 chunk 带 `section`（多级标题路径），`page_no` 若从 docx 可得到则带、否则可空。
- `search_manual` 返回溯源格式：`<手册名> <版本> 第<N>页 第<X.Y节>`，图片命中附加「图 N」（asset_id + 可访问 URL）。
- 溯源要**可点开**：PDF 原页、图片原图通过静态访问路径打开（图片存储与访问见第 11 节风险）。PDF 原页跳转若 PDF.js 等浏览器能力可行则到设计阶段再定，不阻塞 v1。

### 2.6 既有权限 bug 修复（C3 连带，必做）

**Bug**：`graph/single_agent_graph.py:247-253` 只给**写工具**（`not schema.read_only`）自签 admin token；只读的 `search_knowledge_base` 拿 `token=None` → `retriever.py:158 _allowed_sources(None)` 回落**仅 public**。后果：**经 `/ask` 与调试台提问永远检不到 confidential 文档**，只有 `eval/ragas_regression.py:8` 内部直传 reviewer token 才检得到。

**修复方向（实施时定稿）**：

- 方案一：在 `graph/single_agent_graph.py` 给读工具也注入「最小角色」token，而非一刀切 admin。读取工具逻辑上应是 `token_for(role="reviewer")` 或按会话角色签发，让 RAG 权限过滤真正生效，而不是绕成全部可见。
- 方案二：权限过滤上移到会话层——由 `retriever._allowed_sources` 读当前会话角色决定可见文档集合，而不是依赖工具层 token。
- 两案都要配套单测：`test_rag_permission`（鉴权角色从 None → admin/reviewer/operator/viewer 时，confidential 命中与否正确变化）。
- > **设计定稿：选方案一 + 会话角色来源 = `AskRequest.role`（默认 admin）**。单机 demo 无登录态，调试台/手册问答下拉模拟角色；graph 读工具按 role 签 token（详见 `docs/02-specs/2026-09-07-多模态运维手册知识库-design.md` D1）。
- 顺带把 `knowledge_base.py:30 DOC_PERMISSION` 的**文件名硬编码 dict** 改为数据驱动（由 `manual_doc.access` / 合同表驱动），否则手册量一多硬编码不可维护。

## 4. 范围

### 4.1 范围内

- 多格式解析层：PDF（文本层 + 内嵌图 + 扫描页）、Word（.docx 正文 + 内嵌图）、独立图片（png/jpg）
- 图片三级处理（OCR → 自动图注 → 人工标注重生成）
- 手册元数据与图片资产落库（新表，schema v6）
- 手册版本管理（同型号多版本并存 + `is_active` 激活切换，见 2.7）
- 手册权限分级（public/confidential，见 2.5）+ 修复只读工具 token 落差（见 2.6）
- 增量灌库 + 向量库/BM25 索引失效刷新
- 结构感知切分（按页 / 按标题）与富 metadata（手册 id、页码、章节、asset_id）
- 手册检索工具 `search_manual` 注册与 Agent 挂载
- 调试台手册功能面板（列表 / 上传或扫描触发 / 解析详情 / 人工标注 / 问答试验）
- 后端单测 + 手动验收

### 4.2 范围外（v1 明确不做）

- 不做 .doc（旧二进制格式）、.xlsx、.pptx
- 不做手册内容编辑器（只标注图片说明，不编辑正文）
- 不做多模态 embedding（图片仍以文本代理入索引）
- 不做跨手册知识图谱 / 自动目录生成
- 不做三档以上权限（public/confidential 两档已够，见 2.5）
- 不做跨版本自动 diff / 内容差异比对界面（版本并存但对比留到设计阶段细化）

## 5. 数据层设计（初稿，schema v6；当前 `CURRENT_VERSION = 5`，见 `flex_fab_agent/schema/migrate.py:22`）

### 5.1 `manual_doc` —— 手册主记录

关键字段：`id`、`title`、`device_model`（设备型号，版本分组键，见 2.7）、`version`、`is_active`（同一型号仅一个激活版）、`category`（machine / ops / recovery / other）、`access`（public / confidential，见 2.5）、`file_path`、`file_type`（pdf/docx/image）、`file_size`、`file_hash`（同一文件重复导入的幂等）、`page_count`、`status`（pending / parsing / indexed / failed / archived）、`chunk_count`、`asset_count`、`error_msg`、`created_at`、`indexed_at`。

唯一性：同 `device_model + version` 唯一（激活版与历史版并存，见 2.7）；`file_hash` 仍用于同文件重复导入的幂等跳过。

### 5.2 `manual_asset` —— 图片资产（三级策略载体）

关键字段：`id`、`doc_id`、`page_no`、`image_path`、`ocr_text`、`ocr_confidence`、`caption`（最终入索引文本）、`caption_source`（`ocr` / `vlm` / `human` / `vlm_regen`）、`review_status`（ok / flagged / fixed）、`vector_id`（对应 Chroma 中的 id，供 upsert）、`updated_at`。

### 5.3 `manual_import_job` —— 导入任务（**必做**，见 2.2）

关键字段：`id`、`doc_id`、`stage`（upload / parse / ocr / caption / index）、`stage_progress`（当前阶段已处理/总数，如「图注 12/56」）、`status`（queued / running / failed / done）、`message`、`retry_count`、`failed_stage`（供从失败阶段续跑）、`started_at`、`finished_at`。

> 表结构细节（DDL、索引、字符集）待待确认项闭环后在设计文档中定稿；沿用 `operation_log` 的 `TEXT` 存 JSON 约定，不启用 DB JSON 类型。

## 6. 解析层设计（初稿）

```
上传/扫描 → 格式分派 → 文本抽取 + 图片抽取
                          ├─ 文本 → 结构感知切分 → chunk（带页码/章节）
                          └─ 图片 → L1 OCR → 判定阈值 → 命中则 L2 图注
                                                        → 图片 chunk（带 asset_id/页码）
                          → 增量 upsert 到 kb_manuals collection → invalidate BM25 索引
```

新增模块（建议）：`flex_fab_agent/rag/loaders/`（按格式拆 pdf / docx / image）、`flex_fab_agent/rag/ocr.py`、`flex_fab_agent/rag/captioner.py`、`flex_fab_agent/rag/manual_index.py`（增量灌库与 upsert）。

## 11. 风险与注意

- **解析耗时**：已确认存在大扫描件（2.2），OCR + 多模态图注对其极慢，异步 + 分阶段进度 + 从失败阶段续跑 + 并发限流均为硬要求，不能同步硬扛。
- **后台任务与容器重启**：数十分钟的解析任务若遇容器重启会留下 `running` 僵尸任务，需在启动时把残留 `running` 置为 `failed` 并可重试（参考 `scheduler/auto_scheduler.py` 的后台线程留底模式）。
- **离线约束**：本机部署在 WSL、外网受限。OCR 与 vision 模型的获取路径需按 `core/hf_utils.py` 离线优先模式处理；reranker 已有 1.1GB 下载先例（`retriever.py:24`）。
- **向量库膨胀**：手册体量远大于合同，Chroma 落盘在 `RUNTIME_DIR/chroma_db`，需评估磁盘占用与检索延迟。
- **召回污染**：手册与合同同库会互相稀释 top-k，C5 建议分库的核心原因。
- **多模态调用成本**：L2 每张图一次 LLM 调用，需设上限与失败降级（降级为「仅记录图片位置，不入索引」而非整份解析失败）。
- **图片存储与访问**：原图需可被前端访问（静态托管路径），注意不要与 `api.py:682` SPA catch-all 冲突。
- **写工具授权**：人工标注与重新灌库属写操作，需按现有 `require_admin`（`api.py:274`）鉴权，与调试台其他写操作口径一致。
