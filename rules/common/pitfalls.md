# 踩坑记录与规范反哺

## 定位

把项目实践中的错误、返工、决策失误沉淀成可复用规则，让规范**从实践中成长**，而不是开局一次写好就定格。

- 静态规范 = 一次写好，之后不再变化，靠人脑记教训
- 成长规范 = 反复踩的坑升级为红线，规则文件标注来源可追溯

## 踩坑记录（docs/pitfalls/）

每次遇到以下情况，**遇坑即记**，不等事后补（对话结束前检查本轮是否有坑未记）：

| 触发 | 记录内容 |
|------|---------|
| bug 返工（同一问题修复多次未解决） | 根因、排查过程、最终解 |
| 半途而废（任务做到一半标记完成） | 真实进度 vs 声称进度 |
| 规则冲突（新代码与既有规则矛盾） | 冲突双方、裁决结论 |
| CR 走读发现问题 | 问题类型、修复方式 |
| 代码验收失败 | 未验收项、原因 |
| 对话中被用户纠正的决策 | 纠正点、正确做法 |

格式：`docs/pitfalls/YYYYMMDD-<主题>.md`

```markdown
## 日期 / 场景
## 根因
## 教训
## 规避动作
## 是否已升级为规则（是 → 链接到 rules 文件）
```

**一次性的坑**只记日志，不进规则文件（避免规则膨胀失焦）。

## 反哺机制（何时升级为规则）

- **每里程碑 / 每对话结束**：审视 `docs/pitfalls/` 里本周期记录
- **重复出现 ≥2 次**（或一次造成资金/数据影响）→ 升级为规则：
  - 语言无关 → `rules/common/<对应文件>` 或新增红线
  - 项目特定 → 项目 CLAUDE.md 附加红线
  - 升级时在规则文件标注来源：`> 来源：docs/pitfalls/YYYYMMDD-xxx.md`
- **一次性** → 留在日志，不升级
- **通用反哺**（对多数项目成立）→ 回填模板包，并在模板 README 变更记录记一行

## 与门禁衔接

- 四门禁的门禁 3（CR 批判式走读）发现的问题 → 同一批进踩坑记录
- 踩坑记录不是事后补：**遇坑即记**，避免上下文压缩/会话重启后遗忘（记忆不可靠，落盘可靠）

## 反例

- ❌ 「这个坑我记住了，不用记」→ 记忆会丢（上下文压缩/会话重启）
- ❌ 一次性的坑也塞进规则 → 规则膨胀失焦
- ❌ 升级规则后不留来源 → 后人无法追溯为什么有这个规则
