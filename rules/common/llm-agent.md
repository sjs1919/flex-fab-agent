# LLM 提示词 / Agent 编排规则

## 红线 1：提示词措辞不得暗示系统故障

给 LLM 的系统提示 / 纠错话术 / NUDGE，**禁止使用「工具不可用」「无法完成」「系统故障」等会被模型理解为故障状态的表述**。

- **后果**：模型会据此拒绝任务（「抱歉，我无法完成这个查询…工具已不可用」），而不是纠正行为——答非所问 + 浪费重试 token。
- **反例**：`「工具已不可用，请勿输出任何工具调用语法」` → LLM 误读为工具坏了，拒绝作答。
- **正例**：`「工具结果已收集齐全，请勿再次调用工具，直接基于上述工具查询结果用中文给出最终回答」` → 正向引导基于已有数据作答。
- **通用原则**：纠错话术只描述「该怎么做」，不描述「系统怎么了」。

> 来源：`docs/pitfalls/20260830-汇总步NUDGE措辞误导.md`（trace 8516ffd）

## 红线 2：重试/纠错时附已收集上下文

LLM 输出未解析工具标记等触发重试时，纠错消息应**附上已收集的工具结果摘要**（如 `tool_results` 前 200 字符/条），引导模型基于已有数据作答，避免它「不信结果想再查一次」再次输出工具调用语法。

> 来源：同上

## 红线 3：护栏「必要段落」检查只告警不拦截

`guardrails` 的排产必要段落缺失检查（`缺少必要段落`）仅打印告警、`is_valid=True` 放行。**依赖此检查拦截 LLM 拒绝话术 / 答非所问文本是无效的**——需要拦截的文本必须进「禁止内容」级校验或在编排层（generate_answer）显式处理。

## 红线 4：关键词意图识别必须区分读/写

用关键词匹配识别 Agent 意图（尤其是审批/排产等**写操作**）时，**必须排除读查询信号**——用户文本含「查 / 查询 / 查看 / 找 / 有哪些 / 哪些 / 列出」等查询动词时，写操作关键词（如「审核」）多为定语（**查**已审核数据）而非谓语（**把 XX 审核通过**）。

- **后果**：写操作强制机制（如 pending_write 注入「用户明确要求执行 approve_schedule」）会对纯查询用户注入**与真实意图冲突的指令**，把 LLM 逼进答非所问循环；格式正常的垃圾答案还会绕过缓存门禁写进语义缓存，重问永远命中。
- **反例**：「帮我**查询**审核通过的批次」→ 误判为审批意图 → 强制工具轮 + 注入审批指令 → LLM 编出「综合调度分析」垃圾（trace e3956b5f）。
- **正例**：查询动词命中即判读操作；「帮我把待审核的排产版本**审核通过**」（无查询动词）才判审批写操作。
- **通用原则**：意图关键词不得只看命中，必须结合上下文（是否查询表达 / 是否动作性谓语）判定。只收关键词不排除读语义 = 读操作被当写操作强制执行。

> 来源：`docs/pitfalls/20260830-app_intent审核关键词误伤读操作.md`（trace e3956b5f）

## 红线 5：LangGraph 节点间传递的状态 key 必须在 AgentState schema 声明

节点间要传递的**自定义状态字段**（如 `pending_write`）必须在 `AgentState`（TypedDict）中声明。LangGraph StateGraph 会**静默丢弃 schema 外 key**——节点设置的值不会进入共享状态，下游节点永远读到默认值，机制看似「修了」实则从未生效。

- **后果**：evaluate 设置的 `pending_write` 从没传到 select_and_execute，审批指令从未注入，「修复」靠 LLM 碰巧听指令（trace 83e162c3 暴露，此前验证 ac6c8048 是 LLM 运气）。
- **排查**：节点间状态传递失败但无报错时，先查 schema 是否声明了该 key。
- **附加**：写操作强制指令（pending_write）注入后，写工具执行完毕应在 evaluate 清状态时同步移除 messages 里的指令消息，避免残留指令干扰后续汇总轮。

> 来源：`docs/pitfalls/20260830-app_intent审核关键词误伤读操作.md`（trace 83e162c3）

## 适用

- 所有 Agent 系统提示词 / NUDGE / 纠错话术
- LLM 输出重试链路
- 输出护栏规则设计
- 意图识别关键词（写操作强制检查 / pending_write 注入）
- LangGraph 状态图状态传递
